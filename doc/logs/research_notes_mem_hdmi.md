## 1. DDR3 内存映射

### 1.1 硬事实（`DDR3内存分配分析.md` §1 + `soc.h` 【代码核对】）

| 项 | 值 | 来源 |
| --- | --- | --- |
| DDR **逻辑基址** `SYSTEM_DDR_BMB` | **0x0000_1000** | `soc.h:68`；文档 §1 |
| DDR BMB 窗口大小 | `0xE000_0000`（3.5GB 解码窗，物理只有 256MB） | `soc.h:69` |
| DDR 物理容量 | 256MB → 逻辑有效范围 ≈ `0x1000 ~ 0x1000_1000` | 板卡（MT41J128M16，2Gb×16，800MT/s） |
| 程序镜像加载目标 | `0x0000_1000`（bootloader 从 Flash 拷入后跳转） | `bootloaderConfig.h: USER_SOFTWARE_MEMORY 0x1000` |
| 单次拷贝上限（默认） | `0x1F000` = **124KB**（→ 建议改到 ~1MB） | `USER_SOFTWARE_SIZE 0x1F000` |
| 程序镜像的 Flash 偏移 | `0x0038_0000`（8MB Flash，与 bitstream 分占；3.5MB bitstream） | `USER_SOFTWARE_FLASH 0x380000` |
| I$ / D$ | **各 4KB，1 路，行 64B** | `soc.h:43-47` |
| DDR3 突发粒度 | **16B**（x16 BL8） | 器件 |
| 片内 RAM | `0xF900_0000`，**4KB**（`SYSTEM_RAM_A_CTRL_SIZE 0x1000`） | `soc.h:50` |
| CLINT（mtime） | `0xF8B0_0000`，`SYSTEM_CLINT_HZ = 100_000_000` | `soc.h:19,56` |
| 外设/寄存器 | `0xF8xx_xxxx`（UART/GPIO/PLIC）；**APB slave0 = `0xF810_0000`（64KB）** | `soc.h:66` |
| 链接脚本（当前 `default.ld`） | `ram ORIGIN = 0x0000_1000, LENGTH = 1M` | 【代码核对】`FinalDemo.map`：`ram 0x00001000 0x00100000` |
| 链接脚本（旧 `freertos.ld`） | `ram ORIGIN = 0x0000_1000, LENGTH = 124K` | 文档 §2/§14 |

> ⚠️ 文档 §1 提醒：模拟器/驱动里把 `DDR_BASE` 暂设 `0x8000_0000` 只是 PC 占位；
> **上板一律用生成的 `soc.h` 值（0x1000）**，所有区域写成 `DDR_BASE + 偏移`，改基址只动一个宏。

### 1.2 文档规定的区域布局（`DDR3内存分配分析.md` §3，权威规划）

```
DDR 256MB（逻辑基址 DDR_BASE = 0x1000）
┌──────────────────────────────────────────────────────────────────┐
│ 程序区    +0x0000_0000  1MB    代码/只读/数据/bss/heap/栈          │
│                                 (bootloader 拷贝目标)              │
├──────────────────────────────────────────────────────────────────┤
│ 精灵/图集 +0x0010_0000  2MB    引擎只读源（KEY 抠图源等）          │
├──────────────────────────────────────────────────────────────────┤
│ 帧缓冲对  +0x0030_0000  FB0 ← ★ 推荐起始地址（Front）             │
│           +0x0040_0000  FB1（间隔 1MB，双缓冲 2MB 窗）            │
├──────────────────────────────────────────────────────────────────┤
│ 空闲      +0x0050_0000  ~250MB  关卡/音频/调试转储/扩展            │
└──────────────────────────────────────────────────────────────────┘
```

| 区域 | 偏移 | 大小 | 端地址 | 软件宏（文档口径） |
| --- | --- | --- | --- | --- |
| 程序区 | `+0x000000` | 1MB | `+0x0FFFFF` | linker `ram` |
| 精灵/图集 | `+0x100000` | 2MB | `+0x2FFFFF` | `SPRITE_BASE = 0x00101000` |
| **FB0（Front / 上屏）** | **`+0x300000`** | `0xFD200`（≈1012KB，<1MB） | `+0x3FD200` | `FB_BASE = 0x00301000` |
| **FB1（Back / 备用）** | **`+0x400000`** | `0xFD200` | `+0x4FD200` | `FB1_BASE = 0x00401000` |
| 空闲 | `+0x500000` | ~250MB | `+0x10000000` | — |

- 帧缓冲规格 **960×540 RGB565，行距 stride = 1920B，每帧 1,036,800B（≈1MB）**；双缓冲共 ≈2.1MB。
- `FLUSH_SCRATCH`（缓存冲刷临时区）文档/`fulltest` 口径为 `+0x500000` = `0x00501000`。

### 1.3 为什么选 +0x300000 / +0x400000（文档 §4 的四条理由）

1. **避开程序镜像区**：bootloader 把程序拷到 DDR 基址运行，`.bss`/heap/栈也长在那里；
   FB 放在 `USER_SOFTWARE_SIZE`（程序区）+ 2MB 精灵区之后再无重叠风险。
2. **对齐**：`+0x300000` 是 **1MB 对齐** ⇒ 自动满足 **16B DDR 突发、64B D$ 缓存行、AXI 突发**全部对齐；
   行距 1920B = **120×16B** ⇒ 行首天然 16B 对齐，扫描输出每行正好 **120 个突发、无跨行碎块**。
3. **双缓冲相隔 1MB**：FB0/FB1 落在不同 DRAM 行/bank 区域，"读 Front + 写 Back"并行时行激活/预充电冲突最小。
4. **固定中低地址而非堆顶**：地址写死、引擎/扫描输出用绝对地址也无妨；heap 向上长到 3MB+ 才可能碰到，
   比"顶置贴 DDR 顶"（算错上限即越界）更稳。

**备选方案（文档 §4）**：程序镜像若会超 1MB，整体后移（程序 4MB → FB0=`+0x800000`、FB1=`+0x900000`）；
原则不变：**FB 对放在"程序+资源区之后"的第一个 1MB 对齐边界，两缓冲间隔 1MB**。

## 2. HDMI / 视频输出如何生成与时钟

### 2.1 数据通路（HDMI 文档 §1）

```
RISC-V 软核 ── 写 AW/W/B 直连 ─────────────────────────► DDR3 控制器
            ── 读 AR/R ─► axi_rd_arb ─────────────────► DDR3 控制器
                            ▲   (v3.2: 两级 L1/L2)
                    fb_scanout ──► RGB888 + DE/HS/VS @148.75MHz
                            ──► dvi_encoder（TMDS 8b/10b，原样复制 03_hdmi_tx_demo，一行未改）
                            ──► HSIO 10:1 串化（Interface Designer LVDS 配置）──► HDMI 显示器
```

- **写通路**：CPU 的 AW/W/B **直连** DDR 控制器（旧版）；v3.2 加了 `axi_wr_arb`（CPU / BitBlt 共享，B 按 owner 分路）。
- **读通路**：**两级仲裁**（`板级集成接线清单.md` §0 + HDMI §9.1）：
  L1 = CPU / BitBlt；L2 = (L1) / 扫描输出 ⇒ **优先级：扫描输出 > BitBlt > CPU**（扫描输出必须最高，否则显示断流）。
- **扫描输出粒度**：按行取 960×540 帧缓冲（1920B/行 = 120 拍 128bit），双行/四行缓冲 ping-pong（跨时钟），
  RGB565→RGB888，`SCALE_SH` 最近邻放大后送 TMDS。
- **引擎 AXI 地址 = CPU 看到的 DDR 绝对地址**（同一套地址空间，软硬件一致）。

### 2.2 时钟与分辨率/时序

| 项 | 值 | 来源 |
| --- | --- | --- |
| 像素时钟 | `hdmi_tx_slow_clk` = **148.75MHz** = 25MHz × 119 ÷ 20（PLL_BR0，与 demo `pll_hdmi` 一致） | HDMI §1 |
| 快速时钟 | `hdmi_tx_fast_clk` = ÷4，相位 2 | HDMI §4 |
| 核时钟 | `core_clk` @ **100MHz**（`ddr3_example_top.v:48`）；FinalDemo 注释里出现过 **87MHz** 的口径（DL 看门狗 4096 拍 ≈47µs@87MHz）——**两个口径并存，量时序前需确认当前 bitstream 实际频率** | 代码核对 |
| 输出规格 | **1920×1080@60（CEA-861）**，H 总 2200（1920+88+44+148），V 总 1125（1080+4+5+36），HS/VS **正极性** | HDMI §2.1；`fb_scanout.v:84-91` |
| 实际刷新率 | 148.75MHz ÷ (2200×1125) = **60.10Hz**，显示器可锁 | 算式（文档 §1 同结论） |
| SDC | HDMI 时钟与 `set_output_delay` 由 Interface Designer 自动生成（`create_clock … hdmi_tx_slow_clk 6.723ns`）；`sdc/ddr3.sdc` 不改 | HDMI §4 |
| 窗口 | `WIN_X = WIN_Y = 0`（左上角）；填满全屏靠 `SCALE_SH=1` 2 倍放大 ⇒ `DISP_W/H = FB_W/H << SCALE_SH = 1920×1080`，**无黑边** | HDMI §8；`fb_scanout.v:192-193` |

### 2.3 时序余量与带宽预算（改设计前必算）

| 量 | 算式 / 数值 |
| --- | --- |
| 一条显示行 | 2200 pclk ÷ 148.75MHz = **14.81µs** = **1481 核拍 @100MHz** |
| v2 取一行 | 120 拍 × 9 核周期（1 拍握手 + 8 拍拆 128bit 成 8 像素）= 1080 周期 ≈ **10.8µs（占 73%）** |
| v2.5 取一行 | ≈ **250~400 拍 ≈ 20%**（行缓冲存 128bit 拍、连续 AR） |
| 余量 | 按 1080p：4µs ≈ **27%**（"够用但不算宽裕"）；迟到一行 ⇒ 该行重复上一行（轻微"回跳/撕裂"，不花屏） |
| 帧带宽 | 960×540×2B = 1MB/帧 = **62MB/s @60fps**；若把 FB 改成 1920×1080 ⇒ **~124MB/s** ⇒ 所以**放大放在扫描输出侧做，DRAM 流量为 0 增量** |
| 整屏 COPY | ≈ **1,889,194 核周期 ≈ 19ms**（v2.5 修复后 1,917,926，+1.5%）⇒ 60Hz 场周期 16.7ms ⇒ COPY 上限 **≈53fps** |
| 扫描输出占读通道 | 整行取数期间 **≈73%** 的时间握着读通道（必须握着：R 回程按 owner 分路） |

### 2.4 对"写帧缓冲"的约束（缓存一致性 / 冲刷 / 对齐）

1. **写方向不受仲裁影响**：CPU 往帧缓冲**写**走 AW/W/B 直连（不经读仲裁），所以扫描输出占着读通道
   不会拖慢软件绘制；被挤的是 CPU 的**取指/取数**（I$/D$ miss 走读通道）。
2. **CPU 写 → 硬件（引擎/扫描输出）读：必须先 `cache_evict()`**。
   `FinalDemo.c:492-498` 的实现 = 向 `FLUSH_SCRATCH`（8KB = 2048 word）写 `0xA5A50000+i`，
   **本质是 store 有序屏障**，保证 CPU 的像素对硬件可见。调用点遍布：写图集后、写描述符后、
   发布前、每个"硬件紧接着要读"的场合（`FinalDemo.c:1445/1544/1959/1975/1997/2008/2019/2317/2329/2469/2650`）。
3. **绝不要用 `data_cache_invalidate_all()` 代替 flush**（HDMI §6.2 根因 2）：
   invalidate 是"作废"语义，在写回（write-back）模式下会**丢弃脏行** ⇒ 硬件读到旧数据；
   还可能丢掉栈上脏数据导致程序行为异常。
   **合法用法**：只在"硬件写完 DDR、CPU 要回读校验"的方向用 invalidate
   （`fulltest.c:70,94,295`、`FBtest.c:17,89,148` 就是这么用的）。
   > 口径冲突待确认：HDMI 文档说 D$ 是 **write-back**（invalidate 会丢脏行），
   > `FinalDemo.c:492` 注释说 **"D$ 是写穿"**（evict 只是有序屏障）。两者对"为什么必须 evict"的解释不同，
   > **安全规则不变**：写后读硬件 → `cache_evict()`；读硬件刚写的数据 → invalidate。
4. **对齐**（见 §3 第 7 条）：本 SoC **不支持未对齐访问**，`sw`/`lw` 落在非 4 字节对齐地址 ⇒
   load/store alignment 异常 ⇒ BSP 默认 trap 死循环 ⇒ **静默停死**。
   像素 16bit、行距 1920B（4 的倍数）⇒ 每行起始对齐只由 **x 的奇偶**决定：
   奇数 x 时用 **16bit 收头/收尾 + 32bit 主体**（`cpu_fill32`）。
5. **对齐的其它层级**：FB 基址 1MB 对齐（满足 16B 突发 + 64B 缓存行）；行距 1920B = 120×16B（行首 16B 对齐、
   无跨行碎块）；显示列表描述符 **16B 对齐**（`DL_BASE*` 只写 `[31:4]`，未对齐写入 → 忽略 + `DL_ERR.DESC_RANGE`）。
6. **撕裂与原子呈现**：
   - 早期"单缓冲 + 无 VSYNC 交换"⇒ CPU 直画当前帧缓冲，**可能出现轻微撕裂**（HDMI §8）。
   - v2.6/v2.7【代码核对】已实现 **FLIP**：`fb_sel`（请求）在 **pclk 域帧边界**锁存（帧中途改请求本场不可见）、
     多比特用**格雷码**做 core→pclk CDC；软件写 `FB_SEL(0x24)` 请求、轮询 `FB_STAT(0x28)`
     （`[1:0]` = 已生效缓冲，`[31:16]` = **场计数**）确认，带 100ms 有界超时，绝不往"可能正在上屏"的缓冲里画。
   - `FB_FLIP_PUBLISH` **编译期默认 0 = 关**：上屏仍走已验证的"整帧 COPY"路径，无需重综合。
   - 清屏引擎有**硬件互斥**：清屏目标 == 正在显示的缓冲 或 == `DRAW_SEL`（正在画的缓冲）⇒
     **一个像素都不写**并置 ERR ⇒"清屏永远不会破坏正在上屏的缓冲"是硬件保证。
7. **帧节奏（frame pacing）**：整帧 COPY ≈19ms > 16.7ms 场周期 ⇒ **单帧固定开销超过场周期时，
   "混合帧"是数学必然**；出路只有"异步/翻页"（v3.2 已有 FLIP），或不要每帧搬整屏。

## 3. 记录在案的全部开发问题（现象 / 根因 / 修复）

### 3.1 `开发问题与解决记录.md`（14 章，按上板时间排序）

**① 串口观察通道失效 → 一串测试结论作废**
- 现象：有开机 banner，之后画面与串口"全无响应"；`m`/`n`/`r` 无回显。
- 根因（两层）：(a) **代码层真 bug**：`uart_poll_char()` 判据写成 `((st>>16)&0xFF)==0`
  取的是 **TX 剩余空间**而非 RX 占用 ⇒ banner 打完 TX FIFO 有货 ⇒ 判据恒真 ⇒ 每圈读空 RX，
  串口指令完全无效且可能吃掉真字符。厂商语义：
  `uart_writeAvailability = (status>>16)&0xFF`（TX 余量）、`uart_readOccupancy = status>>24`（RX 占用）。
  (b) **工具层**：板上→PC 方向在若干构建上确实是死的，最后发现 **PC 侧串口工具需要重启** 【据观察记录】。
- 修复：一律 `if ((uart_status_raw() >> 24) == 0u) return 0;`（反汇编确认：`lw`→`srli a5,a5,0x18`→`beqz`）；
  主循环**非阻塞轮询**、**不调用阻塞的 `bsp_getChar()`**；把"串口是否活"变成独立可观测量（`UST`/`URO`、屏幕方块闪烁）。
- **mini-printf 三条硬约束**（`print.h`）：只认 **`%c %s %d %X %x`**；
  `%u`/宽度数字（`%5d`）会让解析器**错位消耗 va_arg**（后面的 `%s` 拿整数当指针 ⇒ 挂死）；
  `%%` **不被当转义**（`"%%s"` 被当成 `%s` 并取一个没传的参数 ⇒ 野指针挂死）；调试串一律 ASCII。
- `bsp_init()` **必须最先调用**（UART 分频在里面配）。

**② 扫描输出取数无界 → `s_hold` 把 CPU 永久锁在 DDR 之外**
- 现象：整机跑 1~2 秒后彻底静止。分阶段自检（**按操作类别**拆 PH0~PH3）锁死：只碰 MMIO 能跑满 1 秒，
  **一碰 DDR 就死**。
- 根因：`fb_scanout.v` 里 `m_axi_hold = (st == S_FETCH)`，而 `S_FETCH` 的**唯一出口**是收满 120 拍
  （无超时、无看门狗）；`axi_rd_arb.v` 归还通道要求 `cnt_s==0 && !s_arvalid && !s_hold`
  ⇒ 任一行收不齐就**永远不归还**。而 linker `ram` 只有 124KiB、整个程序（代码/数据/栈）都在 DDR 最开头
  ⇒ CPU 拿不到读通道 = **取指都取不到** = 整机死（片内只有 4KB RAM，装不下 ~12KB 程序）。
- 二次上板暴露下一层：看门狗把"永久死"换成**重试风暴**（CPU 猛写 → 写队列满 → 读延迟暴涨 →
  某行收不齐 → 超时 → 立刻重试），`s_hold`/`s_arvalid` 每次都占通道 ⇒ 占用率 ≈100%，现象一样。
- 修复（`fb_scanout.v`，不改端口表）：`S_FETCH` 看门狗 `FETCH_TO=4096`；新增 `S_DRAIN`（保持
  `rready=1`/`s_hold=1` 把已下单突发的残留 R 拍用 **rlast 计数**收干净，**不**标 `buf_ready`）；
  口径兜底（短回也认本行结束）；`m_axi_hold` 由"整行"改为**按突发** `(ar_idx != burst_done)`；
  新增 `S_BACKOFF=4096` 强制退避；进 `S_FETCH` 时 `drain_to <= 0`；`dbg_abort` 用
  **单比特 toggle + 两级同步 + 目标域累加**（原双 always 驱动同一 reg ⇒ Efinity `VDB-1000/1001`）。
- 证据：故障注入 TB `tb_scanout_wd.v`：`m_axi_hold` 连续为高 **133 拍（有界化）vs 131,075 拍（无界）**，
  判决 ALL PASS vs FAILED；实跑 `hold_max=132`。**有界性算术**：`s_hold` 最坏 ≤ `FETCH_TO+DRAIN_TO`
  ≈ 8192 拍 ≈ **82µs**（core 100MHz），远小于一帧 16.7ms；加退避后扫描输出占读通道上限
  `8192/(8192+4096) ≈ 67%` ⇒ **CPU 至少 1/3 读带宽，"最坏只是慢，不会死"**。
- 教训：**"钉住资源"的机制必须同时有释放上限**。

**③ 960×540 → 1080p 满屏 2 倍上采样（明确需求 + 测试台自坑）**
- 根因/设计：最近邻放大的坐标映射必须**同时**作用于横向、纵向与"已消费源行号"三处：
  `xoff=(hcnt-WIN_X)>>SCALE_SH`、`vsrc=(vcnt-WIN_Y)>>SCALE_SH`、`par_cur=(SCALE_SH==0)?vrel[0]:vrel[1]`、
  `cons_p=vsrc`（否则 core 域按输出行节奏取数 ⇒ 取两倍的行 ⇒ 把带宽又吃回去）。
- TB 四条自坑：把"像素里编码的源行号"当"输出行号"推期望（**3465 个假错误**）；`run_same` 忘递增；
  判定起点落在帧中间/跨帧回绕；每行**最左 1~2 像素是黑的**——定位打印显示 `buf_ok=1/rdy=11`（**不是欠载**），
  是行首控制/数据通路的固定对齐瞬态，TB 按 `hcnt>3` 排除。
- 修法：判据改成**坐标无关的序列性质**（第 k 个像素源列号 = `k>>1`；相邻输出行源行号"重复"或"+1"）。
  结果：41 行检查、0 错误、重复 20/前进 19、DE 期间黑像素 0、AR=38 笔（**不因放大而多读**）。
- `SCALE_SH=0` 时与 v1.0 **逐位等价**（`tb_fb_scanout` 显式 `.SCALE_SH(0)` 继续守"不放大"那条路）。

**④ 板载按键引脚够不到**
- 现象：4 个按键物理在 `GPIOL_07 / GPIOR_22 / GPIOR_21 / GPIOL_03`，而 `soc_gpio[0..3]` 接在
  `GPIOR_27 / GPIOR_24 / GPIOL_P_12 / GPIOL_P_02` ⇒ 读回来是悬空值（改脚前自检 `KEY=0x08`）。
- 根因：约束文件 `gpio_def` 与板级按键物理引脚不对应（**约束配置错误**，RTL/SoC 无问题）。
- 修复：只改 `comp_gpio` 的 `gpio_def`/`io_standard`（总线名与位宽不变 ⇒ **不需要重新生成 SoC**，重跑 P&R 即可）：
  `soc_gpio[0]`→GPIOR_22（模式切换 CPU↔硬件）、`[1]`→GPIOR_21（N +25）、`[2]`→GPIOL_03（场景复位）、`[3]` 不动。
  注意 `GPIOL_07` 已被 `i_arstn`（复位键）占用 ⇒ 4 个键只有 3 个可用；
  **UART 引脚**：`txd = GPIOR_28`、`rxd = GPIOL_02`（改约束时不可抢）。
- 上板验证：`KEY=00000007`（三位都读到高，板上有上拉）。

**⑤ OSD 信息栏花屏**
- 现象：2 倍放大生效后信息栏乱码，**字形碎成 2 像素一块**。
- 根因：帧缓冲**小端** ⇒ 32bit 存储的**低 16 位落在低地址 = 左边像素**；第一版把第 1 个像素（字模 `bit7`）
  放进**高**半字 ⇒ 每个字里两个像素**对调**。
- 修复：低半字放 `bit7/5/3/1`、高半字放 `bit6/4/2/0`（`p[0] = ((bits&0x40)?fg<<16:bg<<16) | ((bits&0x80)?fg:bg)`）。
- 教训：位图 bug 先看"**错位的单位**"（bit / 半字 / 字 / 行）。

**⑥ 读仲裁器 `cnt_s` 泄漏具有永久否决权**
- 现象：第三次上板 `SCAN=00070108`（高 16 位 = `dbg_abort=7`）后 CPU 彻底死、画面停在最后一帧。
- 根因链：看门狗硬放弃时**扫描输出清的是它自己的账本**（`ar_idx/burst_done=0` ⇒ `s_hold` 落下），
  但那笔突发的 AR 在仲裁器里**早已计入 `cnt_s`**，对应 rlast **永远不会来** ⇒ 归还条件
  `cnt_s==0 && !s_arvalid && !s_hold` 中 `cnt_s` **永不归零 ⇒ 永久否决** ⇒ owner 永远停在 1。
- 修复：`axi_rd_arb.v` 新增 `LEAK_TO`（默认 256 拍）：
  ```verilog
  wire s_quiet = !s_arvalid && !s_hold;
  if (s_quiet && (cnt_s != 0)) leak_c <= leak_c+1; else leak_c <= 0;
  if (s_quiet && ((cnt_s == 0) || (leak_c >= LEAK_TO))) owner <= 1'b0;
  ```
  即 `cnt_s` 只能当**优化**、**不能具备否决权**。证据：TB `tb_rd_arb_leak.v`：`cnt_s` 恒 1、
  `owner` 修复后 **1→0**（`leak_c=257`）/ A/B 永远停在 1；C 侧完成突发 **57,105 笔 vs 0 笔**；
  C 侧最长 AR 等待 263 拍。CPU 每次泄漏事件最坏锁定 ≈ **2.6µs**（有界无害）。
- TB 自坑：`28'h010_0000` 是 **bit20** 而不是 bit24，从机把 S 那笔当 C 的回满并拉 rlast ⇒ 泄漏复现不出来
  （A/B 两边都 PASS）。**"A/B 没差异"时不要改结论，要查激励。**

**⑦ CPU 静默死亡：未对齐 32bit 存储（所有早期"冻屏"的真正根因）**
- 现象：画面静止、串口再无输出；修完 ②⑥ 之后**仍能复现**。
- 走过的弯路（**四次全是针对一个幻影**）：① 取数无界 ⇒ 加看门狗；② `dbg_abort` 双驱动 ⇒ 改 CDC；
  ③ 读仲裁 `cnt_s` 泄漏 ⇒ 加 `LEAK_TO`；④ "预热"绕过。这四次在 RTL 里各自修掉了真 bug，
  但**都不是这个冻屏的原因**——把 CPU 侧对齐问题修好后，同样的"开机正常→跑一会儿静止"在**没再动 RTL** 的情况下消失。
- 定位：把"写哪里"从自变量里消掉（改成只写屏外缓冲后**冻屏依然出现**）⇒ 唯一剩下的自变量是
  **CPU 侧 32bit 访问落在奇数 x 上**：`scene_step()` 让 `x += vx`、`vx ∈ {±1,±2,±3}` ⇒ x 会变奇数；
  第一版 `cpu_fill32` 直接 `*(volatile uint32_t*)(base + y*1920 + x*2)` ⇒ 奇数 x 上就是未对齐 `sw`。
  当年 `FBtest` 能跑是因为它用 **16bit** 存储。
- 根因：RISC-V（RV32IM + Zicsr）**不支持未对齐内存访问** ⇒ 触发 load/store alignment 异常 ⇒
  BSP 默认 trap 是**死循环**（与更早"读未实现 `mcycle` CSR 触发非法指令异常"完全同类）。
- 修复：① 对齐安全的 `cpu_fill32`（奇数 x 用 16bit 收头/收尾，主体 32bit）；
  ② **删掉 `x & ~1` 这个补丁**（强行取整成偶数会让 `vx=±1` 的方块卡住不动、永远不擦 ⇒ ALPHA 场景一路变暗）；
  ③ 开机 `aligncheck`（奇数 x=33 画 8 像素、偶数 x=32 画 9 像素后逐点读回）。
- 教训：**"静默停死"第一件事是确认是不是异常，而不是先怀疑总线仲裁**；
  软件侧一行可疑的强制类型转换比 RTL 里十个计数器更值得先查；**现象相同不代表机制相同**。

**⑧ `SCR=0` / OSD 从未被搬上屏：硬件推指令的节奏错了**
- 现象：硬件模式画面在动，但"上屏帧率" `SCR` 恒 0、状态条从不刷新。
- 根因：`blt_idle()` 判据是 `DONE && FIFO_EMPTY && !ERR`；只要"FIFO 一有空间就补下一帧"，
  `FIFO_EMPTY` 永远为假 ⇒ 引擎永远 BUSY ⇒ `blt_idle()` 永不为真 ⇒
  上屏计数/场景推进/OSD 搬运三件事全都不发生。**"完成"是需要在指令流里留出空隙才能被观测的事件。**
- 修复：**按帧节流**（推满一帧就停手，等引擎真空后推进）；新增 `hw_frame_pushed`，在**确定的空闲点**
  做三件事；下发前一律 `blt_can_push()` 查空间（`cnt <= DEPTH - HW_FIFO_MARGIN(56) - 1`）——
  **FIFO 满时写 DATA 会把 CPU 挂在 APB 上，主循环会死在那里**。

**⑨ 改 N / 切模式后屏上留下旧方块**
- 根因：**重铺（repaint）缺失**。增量渲染的 `dx/dy` 记账只在"上一趟画过、这一趟仍在名单里"时成立；
  `n` 变小后多出来的方块像素已写进帧缓冲，但场景数组里没有它们的下标了。
- 修复：两侧各自 `repaint[2]` / `repaint_hw` / `repaint_cpu` 标记，任何"场景/路径/模式/复位变化"都置 1，
  下一趟先整片铺回背景（**`scene_sync()` 让 px=py 重新对齐**）；硬件侧重铺 = 引擎整屏 `blt_fill` **紧跟一条 COPY**
  把状态条补回（依赖命令 FIFO 保序）；顺带修 `vrg_h(path)`（原虚拟区高度固定 `HALF_H`，导致单模式只渲染一半）。

**⑩ 运动尾迹（以及一次失败的"两阶段"重写）**
- 现象：路径上拖残影，**越慢的一侧（帧率越低）越稠密**；ALPHA 场景"不动时逐帧变暗、步进时恢复"的 **25Hz 忽明忽暗**。
- 根因：① **记账时刻错误**（趟结束时记 `dx/dy`，而绘制用趟内实时位置 ⇒ 一趟内前后块位置不一致）；
  ② **两阶段重写放大瞬态窗口**（"已擦未画"从 1 块拉长到 N 块 ≈10ms，屏幕 16.7ms 采一次样 ⇒ 更容易被拍到）——
  这次重写"没修好闪烁 + 引入尾迹"，说明它对闪烁的因果判断本身就错。
- 修复：① 每趟开始 `scene_snap()` 冻结 `x,y → tx,ty`（**快照 = 把动画时间与渲染时间解耦**）；
  ② 回到相邻式擦+画；③ **双缓冲**（中间态关在后台缓冲）；④ **ALPHA 必须每次都擦**（FILL/KEY 幂等可省擦）。
  25Hz = `SCENE_TICKS = BSP_CLINT_HZ/25` = 40ms 步进。

**⑪ 重叠处上下关系高频切换（z 序乱跳）—— 最长的一次调查**
- 现象：背靠背下发多条**写重叠区域**的指令时，重叠处 z 序高频闪/换；**纯 CPU 渲染没有**。
- 定位与结论：
  - **仿真证伪 WAW 假设**：新 TB `tb_wr_order.v` + 可乱序提交从机模型 `axi_slave_mem_ord.v` 测出
    写突发**在飞峰值 = 1**，RTL `b_pending` 与引脚上 AW−B 完全一致，T3（重叠 FILL 的 WAW）**屏障 OFF 时也 PASS**
    ⇒ **写通道本来就是程序序，WAW 重排在这份 RTL 里不可能发生**（结构性证据：写主机 `S_AW→S_W→S_B→S_IDLE`
    串行、`m_axi_awvalid=(st==S_AW)`；写仲裁是纯组合直通、只在 `cnt_b==0 && !b_wvalid` 换 owner）。
  - **但 TB 抓到一个真的"假完成"**：引擎 `ST_WDWAIT` 出口 `wd_empty && !wd_busy`，
    而 `sync_fifo.empty = !out_v`（**同步读 + 输出寄存器**）⇒ 最后一个写词推进 FIFO 后要 **2~3 拍**才在 `out_v` 可见，
    这段窗口里 `empty=1`（**假空**）。逐拍时间线 ⇒ **`BUSY=0` 比"这个词被 AXI 受理"早 3~4 拍、
    比"内存系统受理（B）"早了一次写往返**；软件按 BUSY 判完成 ⇒ 下一条 dst/src 读抢在前面（**RAW 危险**）
    ⇒ ALPHA 混到旧背景、KEY 用旧值比较 ⇒ 重叠处"层级闪/换"。
    证据：H1「引擎报 IDLE 那一拍写通路是否干净」117/**0**（屏障 ON）vs 117/**55**（OFF）；
    T1/T2/T2b 屏障 OFF 全 FAIL，T3 两侧都 PASS。
  - **板级对照**：**纯硬件模式（`h`）完全不出现 z 序乱跳** 【据观察记录】⇒ 现象只属于 SPLIT 模式
    （**两个主机写同一块后台缓冲** + "发布"被**更慢的 CPU 侧**用 `hw_done/cpu_done` 门控）。
  - **另两条残影是擦除策略**：只擦旧矩形会 (i) 咬到本趟已画好的邻居（背景色拖尾，**宽度 = 每步位移**）、
    (ii) 不刷新新位置前沿带（KEY 场景洋红透明四角露出旧像素并闪烁）。
- 修复：**① RTL 指令边界写屏障**（`b_pending`：AW +1 / B −1 带 0 保护；
  `wr_idle_committed = (b_pending_r==0) && (st==S_IDLE)`；`blt_top` 合成
  `wr_commit_idle = wr_idle_committed && wd_count==0 && !wd_busy`；引擎 `done_out` 与 `ST_WDWAIT` 出口都并上它）。
  **吞吐代价 = 命令尾部一次写往返**（T4a +2 周期、T4b +0、T4c +8、T4d +38），
  指令内部的写突发仍与行计算重叠、**没有把像素串行化**。
  **② 软件 `e` 模式 = 每趟整片重铺 + 不发任何逐块擦除**（第一版只加整片清屏却保留破坏性逐块擦除 ⇒ 看起来毫无用处）；
  CPU 侧**故意保持"先擦后画"**不动，这样 CPU-vs-HW 帧率对比才诚实。
- 教训：**"完成"的定义要落在最下游的确认上（这里是 B）**，不能用上游"看起来空了"的代理标志。

**⑫ 性能回退：OSD / 像素扫描诊断把帧率吃掉了**
- 现象：加"周期性像素扫描"后 `HW=` 明显下降，关掉立刻回升。
- 根因：诊断代码走**与引擎/扫描共享的 DDR 读通路**（两级 `axi_rd_arb`）；
  每帧几万次 16bit 读几乎全 miss、还按行填充 ⇒ 既占带宽又拉长引擎突发排队。
  **测量装置改变了被测对象。** 算式：`dbg_quick`（1/4 抽样）125,760 点 ×2 缓冲 = 251,520 读/次（每 32 帧）+
  `osd_fill`（1/16）31,440×2 = 62,880 读/次（每 4 帧）⇒ **平均 ≈23,580 次/帧**，
  代价 **2.4~4.7ms/帧** 【据观察记录】；SPLIT 模式约 11,700 次/帧。
- 修复：周期扫描**停用**，只保留手动 `'d'`；最终版彻底删除 `dbg_quick`/`osd_fill`，
  信息栏改成"≥16 个已发布帧 且 ≥300ms"才刷、只写 `960×16` 黑底 + 两串 8×8 点阵（**不含任何逐像素 DDR 扫描**）。
  **优先用硬件计数器观测**：`0x20 SCAN_DBG`。

**⑬ 显示通路与帧时间：一帧 16.7ms，整屏 COPY 就要 19ms**
- 根因：整屏 COPY 960×540 ≈ 1.89M 核周期 ≈ **19ms** @100MHz > 60Hz 场周期 16.7ms ⇒ **COPY 上限 ≈53fps**；
  单缓冲串行"画完再搬"时屏幕每 16.7ms 采一次样而搬运要 19ms ⇒ 显示内容必然是两帧混合，帧率被压到 30 多 fps。
- 修复（软件已实施）：**双缓冲**（`FB_BACK` → 整帧 COPY → `FB_BASE`），只有这一处写显示缓冲；
  **统计口径分开报**：`HW=`/`CPU=` 是**纯渲染**完成帧率（不含 COPY 等待），`SCR` 是**实际上屏**帧率。
- RTL 侧当时**尚未实施**（文档 §13）：① 扫描输出基址**寄存器**（当时是参数，无法翻页）；
  ② 场/帧计数可读（`frame_tick` 顶层悬空未接）。**【代码核对】这两项在 v2.6/v2.7 已实现**
  （`FB_SEL`/`FB_STAT` + 场计数 + 帧边界中断），见 §2.4 第 6 条。
- 原理：游戏渲染需要三条性质——**单写者**、**原子呈现**（场边界切换）、**固定的每帧命令预算**。
  双缓冲仍要搬整屏（19ms 只是被藏到后台），**翻页只改一个寄存器（0 搬运）**。

**⑭ 最终演示程序 `FinalDemo`（两个过程事故）**

### 3.2 `HDMI输出集成说明.md` 记录的问题

**编译期（§6.1）**
1. `ERROR: io_bank_rule_lvds: I/O Voltage has to be set to 1.8 V when LVDS Tx is used`（bank 3A）：
   TMDS 引脚 `GPIOR_PN_10..13` 在 **I/O bank 3A**，LVDS 发送强制该 bank **1.8V**，
   而工程沿用 DDR demo 默认 `3A = 1.5V LVCMOS` ⇒ 改成 `3A=1.8V LVCMOS`；
   依据板卡官方 09/10 号 demo：**DDR 在 3B/4A/4B（1.5V），HDMI 在 3A（1.8V），两不冲突**。
2. `warning: lvds_rule_tx_distance … GPIOR_P_09`：DDR 时钟 `ddr_ck`(P_09) 与 HDMI 时钟 `tmds_clk`(PN_10)
   板上是**相邻引脚对**，工具提示噪声耦合——**板卡布线决定、无法规避**（官方 demo 同样），
   warning 不影响流程；若 HDMI 时钟抖动导致偶发花屏，优先查 DDR 与 HDMI 的电源/地。

**软件侧第一轮（§6.2：屏上只有彩条、看不到方块）**
1. **主因：每帧整屏重画背景**（960×540 ≈1MB = **259,200 次 32bit 写**）：
   本 SoC 每次写 DDR 都要走 AXI → 软核 DDR3 控制器，单次开销几十周期，整屏重画要**几十毫秒**；
   方块只在"画完 → 下一帧被背景盖掉"之间存在于 DDR 中，占一帧比例只有百分之几 ⇒ 扫描输出几乎永远扫不到它
   （彩条是背景所以一直看得见）。
2. **每帧调用 `data_cache_invalidate_all()`**：invalidate 是"作废"语义，写回模式下**丢弃脏行**；
   对"CPU 写 → 外部主设备读"这个方向正确操作是 **flush/挤出**（`cache_evict()` 写 8KB 冲刷缓冲），
   而且 invalidate 还可能丢掉栈上脏数据。
3. **次要：`dx2 = -9` 等奇数步进**破坏 32bit 写（两像素打包）的像素对齐。
- 修复（fbTest v2）：静态内容只在开机画一次；每帧只重画两个方块自己的矩形（≈1.4 万次写，**少 18 倍**）；
  用 `csr_read(mcycle)` 按 `FRAME_CYCLES = 1,670,000`（≈16.7ms≈60fps）节流；每帧末尾**只** `cache_evict()`；
  每 60 帧打印 `draw/period/fps`。
- **现场判断技巧**：白边框与固定红块是"静态写入"的证据——若彩条/边框/红块都在、只有方块不见 ⇒
  写入通路正常，问题在动态元素**可见时间（节奏）**；若连边框/红块都不见 ⇒ 首帧之后的写入没真正落到 DDR（查缓存/地址）。

**硬件侧（§6.3：自测平台先复现 → 定位 → 再修）**
1. **取数门控用了 `buf_ready`（主因）**：该标志只在取数开始时清 0，两个行缓冲各取满一次后再没人清它
   ⇒ 取数永久停在第 0/1 行、屏幕一直重复这两行。软件 v1 的 FB 第 0/1 行是彩条 ⇒"只有彩条"；
   v2 的第 0/1 行是顶部白色边框 ⇒"满屏白"。**两者现象相反、根因同一个。**
   修复：门控改成"最多比显示侧正在消费的行超前 1 行 + 不写正在显示的那个缓冲"。
2. **行缓冲写口错位**（画面整体右移 1 像素、丢最后一个像素）：写使能/写数据/写地址在**同一时钟沿寄存**
   ⇒ RAM 写沿看到"地址已 +1、数据还是上一拍" ⇒ 第 k 个像素写进第 k+1 地址（`buf[0]` 永远是 X）。
   修复：写地址用寄存器、**写使能与写数据改为组合产生**。
3. **行缓冲读地址多寄存了一拍** ⇒ 数据比控制晚 1 个像素 ⇒ 每行第一个窗口像素显示上一行残留、整幅右移 1 像素。
   修复：读地址改**组合地址**（= 当前列号），数据与控制都恰好 3 拍。
4. **RGB565→RGB888 绿分量拼接位宽错**：`{px2[10:5], px2[8:5]}` 是 6+4=10 位、赋 8 位被截断 ⇒
   绿分量比特顺序变成 `{G3 G2 G1 G0 G5 G4 G3 G2}`；正确是 `{px2[10:5], px2[7:6]}`（6 位绿 + 补低 2 位）。
   红/蓝 5 位拼接本来就对，所以只坏绿色。**上板看是偏色，自测里更致命**（TB 把行列号编码进像素再读回校验 ⇒ 全错，
   一度把定位带偏成"行号不递增、列号跳到 64"）。
   > 诊断经验：读回数据"整体像被比特打乱"时优先怀疑**通道扩展/位宽拼接**，
   > 先确认 `DUMP` 的行缓冲内容与源数据**逐位一致**，这一步能把"存储通路"与"重建通路"彻底分开。

**自测平台自身的坑（§6.4）**
| 坑 | 症状 | 原因 / 处理 |
| --- | --- | --- |
| 像素时钟设得和核时钟一样快 | "行号十几行才推进一次" | 自测一条显示行只有 960ns，而取一行要 120 拍×8 周期=9.6µs，显示侧比取数快 10 倍。**真实 1080p 是 14.8µs/行 vs 9.6µs 取数**，自测必须保持同样比例（现用 19.2µs/行） |
| 复位释放早于第一个像素时钟沿 | `hcnt/vcnt` 恒为 X、窗口像素一个都不输出 | 复位必须在**至少一个 pclk 上升沿之后**才释放 |
| 在 `posedge pclk` 同时采样 `ctrl2` 与像素值 | 行列号"跨行混搭"的假错误 | 同一时刻读控制与数据有竞争；改到 `negedge pclk` 采样 |
| 第一帧参与判定 | 第 1 行少 3 个像素 | 复位后行缓冲还没取到数、"就绪"标志跨时钟域还要 2 拍同步；第一帧只统计不判定 |

**软件侧第二轮（§6.5：静态画面正确但完全不动、串口停在 `static pattern`）**
- 定位链（纯推理，不需仪器）：屏幕上的内容 = 循环**之前** `draw_static_marks()` 画的东西（右上角红块）；
  而循环体第一件事就是把 120×90 大方块画到 (8,8)、色表第 0 项是红色 ⇒ 屏上**没有**它 ⇒ 第一轮没走完；
  日志最后一行 `static pattern: ...` 的下一句正是 `t_prev = csr_read(mcycle)` ⇒ 嫌疑锁定这次 CSR 读。
- 根因：**`mcycle` 属于可选实现的 CSR**。SoC 只保证 `Zicsr` 指令可用（`SYSTEM_RISCV_ISA_EXT_ZICSR=1`），
  不保证周期计数器存在；读未实现 CSR ⇒ **非法指令异常** ⇒ BSP 默认 trap（死循环）⇒ 程序停住、
  串口无输出、屏幕保留最后一帧。旁证：BSP 与厂商 demo 计时**一律用 CLINT `mtime`**，全树 `mcycle`
  只出现在一个未使用的宏里。
- 修复（v3）：改用 `clint_getTime(BSP_CLINT)`（`BSP_CLINT+0xBFF8` 的 mtime，普通 MMIO 读，不可能陷入异常），
  节流循环另加次数上限兜底。
- v3 分步自检判读表（§6.6）：`step1 timebase OK/BAD`、`step2 coherency check PASS`、
  `step3 write probe N ticks/word` + 预算、`step4 bars`、`step5 blink test`（实时上屏自检）、`step6 entering main loop` + `frame=`。
  判读：有 step5 且屏幕闪 3 次但无 `frame=` ⇒ 问题在循环体；`frame=` 正常但屏幕不动 ⇒ 写入没落到 DDR（缓存）
  或扫描输出没看到（回看 step5）；step5 打了但屏幕不闪 ⇒ 实时上屏通路有问题；
  `frame=` 出得来但 fps 很低 ⇒ 看 step3 的 ticks/word，减少每帧写次数（缩小方块、只擦"L 形区域"）。

**软件侧第三轮（§6.7：静态红块被移动方块"碰掉"）**
- 根因：`restore_bg()` 语义是"把这块整片铺回彩条"，它不知道那里还有一层静态标记；
  大方块移动范围 x∈[8,832]、y∈[8,442] 与固定红块 (820..931, 16..95) 必然相交 ⇒ 红块被涂掉，
  而 `draw_static_marks()` 只在开机调用一次 ⇒ **永久消失**（白边框没事，因为动态方块被限制在边框内侧）。
- **这不是显示异常，而是演示程序少了图层概念**：正确层次是 **彩条(底) < 静态标记 < 动态方块(顶)**。
- 修复（v4）：红块位置/尺寸提成 `MARK_X/Y/W/H` 常量，擦除后按相交区域把静态标记补画回来。
- 通用教训：**擦除必须知道背景由哪些图层组成**；等 BitBlt 引擎接进来后这类合成应交给硬件。

## 4. 加新 demo 必须遵守的"坑清单"（可直接当检查表）

### A. 地址与布局
1. **所有 DDR 区域写成 `DDR_BASE + 偏移`**，`DDR_BASE = soc.h 的 SYSTEM_DDR_BMB = 0x1000`（**禁止留 PC 占位 0x80000000**）。
2. **硬件 `fb_scanout.FB_BASE/FB_BASE1/FB_BASE2` 必须与软件 `FB_BASE/FB_BACK/FB_BUF2` 逐位一致**；
   当前值 `0x0030_1000 / 0x0050_1000 / 0x0070_1000`。不一致 = 屏幕全黑或错位。
3. **别把新缓冲塞进已占用区**：已用 = 程序区 (+0x0~1MB)、ATLAS (+0x200000)、FB_BASE (+0x300000)、
   FB_BACK (+0x500000)、FLUSH_SCRATCH (+0x600000, 8KB)、FB_BUF2 (+0x700000)、
   DL 几何表 (+0x800000)、DL 列表 0/1 (+0x820000/+0x840000)。**新区域从 +0x900000 之后取**。
4. **把缓冲区起始地址放在 1MB 对齐边界**（自动满足 16B 突发 + 64B 缓存行 + AXI 突发）；行距用
   `960×2 = 1920B`（=120×16B，行首 16B 对齐、无跨行碎块）。
5. **帧缓冲尺寸不要随便改**：改成 1920×1080 会让 DDR 读带宽翻倍（62→124MB/s）；
   要"变清楚"就改扫描输出的 `SCALE_SH`（DDR 流量 0 增量）。
6. **程序区变大要同步三处**：`bootloaderConfig.h` 的 `USER_SOFTWARE_SIZE`、链接脚本 `ram LENGTH`、
   重编 bootloader.hex 并在 IPM 重新生成 SoC（当前 `default.ld` 已到 1M）。
7. **Flash 只有 8MB**，bitstream 占 ~3.5MB，程序镜像建议 ≤1MB；数据/图集运行期放 DDR，不要塞 Flash。

### B. 缓存一致性（最容易翻车）
8. **CPU 写完 → 硬件（引擎/扫描输出）要读：调用 `cache_evict()`**（8KB 写穿屏障，`FinalDemo.c:493`），
   在"硬件紧接着要读"的每个点都要调（图集、描述符、发布、开机首屏）。
9. **绝不用 `data_cache_invalidate_all()` 代替 flush**：它是"作废"，写回模式下会丢脏行、还可能丢栈上脏数据。
   invalidate 只用在相反方向（**硬件写完 DDR、CPU 回读校验**，如 `fulltest.c` step [3]/[6]）。
10. `bsp_init()` **必须最先调用**（UART 分频在里面配）。

### C. 对齐（会静默停死）
11. **任何 32bit 访存地址必须 4 字节对齐**：本 SoC 无 misaligned 通路 ⇒ `sw`/`lw` 落在奇数 x 上会触发
    alignment 异常 ⇒ 默认 trap 死循环 ⇒ **屏幕停最后一帧 + 串口静默**（和"取不到 DDR 读通道"现象一模一样）。
    写法：奇数 x 用 16bit 收头/收尾，中间主体才 32bit（`cpu_fill32`）。
12. **不要用 `x & ~1` 之类的"取整"补丁**：`vx=±1` 的方块会被卡住不动、永远不擦（ALPHA 场景一路变暗）。
13. **开机自检**：奇/偶 x 各画一次再逐点读回（`aligncheck`）；给每一类"静默失败"配一个上电第一秒可见的自检。
14. 显示列表描述符必须 **16B 对齐**（`DL_BASE*` 只写 `[31:4]`，未对齐写被忽略并报 `DL_ERR.DESC_RANGE`）。

### D. 硬件加速器接口
15. **写指令 FIFO 前必须先查空间**：FIFO 满时写 `CMD_FIFO_DATA` 会把 CPU 挂在 APB 上、主循环死在那儿。
    用 `blt_can_push()`（`cnt <= DEPTH − HW_FIFO_MARGIN(56) − 1`），或"每圈读一次 COUNT 后自己记账"。
16. **"完成"要看 `DONE && FIFO_EMPTY && !ERR`（`blt_idle_st`）**，且**必须按帧节流**：
    "能推就推 + 轮询完成位"会让 `FIFO_EMPTY` 永远为假 ⇒ 完成事件永远观测不到（`SCR=0`、OSD 不刷新）。
    RTL 侧 v3.2 的完成判据已并上 `b_pending==0 && wd_count==0 && !wd_busy`（**B 才是写受理的确认**）。
17. 引擎的 AXI 地址 = CPU 的绝对 DDR 地址（同一地址空间）；`SOFT_RST` 会清指令 FIFO ⇒
    流程是 SOFT_RST → 0 → 推指令 → GO。
18. **别再声明隐式线网**：`apb_paddr/apb_pwdata/apb_prdata` 必须显式声明为 32 位；
    elaboration 用 `iverilog -Wimplicit` 验证 **0 告警**。

### E. 显示通路的节奏与仲裁
19. **扫描输出优先级最高（> BitBlt > CPU）**，且它在整行取数期间握着读通道 ≈73%：
    **CPU 读（含取指）会变慢，CPU 写不受影响**。任何"周期性逐像素 DDR 回读"诊断都会抢同一读通路，
    实测压低帧率 **2.4~4.7ms/帧（≈23,580 次读/帧）** ⇒ 诊断必须可关闭/手动触发，
    **优先用硬件计数器**（`0x20 SCAN_DBG`：`[15:0]` 欠载行、`[31:16]` 看门狗中止）。
20. **不要往"正在显示"的缓冲里画**：用双/三缓冲 + `FB_SEL` 请求 + 帧边界锁存 + `FB_STAT` 轮询确认
    （有界超时；宁可停一帧也不撕裂）。清屏引擎有硬件互斥（目标 == 显示缓冲 或 == `DRAW_SEL` ⇒ 拒写 + ERR），
    但**软件自己直写**没有这层保护。
21. **帧预算先算**：整屏 COPY ≈19ms > 16.7ms 场周期 ⇒ 单帧固定开销超预算就必然出现"混合帧/低帧率"，
    出路是异步/翻页，不是"搬得更快"。
22. **增量渲染要有失效入口**：任何改变"目标集合"的操作（改 N / 切场景 / 切模式 / 复位）都要
    整片重铺（`repaint_*`），并注意重铺别擦掉不该擦的（信息条放 `y=0..16` 的渲染区之外）。
    **ALPHA 必须每次都擦**（非幂等，不擦会一次比一次暗）；FILL/KEY 幂等可以省擦。
23. **一趟渲染开始拍场景快照**（`scene_snap`：`x,y → tx,ty`），一趟内位置恒定；
    否则帧率越低尾迹越密（把"动画时间"与"渲染时间"解耦）。
24. **整片重铺 + 不发逐块擦除**是上板验证过能同时消掉"邻居拖尾"和"KEY 透明四角闪烁"的组合；
    只加整片清屏却保留逐块擦除 = 没用。

### F. UART / printf（测量通道）
25. **RX 判据用 `status>>24`（占用），不是 `>>16`（TX 余量）**；主循环非阻塞轮询、不调用阻塞的 `bsp_getChar()`。
26. **mini-printf 只认 `%c %s %d %X %x`**：`%u`、宽度数字、`%%` 都会错位消耗 `va_arg` 甚至野指针挂死；
    调试串一律 ASCII。`bsp_printf` 的周期性状态行本身也吃 CPU 时间（115200 波特）。
27. **不要读未实现的 CSR**（如 `mcycle`）：会触发非法指令异常 ⇒ 死循环。计时一律用 **CLINT mtime**
    （`clint_getTime(BSP_CLINT)`；高频场合直接读低 32 位 `tick32`，1 次总线读）。
28. 出现"静默停死"：**先确认是不是异常**（对齐 / 未实现 CSR / 默认 trap），再怀疑总线仲裁。

### G. 工程与工具
29. **引脚问题第一件事是对照厂商 demo 的约束文件**（`peri.xml` 的 `gpio_def`），不是调软件极性/消抖；
    改约束前查重，并把时钟/复位/UART 等关键引脚一起核对（UART: `GPIOR_28`/`GPIOL_02`）。
30. **bank 电压**：LVDS/TMDS 所在 bank 3A 必须 **1.8V**；DDR 在 3B/4A/4B（1.5V）。
31. **UTF-8/LF 源码只走编辑器工具**（read/edit/write），不做 PowerShell 文本往返：`Get-Content -Raw`/`Set-Content`
    会把中文注释按 GBK 解坏并吞换行，`-replace` 的 `$1` 是正则反向引用（曾写出 `#define N_MAX$1700`）。
32. **子代理/他人报告的"已验证"不能当证据**：关键产物（标签、寄存器、打印串）必须自己回读文件逐行确认。
33. **A/B 没差异时先查激励**：TB 第一版因 `28'h010_0000` 是 bit20 而非 bit24 导致两边都 PASS；
    给内部状态加**变化监视器**是最便宜的定位手段。测试用例的形状要覆盖真实使用
    （早期 6 个用例全是 8 像素宽/1 词每行，恰好绕过"多词每行"这条最容易错的路）。
34. **"释放/归还/完成"的每个条件都要问：它有独立上限吗？**（`S_FETCH` 唯一出口 / 硬放弃后立刻重试 /
    `cnt_s` 永久否决 / `sync_fifo.empty` 假空窗口——四处各栽一次）。
35. **硬件/TB 证据优于推理**；**否定性证据和阳性结果一样值钱**（`tb_wr_order` 一次性证伪了整个 WAW 方向）。

| `0x00` | `CTRL` | bit0 GO、bit2 SOFT_RST |

## 7. 【重要】文档 vs v3.2 代码的漂移清单（照文档做会踩坑的地方）

| 项 | 三份文档口径 | v3.2 代码实际 | 影响 |
| --- | --- | --- | --- |
| 链接脚本 `ram` | 124 KiB @0x1000（文档 §2/§14） | **1 MB** @0x1000（`default.ld`；`freertos.ld` 仍是 124K） | "整个程序在 DDR 最开头、拿不到读通道就死"这一因果仍成立，但空间不再是 124K |
| 程序镜像大小 | `FinalDemo.bin` 11,986B、`.bss` 40,000B | `FinalDemo.bin` **26,930B** | 规模预算要按当前值算 |
| 后台缓冲 | 文档说 FB1 = `+0x400000`（双缓冲） | 实际 **FB_BACK = +0x500000**、另加 **FB_BUF2 = +0x700000**（三缓冲 FLIP） | 按 `+0x400000` 放数据会与当前实现不一致 |
| 精灵区 | `+0x100000`（2MB，`SPRITE_BASE`） | `ATLAS_BASE = +0x200000`（`FinalDemo.c`） | 图集地址不同；`fulltest/userDef.h` 仍用 `+0x100000` |
| `FLUSH_SCRATCH` | `+0x500000` | **`+0x600000`** | 冲刷区位置变了 |
| 显示列表 | `display_list_design.md` 规划；开发记录未提 DDR 位置 | **已实现**：几何表 `+0x800000`、列表 0/1 `+0x820000`/`+0x840000`，寄存器 0x4C~0x88 | 新 demo 若要建列表必须避开这三段 |
| 翻页（buffer flip） | 开发记录 §13 明确"**尚未实施**"（基址是参数、`frame_tick` 悬空） | **v2.6/v2.7 已实现**：`FB_SEL`/`FB_STAT` + 帧边界锁存 + 格雷码 CDC + 帧中断；`fb_scanout` 有 `FB_BASE1/FB_BASE2` 参数 | 撕裂/原子呈现的做法要按新能力写，而不是按"缺能力"写 |
| 显示缓冲数量 | 双缓冲 | 三缓冲（显示 A / 画 B / 预清 C）+ 并发清屏引擎 + 硬件互斥 | — |
| 核心时钟 | HDMI 文档写 100MHz | 顶层注释 100MHz，但 FinalDemo 的 DL 看门狗口径按 **87MHz** 换算 | **量时序前必须确认当前 bitstream 的实际核频** |

> 结论：**地址、时钟、能力三件事都以 v3.2 源码为准**（`FinalDemo.c` / `ddr3_example_top.v` / `fb_scanout.v` /
> `soc.h` / 当前 linker），三份文档用于理解**为什么这样设计**与**踩过哪些坑**。
