## 1. 与赛题要求的对应关系

赛题【高阶挑战 3】原文：

> 在 RISC-V 上运行一个具有极高同屏元素数量的游戏 Demo（如《吸血鬼幸存者》的简化版或类似
> 《东方 Project》的弹幕射击游戏）。在开启硬件加速（Alpha 混合 + Color Keying）的情况下，
> 挑战保持 **60 FPS** 稳定运行时的同屏活动元素（Sprite）数量极限。

| 赛题要求 | 本 Demo 怎么做 | 在哪里能看见 |
| --- | --- | --- |
| 极高同屏元素数量 | 同屏 = 敌弹 + 自机弹 + 敌机 + 自机 + 爆点火花 + 星空，**全部是引擎下的 sprite 指令**；N 上限可设到 2400 | 屏上 `ON=` 字段 / `ST` 行 / `d` 诊断行 |
| Alpha 混合 | 敌弹/自机弹/火花走 **加算混合**（`ATTR_PORT` `blend=ADD`），每颗弹的 `global_alpha` 就是发光强度（爆点靠它淡出） | 弹幕的辉光；`A` 标记 = 属性侧口在用 |
| Color Keying | 图集统一用 **0x0000（纯黑）** 作键色（`OP=KEY` + `w7=0`），自机/敌机是硬边抠图 | 机体的不规则边缘 |
| 60 FPS 稳定 | 三缓冲 FLIP + 并发清屏引擎（**不做整屏 COPY**），上屏锁在扫描输出的场边界上 | 屏上 `HW=` / `FPS` |
| 同屏数量**极限** | 串口按 `g` 打开自动爬坡：逐秒抬 N 直到帧率跌破 58，把结论打一行 `LIMIT N=… fps=… ON=…` | 串口 + 上位机记分板 |
| 同屏数量极限 **× 三种算子** | `5/6/7/8`（或 `f` 循环）切换**敌弹显示模式** FILL / ALPHA / ADD / KEY，四档各跑一次 `g`，比较各自能顶住的同屏数量 | 屏上 `OP=` 字段 + 记分板 + `LIMIT` 行（见 §6.3） |
| 与纯 CPU 对比 | 按 `c` 切到**纯 CPU 渲染**同场景（逐像素 16bit 读改写，诚实分母），按 `h` 切回；`HW=` 与 `SW=` **两个数都留在屏幕上** | 屏上 `HW= / SW=` |
| 不用板卡按键 | 输入全部走 USB-UART（115200 8N1），PC 键盘 → `@HH\n` 按键包 | 见第 4 节 |

## 2. 一页速览

### 2.1 上板（详细步骤见第 10 节）

```
1. Efinity Programmer 烧 firmware\v3.2\GameDemo_v3.2_soc.hex（SPI Active）→ 断电重上电
2. 浏览器打开 tools\game_console.html（双击即可，file:// 属安全上下文）
3. 点「连接」→ 选板子的串口（115200 8N1）
4. 点一下页面取得焦点 → 用键盘玩
```

### 2.2 键位

| 计算机按键 | 位 | 作用 |
| --- | --- | --- |
| `W` / `↑` | bit0 | 上 |
| `S` / `↓` | bit1 | 下 |
| `A` / `←` | bit2 | 左 |
| `D` / `→` | bit3 | 右 |
| `J` / `空格` | bit4 | 开火（标题页/结束页按它开始或重开） |
| `K` / `Shift` | bit5 | 慢速（精确走位，速度减半） |
| `L` / `X` | bit6 | 炸弹（清光敌弹，**上升沿**触发一次） |
| `P` / `回车` | bit7 | 暂停 / 继续（上升沿） |

### 2.3 固件命令（单字符，按下即生效，不需要回车）

| 键 | 作用 |
| --- | --- |
| **`5` `6` `7` `8`** | **敌弹显示模式直选：FILL / ALPHA / ADD / KEY**（见 §6.3） |
| **`f`** | **敌弹显示模式循环：FILL → ALPHA → ADD → KEY → FILL** |
| `1` `2` `3` `4` | 预设负载档：N = 256 / 640 / 1280 / 2400 |
| `n` 或 `+` / `-` | N ± 64（越界回绕） |
| `=` + 数字 + `\n` | 精确设置 N（行命令，钳到 64–2400，回 `EV N=…`） |
| `c` / `h` | 渲染路径：纯 CPU / 硬件加速（来回切就是实时对比） |
| `g` | **自动爬坡**：逐秒抬 N 直到掉帧，给出 `LIMIT` 一行 |
| `b` | 星空背景开关 |
| `p` | 暂停 / 继续 |
| `r` | 重开一局（换种子） |
| `d` | 打一行诊断（引擎寄存器现场 + 四档容量） |
| `?` | 帮助 |

### 2.4 屏幕上的信息条

```
HW=60 SW=7 N=1280 ON=1341 SC=20481 LV=3 HP=2 OP=ADD S G                      HW ACCEL
└─ 左：数字与标记 ────────────────────────────────────────────────────┘   └─ 右：渲染路径 ─┘
```

| 字段 | 含义 |
| --- | --- |
| `HW=` | **硬件加速路径**最近一次 1Hz 窗口实测的帧率 |
| `SW=` | **纯 CPU 渲染**最近一次实测的帧率（切过去跑一秒再切回来就有数） |
| `N=` | 敌弹同屏上限（串口可调） |
| `ON=` | **本帧真正下发的 sprite 总数**（含星空装饰） |
| `SC=` / `LV=` / `HP=` | 分数 / 关卡 / 剩余生命 |
| **`OP=`** | **敌弹实际生效的算子档**：`FILL` / `ALPHA` / `ADD` / `KEY`。★ 报的是**生效值**：ADD 档在没有属性侧口时会显示 `KEY`（固件降级了，HUD 不许说谎） |
| `S` / `G` | 标记：星空开 / 自动爬坡开 |
| 右侧 | `HW ACCEL` 或 `PURE CPU` |

> 最坏串 `"HW=999 SW=999 N=2400 ON=9999 SC=999999 LV=99 HP=9 OP=ALPHA S G"` = **62 字符 = 496px**，
> 黑底按 64 字符 = 512px 铺 ⇒ 塞得下；右标签最左 896px ⇒ 仍空 400px。开机自检会真的量一遍。

## 3. 渲染架构：为什么能顶住几千个精灵

```
        RISC-V（100MHz core）                          FPGA 2D 引擎（BLT_BASE = 0xF8100000）
 ┌──────────────────────────────┐              ┌───────────────────────────────────────────┐
 │ 游戏逻辑（碰撞/生成/AI）      │              │  cmd_fifo（256 条，每条约 8 字）           │
 │   ↓ 只算不画                 │  8 字/命令   │      ↓                                     │
 │ build_draw_list()            │ ───────────► │  blt_engine_fsm → pixel_path（双 lane）    │
 │   一条 draw_t = 一个 sprite  │  ATTR_PORT   │      ↓                                     │
 │   ↓（按 FIFO 余量分块下发）  │  1 字/命令   │  axi_wr_master → DDR3（帧缓冲）            │
 └──────────────────────────────┘              └───────────────────────────────────────────┘
        ↑ 串口 4Hz ST 行 / EV/LIMIT                       ↓
        │                                        fb_scanout（1920B/行）→ HDMI 1080p @60.1Hz
   上位机 game_console.html                                 ↓
        ↑ PC 键盘 '@HH\n'  （**板载按键一个都不用**）   屏幕
```

### 3.1 上屏方式：三缓冲 FLIP，不做整屏 COPY

| 方案 | 每帧代价 | 结果 |
| --- | --- | --- |
| 整屏 COPY（老 FinalDemo 的默认路径） | 960×540 RGB565 整帧搬运 ≈ **1.89M 核拍 ≈ 19ms** | 19ms > 16.7ms 场周期 ⇒ **上限被钉死在 ~53fps**，与画多画少无关 |
| **三缓冲 FLIP（本 Demo）** | 写 1 个寄存器 + 等一个场边界，**一次 DDR 搬运都不做** | 硬件先扫完的那 19ms 全部变成内容预算 |

三块缓冲轮转：**显示 A / 画 B / 预清 C**。
`FB_SEL(0x24)` 只是"请求"，扫描输出在**下一个帧边界**才锁存；`FB_STAT(0x28)[1:0]` 是"已生效"。
固件等 `FB_STAT == 请求值` 才认为"这一帧真的上屏了"，**有界超时（100ms）后重发请求，
绝不往可能正在上屏的缓冲里画**。

### 3.2 背景重铺：交给并发的清屏引擎

弹幕游戏每帧都要把整片背景清掉重画。硬件的**并发清屏引擎**（`0x2C~0x48`）在后台把
"下一块缓冲"的游戏区铺成背景色，**不进关键路径**；`CLR_STAT[5:2]` 是四块缓冲的 clean 位图。

| 情形 | 固件行为 |
| --- | --- |
| 目标缓冲 clean | 本帧**不发**任何整片重铺指令 |
| 目标缓冲不干净（清屏超时/被互斥拒绝） | 退回**命令式整片 FILL**（960×524），语义与老版本逐位相同，宁可多花拍也绝不在脏底上作画 |
| 清屏目标 == 正在显示 / 正在画的缓冲 | **硬件直接拒写并置 ERR**（互斥是硬件保证，不依赖软件正确性） |

> 主机仿真里每 7 个场强制报一次"不干净"，把这条退化路径也真的跑到了：
> `d` 诊断行里 `clr fb=67` ≈ 600 帧中的 11%，画面照常。

### 3.3 为什么走"逐条下发"而不是显示列表（DL）

| 理由 | 说明 |
| --- | --- |
| **属性字没有 DL 槽位** | v3.2 的 `ATTR_PORT(0x8C)` 只有"每条命令配一个"这一种配对方式；DL 的 16B 描述符四个字全占满，**装不下混合模式 / global_alpha** ⇒ 要"每颗弹不同亮度"就只能逐条。 |
| 板级记录里 DL 在 ALPHA/KEY 场景不可靠 | `doc/开发问题与解决记录.md` / `rtl/功能清单.md` §25：ALPHA/KEY 的描述符取指被 DDR 争用饿过 `DL_TIMEOUT`（`stall_seen=1`），固件最多重试一次就退回逐条。 |

### 3.4 逐条下发的成本去哪了

一条命令的固定开销（写 8 个 FIFO 字 + 写 1 个属性字）在 N=2400 时是 24000 次 APB 写/帧。
固件用**每圈最多 64 条**的分块下发 + "先读一次 `CMD_FIFO_COUNT` 再在圈内自己记账"的办法摊平，
并且**FIFO 满时绝不写 `0x08`**（写了会把 CPU 挂在 AXI-Lite 上，这是老版本的坑）。

## 4. 输入通路：PC 键盘 → 串口（**不用板卡按键**）

### 4.1 协议

```
PC → 板：  '@' + 两位十六进制 + '\n'          例："@18" = 右 + 开火
            bit0 上  1 下  2 左  3 右  4 开火  5 慢速  6 炸弹  7 暂停

PC → 板：  单字符命令
            5/6/7/8   敌弹显示模式 FILL/ALPHA/ADD/KEY
            f         敌弹显示模式循环
            1/2/3/4   负载预设   n + - =N 调 N
            c/h 渲染路径   g 自动爬坡   b/p/r/d/?

板 → PC：  上电横幅
           EV ...    命令回显（EV N=1280 / EV path=HW accel / EV hit hp=2 /
                                EV bulm=FILL (requested; effective=FILL) / EV bomb left=2 …）
           ST ...    4Hz 记分板（fps/n/on/sc/lv/hp/bm/md/**OP**）
           LIMIT ... 自动爬坡结论（N/fps/ON/path）
```

### 4.2 三条设计决定（都是为了"不会卡住自机"）

| 决定 | 为什么 |
| --- | --- |
| **整包替换语义**：每个包携带**完整**的 8 位按键位图，不是增量 | 丢一个包最多让状态晚 100ms 生效，**永远不会"卡住某个方向键"** |
| **100ms 心跳**：上位机每 100ms 补发一包（4 字节 = 40 B/s） | 顺带把固件的看门狗喂饱；4 字节/包在 115200 上只有 ~0.35ms 的串口时间 |
| **500ms 看门狗**：固件收不到包就把所有键视为松开 | 浏览器标签被切走、拔线、上位机崩了 —— 自机都不会一直往一个方向飞 |

### 4.3 输入延迟

固件把串口轮询放在**每 4 圈一次**（不是 FinalDemo 的"每 32 圈慢时间片"）：
主循环一圈 ≈ 一两百拍 ⇒ 轮询间隔 ≈ 几十 µs，比一个 16.7ms 的帧快两个数量级。
`serial_drain()` 一次最多吃掉 64 字节，所以突发来的整包也不会堵住主循环。

### 4.4 与既有命令协议不打架

`@` 包、`=N` 行、单字符命令是**三套互斥的语法**，分派顺序固定：

```
kp_feed(c)   → KP_OK      ⇒ 按键包结算（消费掉）
             → KP_MORE/ERR ⇒ 本函数已消费，不再往下走
             → KP_NONE     ⇒ 原样交给 nline_feed
nline_feed(c)→ NL_OK/ERR  ⇒ 行命令结算（消费掉）
             → NL_MORE     ⇒ 已消费
             → NL_NONE     ⇒ 原样交给 serial_cmd（单字符命令）
```

主机自检里有一条**穷举**用例：长度 1–4、字母表 `{'@','0','F','\n','g','='}` 的全部
**2058 种组合**，判据是"只有 `@HH\n` 这一种形态能返回 KP_OK"，外加一条
"所有单字符命令都必须返回 KP_NONE" —— 把两套协议互相吞噬的可能性钉死。

## 5. 图集与「黑 = 透明」这个统一约定

所有精灵都是**程序化生成**的 RGB565（没有外部素材），透明处一律写 `0x0000`。
于是**一张图集同时服务两条路径**，不需要按位流能力准备两套素材：

| 位流 | 辉光弹怎么画 | 屏幕效果 |
| --- | --- | --- |
| **有 v3.2 属性侧口** | `OP=ALPHA` + `attr(blend=ADD, fmt=565)`，`w6=255`，`global_alpha=ga` | 加算数学 `out = min(255, ⌊fg·A/255⌋ + bg)`：**黑像素加 0 = 背景不变（天然透明）**，彩色像素把光加上去 ⇒ 真辉光；`ga` 就是发光强度（爆点靠它淡出） |
| **没有属性侧口**（老位流） | `OP=KEY` + `w7=0x0000` | 黑像素被硬件比较器整像素丢弃 ⇒ **硬边精灵，观感降级但画面完全正确** |

> 所以"位流有没有 v3.2 属性侧口"**只影响好不好看，不影响能不能跑**。
> 探测方式与 AdDemo 一致：`ATTR_PORT` 只写不可读，就用同批出现的
> `CLIP_X0..Y1` / `LUT_CTRL` 写回读来判定（`feat_probe()`）。

**加算混合是可交换的** ⇒ 辉光弹之间**没有 z 序问题**，画的先后不影响结果。
这一点在弹幕游戏里很值钱：几百颗弹互相重叠时不需要任何排序。

### 5.1 图集布局（编译期常量，主机自检验算过）

| 精灵号 | 名字 | 尺寸 | 图集内偏移 | 用途 |
| --- | --- | --- | --- | --- |
| 0 | `S_PR` | 32×32 | 0 | 自机（三角机体，青座舱/白机身/暗机翼） |
| 1 | `S_EN` | 32×32 | 2048 | 敌机（菱形，红外壳/琥珀/白芯） |
| 2 | `S_SH` | 16×16 | 4096 | 自机弹（青色辉光） |
| 3–6 | `S_B0..S_B3` | 16×16 | 4608/5120/5632/6144 | 敌弹四档配色（品红/青/琥珀/绿） |
| 7 | `S_SP` | 16×16 | 6656 | 爆点火花（白色辉光，靠 `ga` 淡出） |

合计 **7168 字节**，放在 `ATLAS_BASE = DDR_BASE + 0x200000`（离 `FLUSH_SCRATCH` 十万八千里）。

### 5.2 裁剪是硬要求，不是美化

> **改这段代码前必读**：弹幕会飞出游戏区，而目的地址算的是 `FB + y*FB_STRIDE + x*2`。
> `int16` 的负数一旦被转成 `uint32` 参与乘加，就会写到帧缓冲之外 —— 那是
> "画面花掉 + 别的缓冲区被踩"级别的事故。
> 所以**每一条精灵在进绘制清单之前**都先按游戏区裁成矩形，并记下源偏移 `(sx,sy)`；
> 完全在区外的条目直接丢弃（`g_clip_drop` 计数）。
> 顺带把屏幕骨架也保护住了：`y` 一律裁到 `PLAY_Y0=16` 以下，弹幕永远不会糊到信息条上。

主机自检的 D 组每一帧都遍历整张绘制清单，断言
`x≥0 && y≥PLAY_Y0 && x+w≤960 && y+h≤540 && w,h>0` —— 600 帧 × 最多 2584 条，**0 次越界**。

## 6. 游戏设计

| 项 | 做法 |
| --- | --- |
| 状态机 | `GS_TITLE` → `GS_PLAY` ⇄ `GS_PAUSE` → `GS_OVER` →（按开火）回到 `GS_PLAY` |
| 自机 | 1/8 像素定点（Q3）位置，正常 5 px/帧、慢速 2.5 px/帧；判定半径 4px（弹幕礼仪：判定比看起来小） |
| 自机弹 | 按住开火每 7 帧一对，速度 7 px/帧；**专用 32 个槽位**，永远不被敌弹挤掉 |
| 敌机 | 最多 24 架，三种弹幕：**环弹** / **瞄准扇**（朝自机方向扇开）/ **双螺旋**；缓慢下压后悬停开火 |
| 敌弹 | 16×16 辉光，径向平方衰减；寿命 240 帧或飞出区外即回收 |
| 生命 / 炸弹 | 3 命；中弹后 100 帧无敌 + 消掉命中弹；炸弹清光全场敌弹并给敌机 3 点伤害 |
| 关卡 | 每 1800 帧（30s）升一级：环弹变多、弹速变快 |
| 分数 | 击杀 100×关卡，存活每 10 帧 +1（上限 999999） |
| 星空 | 64 颗 2×2 FILL，三档下落速度，`b` 可关（关掉能少 64 个元素，方便对齐口径） |

### 6.1 生成器必须跟得上 N（这条踩过坑）

主机仿真第一次跑出来的结论是：把 N 从 256 跳到 2400 之后，**同屏元素数只到 345**。
根因不是引擎，是**生成器**：老逻辑"每个生成节拍只补一架敌机"，铺满 27 架要 7 秒，
再等它们把弹幕铺开又要好几秒 —— 用户按 `4` 之后要等半分钟才看见密集弹幕，
第一反应必然是"这加速器带不动"。

现在改成：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `ENEMY_MAX` | 24 | **同屏弹幕能不能被喂到 N 的天花板**：24 × 22 × 240 / 46 ≈ 2750 > N_MAX |
| `ENEMY_SPAWN_T` | 16 帧 | 生成节拍 |
| `ENEMY_TOPUP` | 4 架/拍 | 每拍**补到 want**，N 一跳就快速跟上 |
| `want` | `2 + N/80`（钳到 24） | 敌机数随 N 增长 |
| 环弹发数 | `8 + level·2 + N/192`（钳到 24） | 环的粗细也随 N 增长 |

改完之后同一次仿真里 `ON_max = 784`（N=2400，10 秒虚拟时间）。
主机自检里那条 `D8 高负载：同屏元素数 > 600` 就是为了把这个坑钉住。

### 6.2 弹池与"池满"的 O(1) 快路径

`bul_alloc_enemy()` 有一条 `if (g_bul_live >= g_ncap) return -1;` 的快路径。
没有它的话，池满时**每一次发射**都要把 2400 个槽线性扫一遍；
一帧里最多有"敌机数 × 环弹数"= 24×24 = 576 次发射 ⇒ 最坏 138 万次循环 ≈ 3~4M 拍，
**比一帧预算（1.67M 拍）还长** —— 表现就是"弹幕铺满的一瞬间掉帧"。
`g_bul_live` 每帧在子弹循环里重算一次（那里本来就要遍历），帧内靠 `++` 记账；
子弹在别处被回收时计数会暂时偏大 —— 那只会让判断更保守，不会漏发。

### 6.3 ★ 敌弹显示模式：FILL / ALPHA / ADD / KEY（`5/6/7/8` 直选、`f` 循环）

**只作用于敌机放出的那些弹**（同屏元素的主体）。自机弹与火花固定用加算辉光，
所以切档时**只有弹幕这一种元素的画法在变** —— 观感与帧率的差别一眼就能对上号。

| 档 | 引擎算子 | 观感 | 16×16 @70% 帧预算容量（单 lane 板测口径） |
| --- | --- | --- | --- |
| **FILL** | `op=1` | 纯色方块。**没有源、没有键色、没有 alpha** —— 会盖住底下的东西 | **2269 颗/帧** |
| **ALPHA** | `op=2` + 命令字 `α=160` | 经典半透明 `out=(fg·α+bg·(255−α)+127)>>8` | **1362 颗/帧** |
| **ADD** | `op=2` + 属性字 `blend=ADD` | 加算辉光（默认档，观感最好） | 1362 颗/帧（同 ALPHA 的像素通路） |
| **KEY** | `op=3`，色键 `0x0000` | 硬边抠图 | **1622 颗/帧** |

#### 三条值得写下来的细节

**① ALPHA 档"每颗弹外面套一个暗方块"是正确行为，不是 bug。**
图集是**矩形**的，圆盘四角是纯黑（`0x0000`）。经典半透明的式子是
`out = fg·α + bg·(1−α)`，黑像素参与混合就是把背景压暗 —— 方框范围内背景变暗，
所以看起来像套了一个暗方块。**这恰好是 Color Key 存在的理由**：切到 KEY 档，
四角的黑像素被硬件比较器整像素丢弃，方块感立刻消失。
把这条写进文档而不是"想办法抹掉它"，是因为它正是赛题要展示的"三种算子的差别"。

**② ALPHA 档故意走 `blend=0` + 命令字 alpha 的老路径，不碰属性侧口。**
v3.2 的 attr `blend=ALPHA` 走的是 `A = ⌊w6·ga/255⌋`，取 `w6=255` 时 `A == ga`，
与老路径**数学完全等价**。老路径在 v2.x 就上过板、逐位可复现 ⇒
没必要为了"用上新寄存器"去多担一份未上板的风险。
（想验证属性侧口的话，切到 ADD 档就是在用它。）

**③ `ADD` 档没有属性侧口时会**静默降级**成 KEY —— 所以 HUD 报的是"生效档"而不是"请求档"。**
`bulm_eff_name()` 是唯一的判定点：`if (g_bulm == BULM_ADD && !g_glow) return "KEY";`
串口回包也同时给两个值：`EV bulm=FILL (requested; effective=FILL)`。
主机自检的 E3 用例就是钉这一条的（把 `g_glow` 强行置 0，断言 `bulm_eff_name()` 返回 `"KEY"`）。

#### 怎么用这一档量极限

```
1. 按 4 把 N 拉到 2400（或直接 =2400）
2. 按 g 打开自动爬坡，等 LIMIT 行
3. 换一档（5/6/7/8 或 f），重复
4. 比较四次的 LIMIT N=… 与屏上 OP=、ON=
```

同一份弹幕在 FILL 档能顶住的同屏数量明显高于 ALPHA 档（容量 2269 vs 1362，约 1.67×），
**这就是"算子选择"对 60FPS 极限的直接影响** —— 也是本档位设计出来要回答的问题。

> 四档都是**同一条下发路径**（逐条命令 + 每条恰好一个属性字），
> 差别只在 `blt_emit()` 的参数上：`e_fill()` / `e_alpha()` / `e_glow()` / `e_key()`。
> 属性配对纪律由 `blt_emit()` 这个唯一出口保证，切档不会破坏它。

## 7. 60FPS 极限怎么量（这是赛题的核心问题）

### 7.1 自动爬坡（串口 `g`）

```
每秒判一次（与 1Hz 帧率窗口同一个节拍）：
    测得帧率 ≥ 58 ⇒ N 抬高一档（+max(64, N/8)），继续
    测得帧率 <  58 ⇒ 回退一档、打印 LIMIT、关掉自动爬坡
```

因为上屏是**垂直同步锁定**的，帧率只会是 60 / 30 / 20… 的台阶，
所以判据用 58 而不是 45。爬坡停下来时串口会打一行：

```
LIMIT N=1152 fps=59 ON=1203 path=HW ACCEL (max stable at 60fps)
```

这一行 + 屏幕上的 `N=` / `ON=` 就是赛题要的"极限"结论，**可复现、不用人工试**。

### 7.2 容量模型（固件里就带，`d` 命令随时可读）

板级实测（v2.16 口径，逐条下发、单 lane）拟合出来的是 `每块 = A + B×px`：

| 算子 | A（拍） | B（拍/像素 ×1000） |
| --- | --- | --- |
| FILL | 252 | 1025 |
| KEY | 398 | 1255 |
| ALPHA | 464 | 1533 |

固件里的 `cyc_of()` 就是这个式子（整数定点 ×1000）。它**逐拍复现了三个板测点**：

| 尺寸 | 模型 | 板测 | 差 |
| --- | --- | --- | --- |
| 16×16 FILL | **514** | 514.3 | 0.06% |
| 16×16 KEY | **719** | 719.1 | 0.01% |
| 16×16 ALPHA | **856** | 856.4 | 0.05% |
| 32×32 ALPHA | 2033 | 1969.0 | +3.3%（拟合残差，文档已记 −2.9%~−3.9%） |
| 64×64 ALPHA | **6743** | 6742.7 | 0.00% |

⇒ 60fps 帧预算 1,666,667 拍，按 **70% 预算**算，16×16 辉光弹的容量：

| 口径 | 精灵/帧 |
| --- | --- |
| 单 lane（板测 v2.16 口径，**已上板证实**） | **1362** |
| 双 lane（v3.1 的 2px/拍，**只到仿真**，1.5~1.8× 外推） | 1767 |

**这两个数是"预期量级"，不是保证**：v3.1/v3.2 的双 lane / 属性侧口只到仿真、没上板，
真板上限必须用 `g` 自动爬坡自己量。`d` 诊断行会把这两个数打出来，方便和实测对。

### 7.3 与纯 CPU 的对比

按 `c` 切到纯 CPU 路径：**同一个场景、同一份精灵图集**，由 CPU 逐像素做
16bit 读改写（`cpu_blit()`，加算用 `add565()`，与 RTL 的 `blend=ADD` 同式），
外加整屏 `cpu_fill32` 铺底。不做任何批量化 —— 这是"诚实分母"。

对比结果两个数**都留在屏幕上**（`HW=` 和 `SW=`），按 `c` / `h` 来回切就能做实时对比，
不需要另开一个 demo。切路径时 1Hz 窗口会**重置**，避免读到"半个窗口"的假帧率。

## 8. 主机自检：怎么在没有板子的情况下证明它能跑

本工作区没有板子，所以验证分三层，全部可复现：

### 8.1 第一层：全固件仿真（**最强的一条**）

`tools/host_selfcheck_game/` 把 `GameDemo.c` **原样 `#include`** 进一个仿真宿主，
只覆盖三个**基址**（`DDR_BASE` / `BLT_BASE` / `UART_TERM`），用一块 RAM 假装是 DDR 和
引擎寄存器，然后在 QEMU（`qemu-system-riscv32`，Efinity IDE 自带）上把**真·主循环**跑起来。

| 做了什么 | 怎么做到 |
| --- | --- |
| 假引擎 | `STATUS` 恒为 `DONE\|FIFO_EMPTY`，`CMD_FIFO_COUNT` 恒 0 ⇒ 命令发出去就被"消费" |
| 假时钟 | `clint_getTimeLow()` 每次调用推进 4096 拍（`sim_tick()`），它就是整个仿真的心跳 |
| 假场边界 | 每 1,666,667 拍更新一次 `FB_STAT = FB_SEL` ⇒ **FLIP 的确认条件是真的被满足的** |
| 假清屏引擎 | 每 7 个场强制报一次"不干净"，让命令式整片重铺那条退化路径也跑到 |
| 输入 | 走固件自己的 `kp_feed()` + `serial_apply_key()` + `serial_cmd()`（不是测试里另抄一份） |
| 收尾 | 跑满 600 个上屏帧后写 QEMU 的 SiFive test 设备自杀退出（不用超时） |

**结论：74 项 0 失败**，覆盖 A 属性字/定点混合/帧预算模型/信息条宽度、B 串口协议、
C 游戏逻辑（含 1800 帧长跑）、**E 敌弹显示模式（四档映射 / 循环 / 生效档名 / 清单算子）**、
D 主循环仿真（600 帧，四档敌弹都真的被渲染过）。
原始日志：`doc/logs/host_selfcheck_GameDemo.txt`。

> ★ **如实记录的三条口径差别**（不要当成通过）：
> 1. 假引擎"瞬时完成" ⇒ 仿真里的帧率恒为 60，**不能**用来测吞吐/极限 N；
> 2. 帧边界中断在仿真里是电平恒高（没法模仿 W1C 的读副作用）⇒
>    FLIP 的确认仍被 `FB_STAT` 卡在真正的场边界上（帧率口径不受影响），
>    但 `EV flip timeout` 那条有界超时分支在仿真里走不到；
> 3. UART 的 RX 在仿真里恒为空（MMIO 读没法挂副作用）⇒ `serial_drain()` 的
>    "无数据"路径被走到，**解析本身**由 B 组直接喂满。

### 8.2 第二层：上位机协议自检（Node，不需要浏览器/串口）

`node tools/game_console_selftest.js` 把 `game_console.html` 里
`==== PROTO_BEGIN/END ====` 之间的**纯函数**原样抽出来在 Node 里跑。

**结论：基础版 34 项 0 失败；增强版 53 项 0 失败**
（`node tools/game_console_selftest.js` 与 `node tools/game_console_selftest.js tools/game_console1.html`）。
其中两批是跨端一致性守门人：
- 256 个按键包全部满足**固件 `kp_feed` 的语法**（参考实现）并解出同一位图；
- 从 `GameDemo.c` 里现读 `#define N_MIN/N_MAX`、`KEY_*` 位定义、`BULM_*` 枚举、
  `g_bulm_name[]` 档名与 `serial_cmd()` 的 `case`，与页面用的常量逐项对账
  ⇒ 以后任何一端改了常量、另一端没跟上，这里会当场红。

原始日志：`doc/logs/game_console_selftest.txt`。

## 9. 一帧的完整时间线（改代码前先读这个）

```
        ┌─ 帧边界（扫描输出锁存 FB_SEL → FB_STAT 变成我们请求的那块）─────────────┐
        │  back_busy = 0                                                          │
        │  rotate: disp = flip_req; draw = clr; clr = old_disp                    │
        │  g_fb_back = fb_of_sel(draw)                                            │
        │  hw_frames / sw_frames++（这就是"已上屏帧"的口径）                       │
        └────────────────────────────────────────────────────────────────────────┘
                                    ↓ 下一个主循环圈
        ┌─ !frame_started：开新的一帧 ───────────────────────────────────────────┐
        │  1) game_tick()          ← 推进一帧游戏逻辑（纯 CPU，不碰总线）         │
        │  2) hw_pass_arm()        ← 等清屏空闲 → 读 clean 位 → 写 DRAW_SEL       │
        │                            → 需要就补命令式整片重铺 → 给第三块下清屏    │
        │  3) build_draw_list()    ← 组清单（含**裁剪**），g_on_screen = 条数     │
        │  4) osd_build()+osd_blit() ← 只重画 y<16 的信息条（渲染区之外）         │
        └────────────────────────────────────────────────────────────────────────┘
                                    ↓
        ┌─ 分块把清单推进 FIFO（每圈 ≤64 条，FIFO 满就纯 ALU 退避）─────────────┐
        └────────────────────────────────────────────────────────────────────────┘
                                    ↓
        ┌─ wait_engine_idle()（有界 10ms；超时走 blt_recover）───────────────────┐
        │  overlay_draw()          ← 中央字幕必须**等引擎画完**再写，且每帧重画   │
        │  cache_evict()           ← store 有序屏障，保证 CPU 像素对引擎可见      │
        │  blt_wr(FB_SEL, draw)    ← 只是"请求"，等下一个场边界生效               │
        └────────────────────────────────────────────────────────────────────────┘
```

纯 CPU 路径（`c`）只在中间那两段不同：不推命令，改成 `cpu_render_frame()` 整帧自己画。

### 10.3 极限 N 怎么记录（赛题要的结论）

```
1. 起始 N=256，按 g 打开自动爬坡，等它自己停；
2. 抄下 LIMIT 行的 N / fps / ON 三个数；
3. 按 d 抄下四档容量那一行；
4. ★ 换一档（5/6/7/8 或 f），重复 1~3 —— 四档各留一组数；
5. 把这几组数和你实际的位流版本（v3.2 / 旧位流有无 attr）一起记进
   doc/logs/board_gamedemo_limit_*.txt（格式见该目录既有文件）。
```

> **四档都要跑**，因为这是赛题"三种算子"最直接的量化对比：同一份弹幕下
> `FILL` 能顶住的同屏数量应当明显高于 `ALPHA`（理论容量 2269 vs 1362）。
> 实测值和理论值对不上时，先看 `d` 里的 `stto`/`err` 是不是涨了。

## 11. 已知限制 / 未验证项（如实列出）

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | **增强版未上板** | 基础版已由用户实测跑通；**敌弹显示模式（`5/6/7/8`/`f`）这一版还没上板**。四档的算子映射、循环、生效档名、绘制清单都有主机自检覆盖（E 组 7 项 + D 组"四档都渲染过"），但没有真板观感确认。 |
| 2 | 双 lane 容量是外推 | v3.1 的 2px/拍只有仿真数据（1.5~1.8×），`dual-lane` 那几个数是乐观估计；实测以 `g` 为准。 |
| 3 | 属性侧口只有仿真 | v3.2 的 `ATTR_PORT` 未上板（RTL 文档 §28.7 自己写明）。若板上属性侧口不生效，`ADD` 档会**自动降级成 KEY**（`OP=` 会显示 KEY），**不会跑不起来**。 |
| 4 | `d` 里的容量是**模型值** | 由板测拟合式 `每块 = A + B×px` 算出来，不是这颗位流的实测。16×16 三档与板测点差 <0.1%，但 32×32 有 +3.3% 拟合残差（文档已记）。 |
| 5 | 显示列表路径没走 | 见 §3.3。属性字没有 DL 槽位，而且板级记录里 DL 在 ALPHA/KEY 场景会被饿过看门狗。 |
| 6 | 假引擎不能测吞吐 | 仿真里帧率恒 60（见 §8.1 口径 1）。仿真验的是**状态机与安全性**，不是性能。 |
| 7 | 帧边界中断在仿真里是电平 | `EV flip timeout` 那条有界超时分支在仿真里走不到（真板上会走到）。 |
| 8 | UART RX 在仿真里恒空 | 解析本身由 B 组的 2058 条穷举用例覆盖。 |
| 9 | 64×64 档的测量粒度差 | 板级文档记录 64×64 档粒度退化到 ±7%~±11%，本 Demo 只用 16×16 精灵，不受影响。 |
| 10 | 编译噪声 | BSP 头（`semihosting.h` 的 `/*` within comment、`print.h` 的 `digi` 未用、`clint.h`/`uart.h` 的静态函数未用）在 `-Wall -Wextra` 下会刷屏，**属于既有 BSP 的预期噪声**；本 Demo 自己的源码 0 警告。 |
| 11 | `.ps1` 只写 ASCII | Windows PowerShell 5.1 会把无 BOM 的 `.ps1` 按 ANSI 读，中文会被解坏（本轮又踩了一次：`build_gamedemo.ps1` 里加了一句中文注释 → 解析报 `Unexpected token '}'`）。所以 `.ps1` 全 ASCII，中文说明放 `.md`；`tools/*.ps1` 现在有"非 ASCII 字节 = 0"的检查。 |
