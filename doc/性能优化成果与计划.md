## 1. 本批成果总览

### 1.1 一句话

**本批把"每像素 1 拍"这条像素通路地板之外的固定开销与读流量都往下压了一档**
（整屏 FILL −11.07%、AW 事务 −93.7%、32×32 命令尾 −33 拍、典型弹幕弹 KEY −21.4%），
并第一次把"列表路径到底赚不赚"变成了板上一行可读的数字；
但**像素通路本身仍是 1 像素/拍 —— 这一条没被动过，它才是当前唯一的墙**。

## 2. 测量方法与工具（本批最值钱的部分）

> 这一节比任何单项优化都重要：本批至少有 4 条结论是被这套工具**推翻**的（见 §5）。

### 2.1 1 Hz 成本行：把"感觉快了"换成"每秒一行数"

固件在两个路径上各打一行**同口径**的成本（`FinalDemo.c` 的 `dl_cost_report()` / `cmd_cost_report()`，
提交 `725134c`）：

```
EV cmd path done: n=<精灵数> cycles=<软件秒表> cyc/sprite=<cycles/n>
EV dl  list done: n=<精灵数> cycles=<DL_PERF>  cyc/sprite=<cycles/n>
```

| 要点 | 内容 |
| --- | --- |
| 门控 | 都是 **1 Hz 门控**（`DL_COST_TICKS = BSP_CLINT_HZ`）：不是每帧、更不是每条，串口不会被刷屏 |
| 单位 | 都是 **core 拍**。`DL_PERF(0x7C)` 由取指器在 core 域计数；逐条路径的秒表是 CLINT `mtime` 低 32 位，CLINT 就在 core_clk 域（`SYSTEM_CLINT_HZ=100000000`，`pt.sdc: create_clock -period 10.000 -name core_clk`） |
| 口径差（**必须知道**） | 列表那行是**纯硬件**（GO→done）；逐条那行是**墙钟**（含 8 次 MMIO/块的 CPU 下发）——后者正是按 `l` 想省掉的东西 |
| 已知污染 | 列表那行的 `n` 只数精灵，`cycles` 里却含同一张表里那条**整片重铺**描述符（W=960 的 FILL）⇒ 小 N 时 `cyc/sprite` 明显偏高；比大小要把 N 加大（N=976 时重铺只占 3%） |
| 为什么它值钱 | 本批**每一个**性能数字都出自这一行；它替换掉了此前几条靠"板上−仿真"反推出来的错误推断（§5 的 (a)(b)(c)） |

### 2.2 两点/三点拟合：从成本行到 `A + B × px` 模型

| 步骤 | 做法 |
| --- | --- |
| 采样 | 三种尺寸各测一趟：16×16（256 px）/ 32×32（1 024 px）/ 64×64（4 096 px） |
| 两点定参 | 用**两端点**（16×16 与 64×64）解 `A`（每精灵固定开销）与 `B`（每像素成本） |
| 三点验残差 | 中间点（32×32）不参与拟合，专门用来看模型对不对 |
| 外推 | 渐近线吞吐 = `1/B` 像素/拍（固定开销被摊薄到 0）；某尺寸的兑现率 = 实测吞吐 ÷ 渐近线 |
| 粒度 | 精灵数 N 由串口网页/命令按 **步进 25** 调（范围 25–6000）⇒ 相对不确定度 = 25/n |

### 2.3 仿真侧纪律：TB + `ifdef` A/B + 逐位一致性 + 回归清单

| 纪律 | 落地 |
| --- | --- |
| 只读探针 | `rtl/tb/tb_perf_probe.v`：不改任何 RTL/寄存器图/FSM，只做层次引用；每个用例给**逐拍直方图**，并要求 `hist_sum − PERF = 0`（不允许"其他"黑洞）；`-DPIXEL_PACK_PINGPONG_OFF` / `-DWR_MERGE_HOLD_OFF` / `-DWR_CMD_END_FLUSH_OFF` / `-DDL_OFF` / `-DMASK_SKIP_OFF` 逐字回到改前读数 |
| A/B 逃生门 | 每个行为改动都配一个 `ifdef`，**两侧都必须 PASS 且位精确读数逐字节相同**（不是"差不多"） |
| 逐位一致性 | FILL/COPY/KEY/ALPHA × 非对齐/行尾残余词：首末像素、写词数、掩码推出的写出像素数、AW/W/B 计数全部逐字节比对（`tb_blt_top` / `tb_alpha` / `tb_blt_unalign` / `tb_blt_burst`） |
| 软件↔RTL 交叉 | `tb_dl_demo`：把**固件 `dl_build()` 原样输出的描述符字节**喂进真实 RTL，比命令字 + 比像素；主机自检则在 PC 上把固件里被标记的源码段（`SPR_MASK_BEGIN/END`、`DL_ENC_BEGIN/END`、`SCENE_BOUNDS`、`DL_LAYOUT`）原样编译运行 ⇒ "被测的就是板上跑的" |
| 回归清单 | `rtl/tb/run_regress.ps1`：**35 项**（其中 `tb_wr_order_off` / `tb_scanout_flip_off` / `tb_clear_engine_off` 是**预期失败**的 A/B 对照项，必须复现旧 bug 才算对）；从 `doc\logs` 目录运行，产物不落仓库根 |
| 写序专项 | `tb_wr_order`：H1（DONE 时刻写通路彻底干净）/ H2（在飞写突发 ≤ 1）是每次改动的必过项 |

### 2.4 板级工具与人为因素

| 项 | 说明 |
| --- | --- |
| 网页串口上位机 | `tools/serial_console.html`（单文件、无外部依赖、Web Serial）：单字符命令 + `=N` 行命令，N 滑块**步进 25**；`l`（列表路径）、`k`（尺寸）、`e`（每趟整片重铺）、`1/2/3`（场景）都在这里 |
| `e` 的语义 | 本批全部读数都是在 **`e` 开**（每趟整片重铺）下取的；稳态下重铺由**清屏引擎在后台**做（`clr fb/to/err` 不涨），因此不在这趟的计时里 |
| 单变量 | 同一场景、同一 N、同一尺寸，只翻一个开关（`l` / `k` / `mask`）前后读两行 —— 这条纪律是 `l` 必须"延迟到帧边界生效"（`0abba96`）的直接原因：旧版一按 `l` 就切，列表在飞时永远切不回去，A/B 根本做不下去 |

### 2.5 口径陷阱清单（本批踩过的）

| 陷阱 | 后果 |
| --- | --- |
| 拿"纯硬件列表"和"含 CPU 的逐条墙钟"直接比大小 | 得到"列表净亏 43%"的错误结论（§5 (c)）；实际 CPU 下发**大部分与引擎重叠**，真正省下的只有 ~55 拍/精灵 |
| 用不同 N 的两行相减 | 每精灵固定开销 / 整片重铺摊薄比例不同，差值里混着 N 的差 |
| 在模式切换与回退重绘期间采样 | 那一趟里既有列表路径又有逐条路径的补画，`cycles` 不是任何一种路径的成本 |
| 把"板 − 仿真"整段当成本地归给某个模块 | 那条差里同时含 DDR 竞争、B 往返、CPU 重叠程度 —— 见 §5 (a) |
| 忘记测量粒度 | 64×64 只跑 350 个精灵、步进 25 ⇒ **±7%**；这一档的任何 3~4% 差异都落在一格之内 |

### 3.2 两点拟合与三点残差（模型推导）

单位：拍/精灵。拟合只用两端点（16×16 与 64×64），32×32 留作检验。

| 场景 | A（拍/精灵） | B（拍/px） | 32×32 预测 | 32×32 实测 | 残差 | 渐近线 `1/B` |
| --- | --- | --- | --- | --- | --- | --- |
| FILL | **252** | **1.025** | 1 301.6 | 1 263.8 | **−2.9%** | 0.976 px/拍 |
| KEY | **398** | **1.255** | 1 683.1 | 1 617.4 | **−3.9%** | 0.797 px/拍 |
| ALPHA | **464** | **1.533** | 2 033.8 | 1 969.0 | **−3.2%** | 0.652 px/拍 |

两点上残差 ≤ 0.03%（它们是拟合锚点）。三个中间点全部**低于**拟合线 2.9%~3.9%，
方向一致、幅度一致 ⇒ 说明真实的 `B` 略小、`A` 略大（32×32 的固定开销比线性外推的要小），
不是随机的测量噪声。

> 口径说明（与口述"残差 3–6%"的差别）：按仓库这组读数复算，中间点残差是 **2.9% / 3.2% / 3.9%**，
> 说"3~4%"更准。它们**落在一格测量粒度之内**：64×64 档 ±7%（n=350、步进 25），
> 32×32 档 ±2.1%（约 2 格）。也就是说这条偏差**没有被单独证明**，只是与粒度相容。

### 3.3 派生指标（模型推导 + 实测混合）

帧预算 = 100 MHz ÷ 60 = **1 666 667 拍**。

| 尺寸 | 场景 | px/拍（实测） | Mpx/s（**瞬时**口径） | Mpx/s（**帧预算归一**口径） | 一趟占帧 | 帧内非本趟拍数 |
| --- | --- | --- | --- | --- | --- | --- |
| 16×16 | FILL | 0.4978 | **49.8** | **41.9** | 84.1% | 265 177（15.9%） |
| 16×16 | ALPHA | 0.2989 | **29.9** | **26.5** | 88.6% | 189 353（11.4%） |
| 16×16 | KEY | 0.3560 | **35.6** | **31.1** | 87.4% | 210 403（12.6%） |
| 32×32 | FILL | 0.8103 | **81.0** | **73.7** | 91.0% | 150 140（9.0%） |
| 32×32 | ALPHA | 0.5201 | **52.0** | **47.6** | 91.6% | 140 706（8.4%） |
| 32×32 | KEY | 0.6331 | **63.3** | **58.4** | 92.2% | 130 142（7.8%） |
| 64×64 | FILL | 0.9204 | **92.0** | **86.0** | 93.5% | 109 151（6.5%） |
| 64×64 | ALPHA | 0.6075 | **60.7** | **55.3** | 91.0% | 149 567（9.0%） |
| 64×64 | KEY | 0.7397 | **74.0** | **67.6** | 91.4% | 143 847（8.6%） |

- **FILL 的渐近线 = 1/1.025 = 0.976 px/拍 = 97.6 Mpx/s**；64×64 实测 92.0 Mpx/s = **渐近线的 94%**。
- 整屏 960×540 FILL（无命令边界）实测 **0.9958 px/拍**（1.0043 拍/px，520 607 拍 / 518 400 px），
  直方图里 518 400/520 607 = **99.58%** 的拍在推进像素 —— 这条独立印证了"B_FILL ≈ 1.0"。

> 口径说明（与口述"FILL 吞吐 41.9 / 73.7 / 92.0"的差别）：这三个数**混用了两种口径**。
> 复算后：`41.9` 与 `73.7` = `n × px ÷ 1 666 667`（**帧预算归一**，即 16×16/32×32 的值），
> 而 `92.0` = `px ÷ 拍`（**瞬时**，64×64 的值）。按帧预算归一，64×64 应是 **86.0**，不是 92.0。
> 本文因此把两列都给出来；引用单个数字时必须说明是哪一列。

> 口径说明（与口述"非通过帧开销 110–150k 拍 = 7–9%"的差别）：9 组读数的区间实际是
> **109k ~ 265k 拍（6.5% ~ 15.9%）**。"110–150k / 7–9%" 只覆盖 32×32 与 64×64 六组；
> 16×16 三组是 189k~265k（11.4%~15.9%），其中 16×16 FILL（n=2 725，精灵数最多）是离群点。

### 3.4 64×64 这一档说明了什么

- 每精灵固定开销 `A_FILL = 252` 拍，只占 64×64 一条命令的 **5.7%** ⇒ **尺寸档这个杠杆已经用尽**：
  继续加大精灵只会让 `Mpx/s` 无限逼近 97.6 的天花板，而那个天花板就是**像素通路自己**。
- 反过来，16×16 时 `A` 占 514 拍里的 **49%** ⇒ 小精灵场景的成本一半在"每条命令的固定动作"上，
  这解释了为什么 S2（想省掉命令下发）在 16×16 上被寄予厚望（也解释了它为什么没能兑现，见 §4.3）。
- 64×64 的价值不是"更快"，而是**给出了缩放律和本批最好的绝对吞吐数**（92.0 Mpx/s）。

### 6.1 墙是像素通路自己的 1 像素/拍

### 6.2 DDR 带宽**不是**限制（含推导）

前提：DDR3 16 bit × 800 Mbps = **1.6 GB/s** 峰值（《赛题二_方案设计与原理讲解.md》§2.2）；
扫描输出 960×540×2 B×60 = **62.2 MB/s**；每趟整片重铺 960×260×2 B ≈ 30 MB/s（`e` 开）。

| 场景 | 每像素访存 | 按**瞬时**吞吐算的流量 | 占 1.6 GB/s |
| --- | --- | --- | --- |
| 16×16 FILL（最低） | 写 2 B | 49.8 Mpx/s × 2 B = 99.6 MB/s；+ 扫描输出 + 重铺 = 192 MB/s | **12.0%**（帧预算归一口径 11.0%；再扣掉重铺 ⇒ **9.1%**） |
| 64×64 FILL | 写 2 B | 92.0 × 2 = 184 MB/s；+ 92 = 276 MB/s | **17.3%** |
| 16×16 KEY | 读 2 B + 写 2 B | 35.6 × 4 = 142 MB/s；+ 92 = 234 MB/s | **14.6%** |
| 64×64 KEY | 读 2 B + 写 2 B | 74.0 × 4 = 296 MB/s；+ 92 = 388 MB/s | **24.3%** |
| 16×16 ALPHA | 读 fg + 读 bg + 写 = 6 B | 29.9 × 6 = 179 MB/s；+ 92 = 271 MB/s | **17.0%** |
| 64×64 ALPHA（最高） | 6 B | 60.7 × 6 = 365 MB/s；+ 92 = 457 MB/s | **28.5%** |
| 线速上界（ALPHA，100 Mpx/s × 6 B） | 6 B | 600 MB/s | **37.5%**（外推，不是实测） |

⇒ 实测口径下 DDR 占用 **9%~29%**，即使按线速外推也只有 37.5%：**带宽不是限制**。
（模型推导；写侧另有独立证据：AW 合并后写主机 AXI 侧成本 1.13 拍/词 ⇒ 可持续 14.2 B/拍 ≈ 1.42 GB/s，
接近峰值，说明**写通道本身**也不是瓶颈。）

> 口径说明（与口述"DDR 带宽在峰值的 9–35%"的差别）：低端 **9.1%** = 16×16 FILL 在**帧预算归一**口径下
> 再扣掉整片重铺（若按瞬时口径、含重铺则是 12.0%）；高端本文实测最高 **28.5%**（64×64 ALPHA），
> **35% 只在"每像素 3 次访存 × 100 Mpx/s 线速"的外推下成立**（37.5%）。
> 上表的假设（2 B/px/流、扫描输出 62.2、重铺 30）已在表内列明；换假设请重算。

### 6.3 DDR 延迟 / 公平性是真弱点

| 证据 | 数字 | 口径 |
| --- | --- | --- |
| 描述符读的最长等待（仿真） | **64 拍 = `AGE_MAX`**（提权生效） | 仿真实测（`tb_dl_arb`） |
| 非引擎读流（CPU）在引擎压满读口时的等待 | **39 998 拍**（窗口 40 000 拍，`WAIT_MAX=32` 兜底） | 仿真实测（`tb_dl_arb` P1） |
| 板上描述符读被饿过 `DL_TIMEOUT` | 看门狗在**随机序号**触发、`stall_seen=1`（=被饿住，不是死了）；超时值已提到字段上界 **65 535 拍**仍会触发 | 板上实测（串口日志；示例行见 `tools/README.md` §3.4） |
| 极端情形 | 引擎把 AR 队列一直压满时，L1 的归还判据 `s_quiet` 让 CPU 整段轮不到（引擎一停立刻放行 98 笔） | 仿真实测（§18 的既有取舍） |

⇒ 判断：**"带宽够、延迟/公平性不够"**。描述符取指是**短突发（≤8 拍）、低频率**的流量，
占用比例只有 18.3% 的授权份额，却会因为引擎长突发把读口压满而被排到 65 535 拍之外。
这条不是吞吐问题，而是**列表路径能不能用**的问题。

### 6.4 结论

1. **吞吐的墙 = 单 lane 像素通路的 1 px/拍**（要动 `B`，只能加宽通路）。
2. **带宽不是墙**（实测 9%~29%，最高外推 37.5%）。
3. **`A`（每精灵固定开销）已经在 64×64 上摊到 5.7%**，只在 16×16 这种小精灵上还占 49% ——
   但小精灵场景同时被读流量与延迟卡住，所以"继续压 `A`"的边际收益有限。
4. **读路径的公平性是现在就妨碍演示的缺陷**（ALPHA/KEY 场景里列表路径会被看门狗打断）。

## 7. 接下来的优化计划（按优先级）

### 7.1 P1 双 lane 像素通路（最后一个大杠杆）

| 项 | 内容 |
| --- | --- |
| **依据** | §6.1：`B_FILL = 1.025` 拍/px、整屏 0.9958 px/拍、`A` 只占 5.7%；S1/S2/S3 全部只在压 `A` 或读流量，**没有一条动过 `B`** |
| **预期收益**（模型推导，`A` 不变） | 64×64 FILL 4 450 → **2 302** 拍/精灵（92.0 → **177.9 Mpx/s**，1.93×）；32×32 1 264 → **777**（81.0 → **131.8**，1.63×）；16×16 514 → **383**（49.8 → **66.8**，1.34×）。按 **85% 兑现率**（打包/lane 边界/双掩码的额外拍）⇒ 约 **160 / 120 / 60 Mpx/s**。**不是干净的 2×** —— 因为 Amdahl：`A` 不会跟着减半 |
| **代价** | `pixel_path` 大改（两路 acc/掩码、32 B/词或"两拍一词"、`lane0` 的两种非对齐起点）；`blt_addr_gen`/`blt_engine_fsm` 的行尾与窗口口径（`pp_width`/`pp_dbase`/`pp_dlane0`）；两套 `ifdef` A/B；一次综合 + 板上复核 |
| **风险** | ① **位精确性**：ALPHA 的 `(fg·α+bg·(255−α)+127)>>8` 与 CPU 参考实现必须逐位不变（6 个组合乘法器 → 12 个，四路 8 bit 乘加 + 32 bit 移位/或，**这是新增的最长组合锥**；当前 `core_clk` 最紧 setup 路径其实在 `u_eng.issue_r → u_dl.rd_beats` 的使能锥上、slack 1.063 ns，**不在乘法器上**，所以现在还有余量，但要综合后重看）；② **背压下丢像素**（§22 的 skid 教训：`wd_wr` 寄存一拍 ⇒ 两次推词决定必须至少隔 1 拍）；③ **非对齐 / 行尾**：`tb_blt_unalign` 的 U1~U12（lane 2/3/4/5/7、W=1/8/9/13/20/32、1×64 竖条、行尾残余词）必须全过；④ **写序**：AW→W→B 串行 + 单笔在飞是结构保证，双 lane 不得打破；⑤ ALPHA 的 DDR 流量翻倍到 **~960 MB/s ≈ 60% 峰值**（模型推导）—— 到那时带宽才开始变成需要考虑的东西 |
| **验收标准** | ① `tb_alpha`（α=0/32/64/128/160/255，含 `9B46/FD20/7BEF/0010/C618` 金标准）、`tb_blt_unalign`（U1~U12）、`tb_blt_burst`、`tb_wr_order`（H1/H2）全部 PASS；② 新增 `-DPIXEL_DUAL_LANE_OFF` A/B 项**必须 PASS**，且 OFF 模式读数与今天**逐字节相同**；③ 探针 `max_px_run` 由 960 变 **1 920**（或整行一次）、`FLUSH_*` 桶仍全 0、`hist_sum − PERF = 0`；④ 整屏 960×540 FILL ≤ **275 000** 拍；⑤ 板上 64×64 FILL `cyc/sprite` ≤ **2 600**（对应 ≥ 157 Mpx/s），且 `EV cmd path done` 的 n 与场景不变 |

> **口径说明（重要，与口述"写路径把双 lane 封顶在 ~1.77 px/拍"的差别）**：
> 写路径的**实测**能力是 **1.13 拍/词**，此处的"词"是 `words16B` 计数的 **16 B 词**
> ⇒ 0.885 个 16 B 词/拍 = **14.2 B/拍 = 7.1 px/拍**，**远高于**双 lane 需要的 0.25 词/拍（2 px/拍 × 2 B）。
> 口述的 "0.88 词/拍 = 1.77 px/拍" 只有在把"词"理解成 **32 bit 字**时才自洽（0.88 × 4 B = 3.52 B/拍 = 1.77 px/拍），
> 这与仓库里 `words16B` 的口径矛盾。**结论：写路径不是双 lane 的封顶项**；
> 双 lane 的 1.6~1.9×（而不是 2×）来自 **Amdahl（`A` 不减半）**，最终封顶项是 **ALPHA 的 DDR 流量**与**乘法器锥的时序**。

### 7.2 P2 读路径公平性 / 描述符预取（修"被饿死"）

| 项 | 内容 |
| --- | --- |
| **依据** | §6.3：板上 ALPHA/KEY 场景描述符读被饿过 65 535 拍（`stall_seen=1`）；`tb_dl_arb` 里非引擎读流等 39 998 拍 |
| **预期收益** | 让列表路径在 **ALPHA/KEY 场景真正可用**（现在会被看门狗打断并停用 ⇒ 那些场景拿到的收益是 0）。对 `A` 本身无收益 |
| **代价** | `axi_rd_master` 的 desc 侧权重/ageing + `dl_fetch` 的预取深度（`DL_CFG.CHUNK` 8→16/32、`FIFO_WM`）；寄存器语义微调；一个新的饥饿边界 TB |
| **风险** | 给 desc 加权会挤占 fg/bg（像素读有**硬死线**）⇒ 必须双向验证；改寄存器语义要同步改软件与文档 |
| **具体四件小事** | ① 加深描述符预取（现在一块 `CHUNK=8` 条、水位 `WM=4`）；② 给 desc 流更强的 ageing（现在要等满 `AGE_MAX=64` 才提权，可降到 16~32）；③ **`DL_STATUS.STALL` 做成粘住位**（它现在是组合位，`S_ERR` 之后恒 0，固件只能自己在轮询里粘）；④ **`DL_PERF` 在错误时刻也给"到目前为止"的拍数**（现在必须等 `BUSY=0` 才有效）；⑤ **BUSY 期间写 `0x4C~0x88` 不要静默丢**（现在 `if (ws[0] && !dl_busy)` ⇒ 写进去读回旧值，`7bdd307` 那个"GEOM_MAX 被丢"的坑就是这么来的；应改成反压或至少置一个 ERR 位） |
| **验收标准** | ① `tb_dl_arb` 新增"desc 权重可配 + fg 饥饿拍数 = 0 + desc 最长等待有界"用例；② 板上 ALPHA/16×16 连续 60 s 无 `DL_ERR`，且 `EV dl list done` 与 `EV cmd path done` **两行都稳定出现**；③ 健康表的 `stall_seen` 恒 0；④ `-DDL_OFF` 与 `tb_wr_order_dloff` 读数逐字节不变 |

### 7.3 P3 降低精灵场景的读流量

| 项 | 内容 |
| --- | --- |
| **依据** | §6.2：ALPHA 每像素 3 次访存（6 B/px）是 DDR 占用的最大项（64×64 ALPHA 实测 28.5% 峰值）；KEY/COPY 的源读也是 2 B/px |
| **做法** | ① **调色板 + 4bpp 索引纹理**（源读 2 B/px → **0.5 B/px** + 一次调色板查表）；② **打开 S3 掩码**（已经能用，缺的是"四角留空"的美术：新弹型按 §4.4 的阈值设计） |
| **预期收益**（模型推导） | ALPHA 6 B/px → **4.5 B/px（−25% DDR 流量）**；KEY/COPY 源读 −75%（KEY 4 B/px → 2.5 B/px）；S3 在 32×32 小弹上**已实测 −68.1%**、典型弹 −21.4% |
| **代价** | `pixel_path` 加 4bpp 解包器 + 调色板（16×RGB565 = 32 B，寄存器或 BRAM）；`blt_addr_gen` 的 4bpp 行跨度/非对齐口径（**一个 16 B 词 = 32 个像素**，与现在的 8 px/词完全不同）；美术侧量化 |
| **风险** | ① 4bpp 量化会改变颜色 ⇒ **ALPHA 的位精确基线必须重建**（现在 `tb_alpha` 的金标准是 16bpp 的），要么就严格限制"只有 KEY/COPY 支持 4bpp"；② 解包器加进 ALPHA 的组合锥（时序）；③ S3 的收益全靠美术，**不能算进 KPI 的确定项** |
| **验收标准** | ① 新增 `tb_pal4`：4bpp 解包 + 调色板 + 同一张图在 16bpp/4bpp 两条路径下**像素完全一致**（图案取自调色板）；② `tb_alpha`/`tb_blt_unalign` 在 16bpp 路径上读数逐字节不变；③ 探针新增用例（4bpp ALPHA）的**源读 beat 数 −75%**、写词数不变 |

### 7.4 P4 逐像素 alpha + 可编程混合（走**属性侧口**，不是显示列表）

| 项 | 内容 |
| --- | --- |
| **依据** | S2 的初衷是"把每精灵一次 CPU 下发换掉"，板上只拿到 +4.3%（§4.3）；但"每精灵参数不同"这个需求是真实的。设计文档 §13 原本要用**平行 ATTR FIFO**，被 S2 否掉（两个 FIFO 必须严格同步，错位即**静默错掩码**）；S3 已经证明**命令字空位**（`w0[31:16]`）能承载 16 bit 掩码 ⇒ **侧口应当是"每精灵一次 32 bit 寄存器写"**（CPU 直接写、不经 DDR 取指），而不是再加一条 DDR 取指流 |
| **做法** | 新增 `0x8C ATTR` 寄存器（`{MODE[1:0], ALPHA[7:0], …}`）+ 命令位"本命令取 ATTR"；引擎在 `ST_DEC` 锁存并使用 |
| **预期收益** | **新增表现力**而不是吞吐：逐像素 alpha（弹幕发光/爆炸）、加算/乘法混合（把 ALPHA 从"整精灵常数 α"升级到"纹理自带 α"）；一次 MMIO（~15~25 拍）比一条 DDR 描述符 + 取指风险便宜得多 |
| **代价** | `pixel_path` 的混合模式多选一；"CPU 写 ATTR → 引擎读 ATTR"必须定死配对规则（**先写 ATTR 再写命令**，或用序号配对）；软件每精灵多 1 次外设写 |
| **风险** | ① ATTR 与命令错位 ⇒ 必须像 S2 的 `I2` 一样做整条命令粒度的互斥；② 加算混合会破坏 ALPHA 的金标准 ⇒ 需要一套新金标准并保留旧模式的 A/B |
| **验收标准** | ① 新增 `tb_attr`：配对 / 乱序 / 缺省 / `MODE` 非法编码报错；② `tb_alpha` 在 `MODE=正常混合` 下读数**逐字节不变**；③ 主机自检新增 ATTR 编码用例；④ 板上：同一场景切换 `MODE` 只改观感，`cyc/sprite` 变化 ≤ 1% |

### 7.5 P5 扫描输出颜色 LUT + scissor 裁剪（两件便宜且互不依赖的事）

| 项 | 内容 |
| --- | --- |
| **依据** | 全屏渐变/闪白/受击闪红现在只能靠 CPU 逐像素写，而"诊断/效果代码与被测对象共用一条 DDR 读通路"已经吃过一次大亏（`开发问题与解决记录.md` 第 12 章：1/4 抽样的回读把帧率直接压低）；scissor 则能让"局部重绘"不再依赖整片重铺 |
| **做法** | ① `fb_scanout` 加 **3×256 项 RGB565→RGB565 LUT**（或 32 级亮度 LUT），只改 LUT 寄存器即得到全屏淡入淡出/闪白/染色；② 加 **scissor 寄存器**（`x0/y0/x1/y1`）限制引擎写区域 |
| **预期收益** | 全屏效果**零带宽**（不碰 DDR）；scissor 一次寄存器写代替一次整片重铺（省 ~30 MB/s 与一趟 pass） |
| **代价** | 扫描输出侧一个小 LUT（3×512 B BRAM）+ 引擎侧地址裁剪判据；各一个 TB |
| **风险** | ① LUT 在 `pixel_clk` 域、寄存器在 core 域 ⇒ 需要跨域同步（工程里已有成熟做法，但必须显式做）；② scissor 与 `CLIP_EN`/`STRICT_BOUNDS` 的语义要定清楚（报错还是裁剪） |
| **验收标准** | ① 新增 `tb_scanout_lut`：LUT 全 0 / 全 1 / 阶梯 / 对角线，逐像素比对；② 新增 `tb_scissor`：裁剪边界 × 非对齐 × 越界，且 `-DSCISSOR_OFF` 逐字节回到今天；③ 板上：切换 LUT 时 `SCAN_DBG(0x20)` 不变差 |

### 7.6 P6 主频 112.5 MHz（+12.5%）

| 项 | 内容 |
| --- | --- |
| **依据** | 吞吐 = 像素率 × 频率，`B` 不变 ⇒ 理论上 +12.5% 线性 |
| **预期收益** | 92.0 → **103.5 Mpx/s**（64×64 FILL，模型推导）；与 P1 叠加时按乘法叠（但 P1 之后 DDR 流量会先成为新约束） |
| **代价** | 一次 P&R + 一次上板；`pixel_clk`/DDR 域不变，但所有 core 域路径重新计时 |
| **风险** | ★ **按已提交的 V3.0 P&R 报告，112.5 MHz 收不了**：`core_clk` 10 ns 约束下 setup slack **1.063 ns**，工具算出的 **`Maximum possible analyzed clocks frequency = 111.894 MHz`（周期 8.937 ns）**；112.5 MHz 对应 8.889 ns，比这个上限还紧 0.048 ns。另外 `core_clk` 的 hold slack 只有 **0.026 ns**（≈0，与"hold 余量 ~0"的说法一致）⇒ 频率上探是**掷骰子**。而且最紧 setup 路径现在是 `u_blt/u_eng/issue_r[*] → u_dl/rd_beats[*]/d_addr_r[*]`（S2 新增的取指器使能锥），不是像素通路 |
| **验收标准** | ① P&R 报告 `core_clk` WNS ≥ 0 且 hold ≥ 0（**先证明 111.894 MHz 的上限被推高**，再谈 112.5）；② 上板同一 N / 同一场景下 `cyc/sprite` **不变**（证明"拍"的语义没变）、`Mpx/s` 提高 ≈12.5%；③ 全量回归 + 三个 `ifdef` 逃生门全过 |

### 7.7 P7 明确降级 / 搁置

| 项 | 为什么搁置 |
| --- | --- |
| **S4 命令内多精灵** | 依据是"每精灵固定开销"：`A=252` 只占 64×64 的 5.7%、占 16×16 的 49%。但 S2 已经把"命令下发"换成硬件（只省 4%），而 16×16 场景真正卡住它的是**读流量与延迟**（§4.3 遗留 ②）。⇒ 在 `B` 没降、读路径没修之前，S4 的收益上限很低，且它与写序屏障（`ST_WDWAIT` + `wr_commit_idle`）的交互是全新风险面 |
