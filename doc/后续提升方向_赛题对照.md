## 1. A 类：赛题字面要求上的缺口

### A1 ★ 「多张大图的快速切换」场景缺失（P0）

**依据** —— 赛题基础要求 3 原文：

> 提供一个基础测试 Demo（**例如：大量方块的随机移动、多张大图的快速切换**），
> 并能在屏幕上实时对比显示"纯软件 CPU 渲染"与"硬件加速渲染"的频率差异。

**现状**：FinalDemo 只做了前半句（大量方块随机移动），**后半句的举例一个都没做**。
整个工程里 `COPY(op=0)` 只在三处出现：AdDemo 的 LAYER 场景（COPY 一张固定背景）、
FinalDemo 的整帧上屏路径（编译期开关关掉的旧路径）、以及 RTL/TB 覆盖。
**没有任何 demo 在演示"多张大图快速切换"。**

**为什么值得补**：不只是"补字面"。COPY 是四个算子里**唯一同时吃读+写双向带宽**的，
是压测突发效率最狠的场景；而且它还能顺带回答一个目前只有单点数据的问题 ——
"整帧 COPY 1.89M 拍"是**上屏路径**的数字，不是**纯 COPY 吞吐**（含读源+写目的）。

**怎么做**（纯软件，不动 RTL）：

```
1. 开机在 DDR 生成 K 张大图（K=8，每张 960×524 RGB565 ≈ 1MB，共 8MB；DDR 256MB 绰绰有余）
   · 内容可以是程序化生成的测试图（色条 / 网格 / 渐变色轮 / 数字标号），不需要外部素材
   · 放 +0x900000 之后（+0x200000~+0x840000 已被图集/三块 FB/屏障/显示列表占用）
2. 加一个场景 SC_IMAGE（FinalDemo 的 1/2/3 之外加 '4'）：
   · 每帧（或每 N 帧，串口可调）用一条 COPY 把"下一张"整屏拷进后台缓冲
   · 信息条显示 IMG=k/K 与切换帧率
3. 复用现成的 1Hz 成本行口径，打一行 EV image switch: n=.. cycles=.. cyc/frame=..
```

**预期收益**：
- 补齐基础要求 3 的字面举例；
- 得到**纯 COPY 的板测吞吐**（px/拍），这是现在缺的一格数据；
- 顺带覆盖"大图切换时的撕裂"——三缓冲 FLIP 在整屏内容全变时是否仍然干净。

**代价与风险**：~150 行 C 代码，零 RTL 改动，风险接近零。

### A2 VGA 输出

**依据**：赛题"生成标准 VGA/HDMI 时序"、"最终通过 VGA/HDMI 接口输出至显示器"。

**现状**：只做 HDMI（板卡上**没有 VGA 接口**，只有 HDMI TX / MIPI / LVDS）。

**结论：不需要改 RTL。** VGA 与 HDMI 在 DE/HS/VS/RGB 这一层是**完全一致**的时序，
本设计的 `video_timing_1080p.v` 是参数化的，改参数就能出 640×480@60。
**建议做法是在报告与答辩里主动说明这一点**（"板卡无 VGA 口，本设计生成的是与 VGA 同一套
DE/HS/VS 时序，只是经 TMDS 编码走 HDMI 输出；把时序参数改成 640×480 即可满足下限"），
而不是留成"是不是没做 VGA"的疑问。

**优先级 P3**（说明性工作，不值当改代码）。

## 2. B 类：性能还能继续压的地方

### B4 ★ 参数级调优（P1，性价比最高）

**依据**：这些都是**改参数就能做、不需要动逻辑**的已知项：

| 参数 | 现状 | 改成 | 解决什么 |
| --- | --- | --- | --- |
| `TAIL_GRACE` | **4** | **6~8** | 现在 32 词被切成 **16+15+1** 笔 AW（尾词被单独切出来）⇒ 每命令多一次写往返。文档原话："参数，无逻辑代价" |
| `DL_CFG.CHUNK` | 8 | 试探 12~16 | desc 取指被长突发挤掉 ⇒ 加大 chunk 让它一次多取一些 |
| `DL_CFG.FIFO_WM` | 4 | 试探 6~8 | 提高取指 FIFO 水位，减少"吃一口停一下" |
| `AGE_MAX` | **64（估的）** | 由三流 TB 定（见 D2） | desc 通道提权太慢 ⇒ 授权率只有 18.3% |

**预期收益**：每条命令残留的 **19 拍**合并代价（16×16 时占 4.4%）应能压下去一部分；
desc 取指压力缓解后，列表路径的成功率提高。

**代价与风险**：改参数 → 重新综合/P&R（一轮几十分钟）。**逻辑不变 ⇒ 回归应全绿**，
但必须重跑 44 项回归 + 上板复核。

**为什么排 P1 而不是 P0**：它需要一次完整的 P&R + 上板，成本比 A1/D1 高。

### B1 ★ 读路径公平性（赛题文档里的 P2，P1）

**依据** —— 这是**文档自己认定的"现在就妨碍演示的缺陷"**：

| 实测/记录 | 数值 | 出处 |
| --- | --- | --- |
| 非引擎读流最长等待 | **39,998 拍** | `log_tb_dl_arb` |
| desc 取指授权率 | **18.3%** | 同上 |
| 带看门狗的 ALPHA/KEY 列表路径 | 超时从 4096 提到 **65535 拍仍然触发**（`stall_seen=1`） | v2.14 板级记录 |
| 后果 | **显示列表在"读多的场景"实际不可用**，必须退回逐条下发 | GameDemo 直接因此不用 DL |
| 更隐蔽的后果 | **程序本身在 DDR 里** ⇒ CPU 取指也吃这条读通路 | `功能清单.md §17` |

**根因**：两级 `axi_rd_arb` 是**固定优先级 + 老化提权**（扫描输出 > BitBlt > CPU，`AGE_MAX=64`）。
问题在于**引擎的长突发会把读口压满**，而 desc 是"短突发（≤8 拍）、低频率"的流，
排不进去 —— 文档的一句话总结很准：

> 占用比例只有 18.3% 的授权份额，却会因为引擎长突发把读口压满而被排到 65535 拍之外。

**怎么做（按风险从低到高）**：

1. **先调参**（见 B4）：`DL_CFG.CHUNK/FIFO_WM` + 降 `AGE_MAX`。**不用改 RTL。**
2. 给 desc 通道**独立的信用额度**（credit-based，而不是纯优先级）—— 它每帧只需要很少的带宽，
   但要求**有界延迟**。
3. 限制引擎**单次连续突发的长度**（长突发之间插空隙），给别的流让路。
4. 把 CPU 取指流单独提到最高优先级（它没有"每帧预算"，但**死了整机就停了**）。

**预期收益**：
- 列表路径在 ALPHA/KEY 场景可用 ⇒ 省掉逐条下发的 CPU 开销（见 B6）；
- CPU 取指延迟改善 ⇒ 主循环更稳。

**代价与风险**：**这是全工程风险最高的改动**。`功能清单.md §13` 就是因为改读侧
（扫描输出优先级）导致"时序收敛但板子不启动"，最后**二分 + 回退**才恢复（§14）。
**所以必须先把 D2（三流联合压测 TB）做出来再动 RTL。**

### B6 ★ 指令下发通路：APB 单字写 → 突发写（P1）

**依据** —— 板测数字：

> 板级实测"每块一次 CPU 下发"≈**190 拍/块**（1 读 COUNT + 8 写 DATA 走 APB 桥），
> 把 16×16 FILL 从引擎自身能到的 367 拍/块抬到 561 拍/块。

**算一下它在帧预算里占多少**：

| N | CPU 下发开销 | 占帧预算（1.67M 拍） |
| --- | --- | --- |
| 256（默认） | 48,640 拍 | 2.9% |
| 1000 | 190,000 拍 | **11.4%** |
| 2400（上限） | 456,000 拍 | **27.4%** |

引擎本身在 N=2400 时已经超预算（2400 × 856 = 2.05M 拍），所以那时瓶颈是引擎；
但**在中等 N（几百~一千）时，CPU 下发是要认真算的一块**，
而且它吃掉的是 CPU 的时间 —— 游戏逻辑（碰撞/生成/AI）也在同一颗 CPU 上。

**怎么做**：
- 方案 A（推荐）：给加速器加一个 **AXI4 从机端口**，支持**突发写指令 FIFO**
  （一次 burst 写 N 条命令）。AXI 突发的每拍吞吐远高于 APB 单字事务。
- 方案 B（更省事）：**软件侧合并** —— 现在 `blt_emit` 是 8 次独立写，
  如果能把 8 个字作为一次 32 字节的写... APB 桥不支持突发，所以这条走不通。
- 方案 C：**用显示列表**（本来就是为这个目的做的）—— 但被 B1 卡住。

**预期收益**：190 拍/块 → 乐观 40~60 拍/块（**约 1/4**），
中等 N 下把 11% 的帧预算降到 3%。而且在 B1 修好之前，**这是唯一能绕开读公平性问题的路子**。

**代价与风险**：新增从机端口 = 改 `blt_top` / `blt_regs_axi_lite` / 顶层互联，
中等改动；需要新的 TB 覆盖突发写路径。

### B2 命令间重叠（藏掉 `A`）（P2，理论收益最大但风险最高）

**依据** —— 结构性事实：

| 事实 | 数值 |
| --- | --- |
| `A_FILL` 固定开销 | **252 拍/命令** |
| 在 16×16 里占 | **49%** |
| 在 64×64 里占 | 5.7% |
| 命令之间重叠了多少 | **64 块背靠背只藏了 63 拍 = 0.075%** |

根因是 §19 的写屏障：**每条命令必须等上一条完全写提交**
（`b_pending==0 && wd_count==0 && !wd_busy`）才开始下一条 ⇒ `A` 逐条串行累加。

**怎么做**（保持写序前提下的重叠）：
1. 只有两条命令的**目的区域不重叠**时才允许重叠 —— 软件在 `w0` 空位或属性字里给一个
   "无重叠"提示位，或硬件做区间比较（代价高）；
2. 或者做**双 bank 的写提交追踪**，让下一条的**取数**与上一条的**写回**并行，
   只在写回同地址时串行。

**预期收益**（模型推算，`A` 减半）：

| 场景 | 现在 | 藏掉一半 `A` | 倍数 |
| --- | --- | --- | --- |
| 16×16 FILL | 514 | ~388 | **1.32×** |
| 16×16 ALPHA | 856 | ~624 | **1.37×** |
| 32×32 FILL | 1264 | ~1138 | 1.11× |
| 64×64 ALPHA | 6743 | ~6611 | 1.02× |

**对小精灵密集的场景（弹幕游戏）收益最大**，对 64×64 几乎无用（`A` 只占 5.7%）。

**代价与风险**：**最高**。写序正确性是 §19 花了整章力气才修好的
（之前"重叠处 z 序高频乱跳"），而当时的结论恰恰是"引擎假完成 ⇒ 下条指令 RAW 抢跑"。
**任何允许重叠的改动都必须先有一个"重叠/非重叠 × 提交延迟随机"的新 TB。**
**建议排在最后做。**

### B5 属性侧口流水化（P2，条件触发）

**依据** —— `功能清单.md §28.7` 自己点出的最大未验证项：

> 混合命令的像素锥变成"α 计算乘法 → ÷255 → 混合乘法"两级串联乘法器……
> V3.0 P&R 的最紧 setup 路径**不在像素通路**，所以现在有余量；
> 但这个锥是运行期信号 `blend` 门控的，**综合器无法按模式剪掉**，即使用户从不写属性。

**怎么做**：把 `A` 的计算打一拍流水 —— `A` 是逐像素值，在 `lane` 计数那一级就能提前一拍算出来，
**不需要改变推词时序与背压**。

**触发条件**：下次 P&R 如果报出像素通路成为新的 critical path，就做这个。
**现在不用动**（V3.0 的 slack 是 1.063ns，有余量）。

### B3 4bpp 调色板（P3，收益有限）

**依据**：赛题文档 §7 把它列为 P3。

**为什么排 P3**：它的卖点是"图集读带宽减半"，但**实测 DDR 带宽只占峰值的 9%~29%**，
**带宽不是墙**。真正的墙是像素通路（`1 px/拍`，v3.1 双 lane 已解决到 2 px/拍）和读延迟（B1）。
所以 4bpp 的收益主要落在"读延迟压力变小"上，间接、且不如 B1 直接。

**代价**：调色板 RAM + 每像素查表（新增一级流水）+ 新的 `src_format`
（属性侧口 `[5:4]` 正好有保留位可用）。

### C1 ★ GameDemo 的 v3.2 特性上板验证（P0）

**依据**：报告里所有 v3.1/v3.2 的数字都标着【仿真】——
因为 `功能清单.md §27.7 / §28.7` 明确写了"未跑 Efinity、上板"。

但**没有任何 v3.1/v3.2 的板级性能读数**。GameDemo 的基础版已由用户上板跑通，
但四档算子 / 极限 N / 属性侧口都还没有板级数据。

**怎么做**（一次上板就够）：

```
1. 烧 firmware\v3.2\GameDemo_v3.2_soc.hex（SPI Active → 断电重上电）
2. 看开机 feat 行：feat: clip=1 lut=1 attr=1   ← 这一行就证实了 v3.2 三个新功能在板上活着
3. 按 4 拉满 N → 按 g 自动爬坡 → 抄 LIMIT N=.. fps=.. ON=..
4. 四档（5/6/7/8）各重复一次
5. 按 d 抄 bulm=.. / cap=FILL/ALPHA/KEY / flipto,clr to,err,stto
6. 存成 doc/logs/board_gamedemo_limit_*.txt
```

**预期收益**：把报告里几处【仿真】直接升级成【板测】；这是**成本最低、收益最高**的一件事。

### C2 ★ GameDemo 加「同屏分屏」对比（P1）

**依据**：赛题明确要求"**在屏幕上实时对比显示**纯软件 CPU 渲染与硬件加速渲染的频率差异"。
FinalDemo 已经用 SPLIT 模式满足了，但那是"方块随机运动"场景。

**现状**：GameDemo 的 CPU 对比是**整屏切换**（按 `c`/`h`），`HW=`/`SW=` 两个数留在屏幕上 ——
但**没法在同一屏上同时看到两边**。

**怎么做**：
- 加一个 SPLIT 模式：上半屏引擎画弹幕、下半屏 CPU 逐像素画**同一份**弹幕；
- CPU 侧渲染器已经现成（`cpu_blit` + `add565`/`blend565`）；
- 弹幕场景下 CPU 侧会直接卡成幻灯片（几百颗 16×16 精灵 = 每帧十几万次逐像素读写）
  ⇒ **对比极其有冲击力**。

**注意口径**：CPU 侧要保留"朴素逐像素"语义（不批量化），否则分母不诚实 —— 这条 FinalDemo 已经立好了规矩。

**代价与风险**：中等（复用 FinalDemo 的 SPLIT 结构），风险低。

### C3 FPS 历史曲线 / C5 上位机统一入口（P3）

## 4. D 类：验证与证据链

### D1 ★ 板级原始日志未归档（P0）

**依据** —— 文档自己承认的**唯一一处"数字在、证据不在"**：

> 本文档全部板级读数（含 §3.1 九组）**没有归档**。

**怎么做**：上板跑一次，把 1Hz 成本行按"场景 / 尺寸 / 路径 / N / cyc per sprite"
存成 `doc/logs/board_costline_*.txt`。

**为什么是 P0**：报告里最核心的性能表（16×16 = 514/719/856 拍）目前**只有文档转述、没有原始日志**。
一次上板就能把这个证据缺口补上，而且它和 C1 是同一次操作。

### D2 三流联合压测 TB（P1）

**依据**：设计文档 §12 计划的"desc + fg/bg + 扫描输出 **联合**压测"**没有写**。
现有的 `tb_dl_arb` 只覆盖了"desc 与 fg/bg 共用信用池、引擎优先"这个结构性保证。

**后果**：
- `AGE_MAX = 64` 是**估的**，没有依据；
- 读仲裁在真实三流竞争下的行为**未验证**；
- 而 B1（读路径公平性）必须动这里 ⇒ **没有这个 TB 就不敢动**。

**怎么做**：在 `tb_dl_arb` 基础上加"扫描输出按 1481 拍/行的死线持续取数"这一路，
三方同时跑，观察：desc 取指最长延迟、引擎像素流欠载、扫描输出欠载行数。

**优先级 P1**：它是 B1 的**前置条件**。

## 5. E 类：工程化

### E1 寄存器映射抽公共头（P2）

**依据**：软件层最大的可维护性风险 ——
**整套加速器寄存器映射在各 demo `.c` 里内联重复了 6 份**
（FinalDemo / AdDemo / GameDemo / comptest / comptest2 / fulltest+userDef.h）。

**怎么做**：抽 `blt_regs.h`（地址与位域宏）+ `blt_drv.c`（`blt_emit` / `blt_push_room` /
`cache_evict` / 清屏引擎封装等），各 demo 改为 `#include`。

**收益**：以后再加寄存器（像 v3.2 那样一次加 8 个）只改一处。

**风险**：要动 6 个已验证过的 demo ⇒ 每个都要重编重测。**建议只在新 demo 上先试用，不要一次性全改。**

---

### E2 自动化回归（P3）

现在回归要 `cd doc/logs && pwsh -File ..\..\rtl\tb\run_regress.ps1` 手动跑。
可以写一个顶层脚本把**四层验证串起来**：44 项 RTL 回归 → 7 个 demo 编译 → 主机全固件仿真 →
协议自检 → 一键镜像，任一环红就退出。

（`tools/build_gamedemo.ps1` 已经是这个思路的雏形，只是只覆盖 GameDemo。）

## 6. 建议的执行顺序（如果按一条线走）

```
第 1 步（一次上板，零代码改动）
   ├── 烧 GameDemo_v3.2_soc.hex
   ├── 看 feat 行 / 四档切换 / g 自动爬坡 / d 诊断
   ├── 归档 doc/logs/board_gamedemo_limit_*.txt 与 board_costline_*.txt
   └── 结果：报告里所有【仿真】→【板测】，D1 + C1 完成

第 2 步（纯软件，零 RTL 风险）
   ├── A1 加「多张大图快速切换」场景（补齐赛题字面举例 + 得到纯 COPY 吞吐）
   ├── C2 GameDemo 加「同屏分屏」对比（答辩效果最强的一屏）
   └── D3 修正文档口径漂移

第 3 步（参数级，需要一次 P&R）
   ├── D2 先写三流联合压测 TB（为第 4 步铺路）
   └── B4 调 TAIL_GRACE / DL_CFG / AGE_MAX，重跑 44 项回归 + 上板复核

第 4 步（RTL 改动，按风险从低到高）
   ├── B6 指令下发改突发写（收益确定、风险可控）
   ├── B1 读路径公平性（有 D2 的 TB 兜底后再动）
   └── B2 命令间重叠（最后做，收益最大风险也最大）
```

**如果时间只够一件事**：做第 1 步。一次上板能把报告里最大的证据缺口补上，
而且它是**已经准备好的**（固件、上位机、验收判据全都在）。

**如果还能做第二件事**：做 A1（多张大图切换）—— 它是**唯一一处赛题字面要求没覆盖到的地方**，
而且纯软件、零风险。
