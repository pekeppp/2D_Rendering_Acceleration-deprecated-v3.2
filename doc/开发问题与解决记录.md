## 1. 串口观察通道失效 → 一串测试结论作废
### 现象
复位后有开机信息，之后画面与串口"全无响应"；反复敲 `m` / `n` / `r` 没有任何回显。§16 的原始现场：banner 打完只剩 `[d] 1A 1B [d] 2A 2B [d] 3A 3B `，此后静默（`[d]` 只在前 3 圈打，第 3 圈之后本就该静默到 300ms）。更麻烦的是这期间**板上→PC 这个方向本身也是坏的**，所以"没回显"既可能是程序死了，也可能是链路死了。
### 我最初以为的原因 / 走过的弯路
① 先怀疑主循环死了，加 `first-loop-ok`、每 16384 圈一条 `T it=...`、300ms 一条 `S ...`——**探针设计错误**：三条全押在"循环能活到那个时间点"上，死点在 ~2000 圈到 16384 圈之间是盲区（§16.5 自己复盘了）。② 再怀疑定时器（`mcycle` CSR 见第 7 章同类案例），已排除。③ 又怀疑 `%s`：统计行 `S ... %s ...` 是唯一从未打印成功的行、也是唯一带 `%s` 的行，于是加了**按键触发**的 `stest-begin / stest-s: %s / stest-end` 做单变量判定（§16.3）。④ 还怀疑过 `bsp_getChar()`——它是**阻塞**的（`while(uart_readOccupancy(reg)==0);`），放进主循环会让循环只在收到字符那一拍转一圈，fps 恒 0、画面像卡死（§16.1）。
### 定位过程
真正区分开的是**不依赖串口**的探针加上状态寄存器原始值：屏幕状态条右端 32×16 方块每次 OSD 刷新绿/红交替 ⇒ **循环活着**；`selfcheck` 新增 `UST=%x URO=%d`，空闲读到 `UST=00800000`（`bit23:16=0x80=128` = TX 剩余空间、`bit31:24=0` = RX 占用）⇒ **硬件层面反证字段布局**，也就证明 `>>24` 是按硬件事实改的；`[d] 3A 3B ` 是**完整**一条 print ⇒ CPU 不是卡在 `uart_write`；整包 424 字节 / 63ms 而 115200 线速率 11.5KB/s、TX FIFO 从未堵住 ⇒ CPU 时间花在循环体上（§16.5）。
### 根因
两层，都是"测量通道"的根因。① **代码层真 bug**：`uart_poll_char()` 第一版判据写成 `((st >> 16) & 0xFFu) == 0u`，取的是 **TX 剩余空间**而非 RX 占用；banner 一打完 TX FIFO 必然有货 ⇒ 判据恒真 ⇒ **每圈都去读空的 RX 数据寄存器**，既拿不到真字符（串口指令完全无效），又可能多推 RX 读指针把真实字符吃掉（§16.1）。厂商语义是 `uart_writeAvailability=(status>>16)&0xFF`、`uart_readOccupancy=status>>24`。② **工具层**：板上→PC 方向在若干构建上确实是死的，最后发现**PC 侧串口工具需要重启**，不是代码问题 **【据观察记录】**。在这一层查清之前，基于 `f`/`g`/`m`（见第 11 章）得出的若干结论——**其命令是否真的送达并不确定**——只能作废重测；更早那版 banner 也在这段时间"消失"过。
### 解决方法
`uart_poll_char()` 一律改为 `if ((uart_status_raw() >> 24) == 0u) return 0;`（`comptest2.c:384-388`、`FinalDemo.c:401-405`）；反汇编确认修复进了 bin（`lw a5,4(0xf8010000)` → `srli a5,a5,0x18` → `beqz`，§16.1）。主循环一律非阻塞轮询、**不调用** `bsp_getChar()`。把"串口是否活"变成独立可观测量：`UST`/`URO` 原始值、屏幕方块闪烁、任何一圈收到字符都回显 `[ev1]`。mini-printf 三条硬约束写进源码头部与流程。
### 原理分析
`bsp_printf` 是 `print.h` 的 mini 版，**只认 `%c %s %d %X %x`**：

| 写法 | 后果 |
| --- | --- |
| `%u` / 宽度数字（`%5d`） | 解析器跳过它继续找转换符 ⇒ **错位消耗 `va_arg`**；后面的 `%s` 拿整数当指针 ⇒ 直接挂死 |
| `%%` | 解析器是 `if (format[i]=='%') { while (format[++i]) {...} }`，**不把 `%%` 当转义**；`"%%s"` 被当成 `%s` 并取一个**根本没传的参数**（野指针）⇒ 挂死（§16.3.1） |
| 非 ASCII 调试串 | 编码/字体链路不可控，调试期一律 ASCII |

另外 `bsp_init()` **必须最先调用**——UART 时钟分频在它里面配置（`FinalDemo.c:538`）。
### 教训
下结论之前先验证测量通道：串口方向、状态字段语义、printf 格式串都算测量通道；调试探针要按**操作类别**拆分（PH0~PH3 式），不要按时间点拆分。
## 2. 扫描输出取数无界 → `s_hold` 把 CPU 永久锁在 DDR 之外
### 现象
整机跑 1~2 秒后彻底静止：串口再无输出、屏幕停在最后一帧。§17.1 的分阶段自检锁得很死——`ticktest`（`d=260149`，mtime 正常）、PH0 只读 CLINT+串口（`it=624088`，跑满 1 秒 ✓）、PH1 再加 UART 状态/GPIO（`it=488323`，跑满 1 秒 ✓）、PH2 加写帧缓冲（含 `scene_step`）后**再无任何输出** ✗。即：**只碰 MMIO（走外设总线不过 DDR）的循环能跑满一秒，一碰 DDR 就死。**
### 我最初以为的原因 / 走过的弯路
① 当成时序/工具问题：22:03 那次时序已收敛（最小 slack +0.254ns、`design_issue.xml` 只有一条 LVDS 布局告警、`cdc.rpt` 无告警）却仍不启动 ⇒ 判定为功能性问题（§14.1）。② 把读侧优先级门控 `S_PRIO=1` 当元凶并整体回退到 v2（§14.2/§14.3）——实际元凶是**写**仲裁器的 skid 改写（§14.5 二分结论）。③ 加"预热"绕过：开机趁 DDR 健康时把主循环工作集读进缓存（`comptest.c:528-557`），这步同时是诊断——预热后仍卡死就说明与"冷读拿不到通道"无关。
### 定位过程
关键对照是**用户提出的**："性能测试（fulltest）时可以直接切 CPU 渲染，为什么这份不行？"查 `fulltest` 源码得答案：它**所有 CPU 侧帧缓冲写都写向 `FB1_BASE`（屏外缓冲）**，从不写正在显示的那块（§17.7 引 `fulltest.c:1243/1318/1353/1415/1548` 与 `fulltest.c:1000-1001`）；comptest 是第一个让 CPU 直写显示中帧缓冲的代码。故障注入 TB `ARC_2DRA/rtl/video/tb/tb_scanout_wd.v`（fault A 某行只回一半拍数并**提前拉 rlast**、fault B 某行回 2 拍后**彻底停住**、fault C 第二个硬故障行），A/B 用 `-DWD_OFF` 把三个超时全放 `0xFFFF`：

| 指标 | 有界化（`FETCH_TO=64`） | 无有界化（`0xFFFF`） |
| --- | --- | --- |
| `m_axi_hold` 连续为高 | **133 拍** | **131,075 拍** |
| `dbg_underrun` | 1 | 21 |
| 故障后继续取到的行数 | 11 | 18 |
| 判决 | ALL PASS | **FAILED** |

仓库内实跑日志 `log_tb_scanout_wd.txt`：`hold_max=132`、`hold_min(timeout)=132`、`hold low after abort=983`、`dbg_abort=2`、`AR after faultB=11`、`dbg_underrun=1`。第二次上板 `SCAN=000a0108`（`abort=10`、`underrun=264`）恰好证明新比特流 + 新看门狗生效（旧代码该计数恒 0），但 PH2 依旧"有 begin 没 end"。
### 根因
RTL 结构性缺陷（v1.0 / v2.5 皆然）：`fb_scanout.v` 里 `m_axi_hold = (st == S_FETCH)`，而 `S_FETCH` 的**唯一出口**是 `beat_idx == BEATS_PER_LINE-1`（收满 120 拍）——没有超时、没有看门狗、没有别的出口；`axi_rd_arb.v` 里 `owner==1` 时归还通道的条件是 `cnt_s==0 && !s_arvalid && !s_hold`。于是只要某行取数没收满 120 拍（从机少回几拍 / 某笔突发不来 / 计数口径任何偏差），FSM 就永远停在 `S_FETCH` ⇒ `s_hold` 恒高 ⇒ 读仲裁器永远不还通道。而 linker 是 `ram : ORIGIN = 0x00001000, LENGTH = 124K`（`FinalDemo.map:429-430`：`ram 0x00001000 0x0001f000`，124KiB）——**整个程序（代码/数据/栈）都在 DDR 最开头**，所以"CPU 拿不到 DDR 读通道"= **取指都取不到** = 整机死；片内只有 4KB RAM（`SYSTEM_RAM_A_CTRL=0xf9000000`），装不下 ~12KB 程序（§17.1）。这正是 §15.4 已记下的残留风险：`s_hold` 只防住"过早归还"，"永不归还"没有上限。第二次上板还暴露出下一层：看门狗把"永久死"换成了"**重试风暴**"——CPU 猛写 → DDR 写队列灌满 → 读延迟暴涨 → 某行收不齐 → 超时 → 立刻重试 → 又超时，而每次尝试里 `s_hold`/`s_arvalid` 都占着通道 ⇒ 占用率接近 100% ⇒ 现象看起来一样（§17.7）。
### 解决方法
`ARC_2DRA/rtl/video/fb_scanout.v`（不改端口表 ⇒ 不改任何 TB 连线）：

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | `S_FETCH` 看门狗 `FETCH_TO`(4096)：无数据流动就累加 `fetch_to`，到点转 `S_DRAIN` | `:62`、`:365-372` |
| 2 | `S_DRAIN` 排空 `DRAIN_TO`(4096)：保持 `rready=1`/`s_hold=1` 把已下单突发的残留 R 拍收干净，判据用 **rlast 计数** `all_bursts_got`；收干净后不标 `buf_ready`、`next_y` 不动 | `:65`、`:171-176`、`:380-401` |
| 3 | 口径兜底：已下发突发全部收到 rlast 但 beat 没到齐（从机短回）也认定本行结束 | `:356-363` |
| 4 | `m_axi_hold` 由"整行取数中"改为按**突发**：`(ar_idx != burst_done)`，与 `cnt_s`（AR 握手 − rlast）粒度一致 | `:192-195` |
| 5 | `S_BACKOFF` 强制退避 `BACKOFF_TO`(4096)：硬放弃后 `s_arvalid=0`/`s_hold=0` 这么久，通道必然回到 CPU | `:66-75`、`:405-410` |
| 6 | 进 `S_FETCH` 时 `drain_to <= 0`（否则上次 DRAIN 中止后残留的大值会让下次排空**立刻**超时） | `:329-333` |
| 7 | `dbg_abort`：core 域只产生单比特 toggle `wd_tgl`，pclk 域两级同步 + 边沿检测得 `wd_ev_p` 再累加 | `:419-426`、`:480-510` |

断言逐条做反向验证：注掉 `drain_to` 清零 ⇒ `hold_min` 从 133 掉到 69 ⇒ TB FAILED；`-DWD_OFF` ⇒ FAILED。备份在 `backup/fb_scanout_v2.6_backup.v` 与 `backup/tb_scanout_wd.v`。
### 原理分析
**AXI 语义**：主机交还总线归属的前提是"不会再有属于我的 R 拍回来"；R 通道没有 ID 之外的路由信息，一旦归属换了，残留 beat 会被送给新 owner（CPU）**写坏它的 D$**。所以排空（`rready=1` 把已受理突发的 R 拍收完）是"安全交还"的必要条件，`cnt_s==0` 只是它的代理指标。**有界性算术**：`s_hold` 连续为高的最坏值 ≤ `FETCH_TO+DRAIN_TO` ≈ 8192 拍 ≈ **82µs**（core 100MHz），远小于一帧 16.7ms；加上退避后扫描输出对读通道的占用上限 = `8192/(8192+4096) ≈ 67%` ⇒ CPU 至少拿到 1/3 读带宽，**最坏只是"慢"，不会"死"**；代价是退避期不取数、画面欠载（可接受，压力解除后自动恢复）。**跨时钟域**：`dbg_abort` 是 pclk 域寄存器，core 域 FSM 直接 `dbg_abort <= dbg_abort+1` 就是两个 always 块驱动同一 reg（Efinity 报 `VDB-1000/1001`，只在综合阶段报）；多位计数器不能直接跨域，正确做法是**单比特 toggle + 两级同步 + 在目标域累加**。
### 教训
"钉住资源"的机制必须**同时有释放上限**——只防"过早释放"不防"永不释放"，等于把死锁写进设计；跨时钟域计数器一律单比特 toggle；故障注入 TB 必须做反向验证，否则断言只是陪跑。
## 3. 960×540 → 1080p 满屏 2 倍上采样
### 现象
帧缓冲 960×540、输出 1920×1080 ⇒ 点对点显示四周必有黑边；把帧缓冲改成 1920×1080 则 DDR 读带宽翻倍。
### 我最初以为的原因 / 走过的弯路
这是明确需求（不是 bug），弯路在**测试台判定口径**上（§18.3 记了四条 TB 自坑）：① 把"像素值里编码的源行号"当"输出行号"推期望值 ⇒ **3465 个假错误**；② `run_same` 计数器忘了递增 ⇒ 误报"只出现 1 条"；③ 判定起点落在帧中间/跨帧回绕；④ 每行**最左 1~2 像素**是黑的——定位打印显示此时 `buf_ok=1 / rdy=11`（**不是欠载**），是行首控制/数据通路的固定对齐瞬态，真实 1920 宽下占 1/1920、不可见，TB 按 `hcnt>3` 排除。
### 定位过程
判据改成**坐标无关的序列性质**（不依赖内部流水线延迟与 `hcnt/vcnt` 对齐）：行内第 k 个像素解码出的源列号必须是 `k>>1`（0,0,1,1,…,31,31）；相邻输出行的源行号必须"重复"或"+1"（2 倍放大 ⇒ 重复次数 ≈ 前进次数）。假错误一次性消失。
### 根因
（设计问题，非缺陷）最近邻放大的坐标映射必须**同时**作用在横向、纵向与"已消费源行号"三处，只改其中两处就会出现"行供不上 / 缓冲奇偶错位"：`xoff=(hcnt-WIN_X)>>SCALE_SH`、`vsrc=(vcnt-WIN_Y)>>SCALE_SH`、`par_cur=(SCALE_SH==0)?vrel[0]:vrel[1]`、`cons_p=vsrc`。
### 解决方法
`ARC_2DRA/rtl/video/fb_scanout.v` 新增参数 `SCALE_SH`（默认 1），`DISP_W=FB_W<<SCALE_SH`、`DISP_H=FB_H<<SCALE_SH`（`:33-39`、`:118-120`）：`xoff` 与 `raddr=xoff[11:3]`/`xlo=xoff[2:0]`（`:199-203`）；`vsrc=vrel>>SCALE_SH`、`par_cur=vrel[1]`（`:446-450`）；输出窗口 = 1920×1080 = active 区 ⇒ 无黑边（`:441-444`）；`cons_p` 改成 `vsrc` 使 core 取数节奏自动减半（`:462-477`）。顶层 `ARC_2DRA/rtl/ddr3_example_top.v:723-730` 例化时**没有显式传 `SCALE_SH`**，吃的是默认值 1（即上板版本就是 2 倍放大）。新增 `ARC_2DRA/rtl/video/tb/tb_scanout_scale.v`（32×16 假帧缓冲，像素值 = `(y<<8)|x`，输出 64×32 铺满 active），实跑日志 `log_tb_scanout_scale.txt`：

| 判据 | 结果 |
| --- | --- |
| 检查过的输出行数 | 41（应 ≥32）✓ |
| 行内 64 像素解码出的源列号 = `0,0,1,1,…,31,31` | **0 错误** ✓ |
| 相邻输出行源行号"重复 / 前进" | **重复 20 / 前进 19**，异常 0 ✓ |
| DE 期间黑像素 | **0** ✓（满屏无黑边） |
| 取数笔数（AR） | 38（只随源行增长，**不因放大而多读**）✓ |
| `dbg_underrun` | 1（仅上电第一帧启动瞬态）✓ |

`SCALE_SH=0` 时 `par_cur = vrel[0] = vcnt[0]^WIN_Y[0]`，与 v1.0 **逐位等价**；`tb_fb_scanout` 显式传 `.SCALE_SH(0)` 继续守"不放大"那条路（`run_regress.ps1:24-25`）。
### 原理分析
**带宽**：仍然只读 960×540 = 1MB/帧 = **62MB/s @60fps**；若帧缓冲改成 1920×1080 则 ~124MB/s——放大在扫描输出侧做，DRAM 流量不变，这是选这条路线的全部理由。**可实现性**：横向靠"列号右移一位"（同一源像素被两个输出列读两次、读地址不变），纵向靠"一条源行供两条输出行"（缓冲奇偶由 `vrel[1]` 决定），因此 `cons_p` 必须跟着变成源行号，否则 core 域按输出行节奏取数、取两倍的行，把带宽又吃回去。**行预算**：1080p 一行 `2200 pclk / 148.5MHz = 14.81µs`，在 core 100MHz 上是 **1481 拍**；取一行 120 拍即使按 v2 的慢取数（≈1080 拍）也只占 73%，v2.5 之后 ≈250~400 拍 ≈ 20%。
### 教训
缩放/映射类改动的验证要判**序列性质**，不要把内部延迟对齐写进期望值（那是测试台自己在制造假错误）；带宽预算要在改之前算——改帧缓冲尺寸是 2 倍流量，改扫描输出是 0 倍。

## 5. OSD 信息栏花屏
### 现象
2 倍放大生效、画面铺满全屏，但**信息栏乱码**：字形碎成 2 像素一块（§18.6 ②）。
### 我最初以为的原因 / 走过的弯路
先怀疑字模表、`glyph_of()` 查表、字符宽度推进（`x += 8`），以及"OSD 是不是被渲染区擦掉了"。都不是原因。
### 定位过程
"碎成 **2 像素一块**"这个形状本身就是线索：错位的单位是 **32bit 字**而不是字符或行 ⇒ 直接看写字代码。`cpu_osd_text` / `osd_text` 把一行 8 个像素合成 4 个 32bit 字写下（`comptest.c:242-263`、`FinalDemo.c:358-378`），逐个检查每个字两个半字的来源即可。
### 根因
帧缓冲是**小端**：32bit 存储的**低 16 位落在低地址 = 左边的像素**。第一版把第 1 个像素（字模 `bit7`）放进了**高**半字，于是每个字里的两个像素被**对调**，字形碎成 2 像素一块 ⇒ 屏上就是乱码（旧版逐像素 `wr16` 没有这个问题）。
### 解决方法
`osd_text()`（`FinalDemo.c:355-378`、`comptest2.c:341-361`、`comptest.c:242-263`）改为低半字（x+0）放 `bit7/bit5/bit3/bit1`、高半字（x+1）放 `bit6/bit4/bit2/bit0`，即 `p[0] = ((bits & 0x40) ? fg<<16 : bg<<16) | ((bits & 0x80) ? fg : bg);`（`FinalDemo.c:367-374`）。
### 原理分析
RISC-V 是小端：`volatile uint32_t *p` 写到地址 `A` 时 bit15:0 落在 `A+0`、bit31:16 落在 `A+2`；像素在内存里按 x 递增排列（`x*2` 字节步进）⇒ `A+0` 是**左**像素。把 `bit7`（字形最左）放低半字才与内存序一致。一次 32bit 存储顶两次 16bit 存储，所以这个优化值得保留——前提是半字顺序不能反。
### 教训
位图写入类 bug 先看"错位的**单位**"（bit / 半字 / 字 / 行），基本就指向了原因；端序假设要写成注释钉在函数头上（现在是钉住的，`FinalDemo.c:355-357`）。
## 6. 读仲裁器 `cnt_s` 泄漏具有永久否决权
### 现象
第三次上板（17:06 日志）：`selfcheck: ... SCAN=00070108 ...`——高 16 位 = `dbg_abort = 7`（看门狗在自检阶段就已放弃过 7 行取数），紧接着 CPU 彻底死、画面停在最后一帧（§18.8）。
### 我最初以为的原因 / 走过的弯路
加了看门狗 + 排空 + 退避之后，我以为什么都解决了：`s_hold` 有上限了、硬放弃时也清了扫描输出自己的账本（`ar_idx/burst_done`）⇒ `s_hold` 会落下 ⇒ 通道会还。上板证据（`abort=7` 却仍然死）说明这个推理漏了一道闸门。
### 定位过程
`SCAN=00070108` 把"abort 已经发生"变成板上事实；接着**逐条核对归还条件需要哪些量**，发现通道归还要求 `cnt_s==0 && !s_arvalid && !s_hold` 三个条件，而上一版只关掉了 `s_hold` 这一道。用 `ARC_2DRA/rtl/video/tb/tb_rd_arb_leak.v` **精确模拟板级现场**：S 侧发一笔 AR、只收 2 拍就放下 `s_hold`（= 看门狗放弃本行），从机给 S 那笔**永不拉 rlast**；C 侧持续请求读、统计完成笔数。实跑日志 `log_tb_rd_arb_leak.txt`：

| 指标 | 修复后（`LEAK_TO=256`） | A/B（`-DLEAK_OFF`，等价无兜底） |
| --- | --- | --- |
| 仲裁器 `cnt_s`（内部） | **1**（泄漏确实存在、永不归零） | 1 |
| 仲裁器 `owner`（内部） | **1 → 0**（`leak_c=257` 触发兜底） | **永远停在 1** |
| C 侧完成突发 | **57,105 笔** | **0 笔（一拍都没收到）** |
| C 侧最长 AR 等待 | **263 拍** | — |
| 判决 | **ALL PASS** | **FAILED** |

TB 自己也踩过坑：`28'h010_0000` 是 **bit20** 而不是 bit24，导致从机把 S 那笔当 C 的回满并拉 rlast，泄漏复现不出来（第一版 A/B 两边都 PASS）。定位手段是给 `cnt_s`/`owner` 加**变化监视器**（`tb_rd_arb_leak.v:216-230`）。**"A/B 没差异"时不要改结论，要查激励是不是真的制造出了要测的场景。**
### 根因
链条完整闭合：① CPU 持续写 DDR ⇒ 扫描输出某行取数收不齐 120 拍；② 看门狗超时 → `S_DRAIN` → 硬放弃时**扫描输出清的是它自己的账本**（`ar_idx/burst_done=0` ⇒ `s_hold` 落下），可那笔突发的 AR 在仲裁器里**早已计入 `cnt_s`**，对应的 rlast **永远不会来**；③ 归还条件 `cnt_s==0 && !s_arvalid && !s_hold` ⇒ `cnt_s` 永不归零 ⇒ **被永久否决**；④ `owner` 永远停在 1（扫描输出）⇒ CPU 再也拿不到 DDR 读通道；⑤ 整个程序都在 DDR 里 ⇒ 取指都取不到 ⇒ 整机静止、串口再无输出，而扫描输出仍在正常扫描 ⇒ 屏幕停在最后一帧。
### 解决方法
`ARC_2DRA/rtl/video/axi_rd_arb.v` 新增 `LEAK_TO` 参数（默认 256 拍，`:22-25`、`:85-86`、`:185-192`）：

```verilog
wire s_quiet = !s_arvalid && !s_hold;      // s 侧自称"搬完了、也没有新 AR"
if (s_quiet && (cnt_s != 8'd0)) leak_c <= leak_c + 1; else leak_c <= 0;
if (s_quiet && ((cnt_s == 8'd0) || (leak_c >= LEAK_TO))) owner <= 1'b0;
```
### 原理分析
`s_hold` 的语义是"有一笔突发真在飞"（`fb_scanout.v:195`：`ar_idx != burst_done`）；它为假就代表**不可能再有属于 s 侧的 R 拍回来**（在飞突发的账本已被放弃逻辑清零）⇒ 此时换手不会错路。所以 `cnt_s` 只能当**优化**用、**不能具备否决权**。`LEAK_TO=256` 拍（2.5µs @100MHz）的取法：正常一笔突发收完只要几十~几百拍，而 `s_quiet` 为真时本就不该有在飞突发，256 拍足够区分"泄漏"与"正常"；CPU 每次泄漏事件的最坏锁定时间 = `LEAK_TO` ≈ 263 拍 ≈ **2.6µs**（有界、无害）。这也解释了上一版"看门狗已生效（`abort=7`）却仍然卡死"：看门狗只关了一道闸门。
### 教训
"归还/释放"类条件里的每一个量都要问：**它有没有独立的上限？**只修其中一个，剩下的照样能把系统锁死；A/B 两边都没差异时先验激励。
## 7. CPU 静默死亡：未对齐 32bit 存储（所有早期"冻屏"的真正根因）
### 现象
画面静止、串口再无输出。这个现象在早期版本里反复出现，先后被归因给看门狗、排空、退避、读仲裁器泄漏（第 2、6 章），但**每次修完都还能复现**。
### 我最初以为的原因 / 走过的弯路
这是最长的一段弯路，全发生在 RTL 侧：① 认为取数无界 ⇒ 加 `FETCH_TO`/`DRAIN_TO`/`S_BACKOFF`（第 2 章）；② 认为 `dbg_abort` 双驱动是问题 ⇒ `VDB-1000: net 'dbg_abort[15]' is constantly driven from multiple places`，改成单比特 toggle + 两级同步；③ 认为读仲裁器 `cnt_s` 泄漏是"整机卡死的真正根因" ⇒ 加 `LEAK_TO`（第 6 章）；④ 还试过"预热"绕过（`comptest.c:528-557`）。这四次改动**都是针对一个幻影**：它们在 RTL 里各自确实修掉了真 bug（第 2、6 章的修复都有效、都有 TB 守着），但**都不是**这个冻屏的原因——`comptest` 把 CPU 侧对齐问题修好之后，同样的"开机正常→跑一会儿静止"在没有再动 RTL 的情况下消失了。
### 定位过程
决定性的一步是**把"写哪里"从自变量里消掉**：早期版本让 CPU 直写正在显示的帧缓冲，于是所有人都在怀疑"DDR 写队列灌满 → 读延迟暴涨"；在 `comptest` 里改成 CPU 只写屏外缓冲（`comptest.c:210-221`）之后冻屏**依然出现** ⇒ 与写哪块缓冲无关，剩下的唯一自变量就是 **CPU 侧 32bit 访问落在奇数 x 上**。反证链：`scene_step()` 让 `x += vx`、`vx ∈ {±1,±2,±3}` ⇒ **x 会变成奇数**（`comptest.c:215-216`）；第一版 `cpu_fill32` 直接 `*(volatile uint32_t*)(base + y*1920 + x*2)` ⇒ 奇数 x 上就是**未对齐的 32bit 存储**；当年 `FBtest` 能跑是因为它用 **16bit** 存储 `FB16[...]`，任意 x 都安全（`comptest.c:219`）。为了让这个类别的错误"一上电就看得见"，加了开机 `aligncheck`：在奇数 x=33 处画 8 像素、偶数 x=32 处画 9 像素（奇数宽度），再逐点读回（`FinalDemo.c:554-562`）——**读不出来或值不对就说明有问题**。
### 根因
RISC-V（本 SoC：RV32IM + Zicsr）**不支持未对齐的内存访问**：对非 4 字节对齐地址执行 `sw`/`lw` 会触发 **load/store alignment 异常**，而 BSP 的默认 trap 处理是死循环（与更早那次"读未实现的 `mcycle` CSR 触发非法指令异常"完全同类，见 `doc/HDMI输出集成说明.md:253-277`）。于是 CPU 就地停死、屏幕保留最后一帧、串口再无输出——与"冻屏"逐条吻合。
### 解决方法
① **对齐安全的 `cpu_fill32`**（`FinalDemo.c:245-260`、`comptest2.c:229-244`、`comptest.c:222-237`）：奇数 x 用 16bit 收头/收尾，中间主体才用 32bit 批量写——`if (odd) { *p++ = color; rem--; }` / `for (i=0;i<(rem>>1);i++) q[i]=two;` / `if (rem & 1) p[rem-1]=color;`。② **删掉 `x & ~1` 这个补丁**：`comptest.c:330` 曾有 `b->x = (int16_t)(x & ~1);`，`comptest2.c:547-549` / `FinalDemo.c:457-459` 删掉并写明理由——强行取整成偶数会让 `vx=±1` 的方块**被取整卡住不动**，不动就永远不擦，ALPHA 场景会因为反复叠加而一路变暗。③ **开机 `aligncheck` 自检**（`FinalDemo.c:554-562`）。
### 原理分析
**CPU 语义**：RISC-V base ISA 允许实现选择是否支持非对齐访问，本 SoC 没有 misaligned 处理通路，硬件直接 raise exception；异常进了默认 trap（死循环）⇒ 现象是"静默停死"而不是"报错重启"。**为什么 16bit 收头/收尾就够**：像素是 16bit、行距 1920 字节（4 的倍数），所以每行起始地址的对齐只由 `x` 的奇偶决定——头部最多 1 个像素即可把指针推到 4 字节边界，尾部剩 0 或 1 个像素；32bit 主体写 `color | color<<16` 与两次 16bit 写在**小端**下等价。**代价**：奇数 x 时每行多 2 次 16bit 存储，相对 `w/2` 次 32bit 存储可忽略，而收益是"任意 x 都安全"——这才让 `scene_step` 可以老老实实 `x += vx`。**为什么误判了四轮**：死因与"读通道被扫描输出钉住"**表象相同、机制不同**（前者 CPU 自己触发异常，后者 CPU 取不到指），两者都会"屏幕停最后一帧、串口静默"——**现象相同不代表机制相同**。
### 教训
出现"静默停死"时第一件事是确认**是不是异常**（有没有 trap 输出、能否打印），而不是先怀疑总线仲裁；软件侧一行可疑的强制类型转换比 RTL 里十个计数器更值得先查。给每一类"静默失败"配一个**开机自检**，把"偶发冻屏"变成"上电第一秒就可见的失败"。
## 8. `SCR=0` / OSD 从未被搬上屏：硬件侧推指令的节奏错了
### 现象
硬件加速模式画面在动，但串口统计里的上屏帧率 `SCR` **恒为 0**，而且状态条（OSD）**从不刷新**。
### 我最初以为的原因 / 走过的弯路
先怀疑引擎没干活（读 `STATUS`/`COUNT`）、再怀疑帧计数变量没累加、又怀疑 COPY 指令发不出去——这些只是症状的不同侧面。
### 定位过程
把三个动作**放在同一处代码上读**就露馅了：上屏帧计数（`scr_frames++`）、场景推进、OSD 搬运，三者都挂在 `blt_idle()` 成立的时刻上（`comptest.c:611-615`、`:648-652`、`:674-677`）。判据：**画面在动**（说明引擎确实在执行指令）但 `SCR=0`（说明完成事件一次都没被观测到）——两者同时成立只能解释成"完成点被指令流淹没了"。
### 根因
硬件侧的下发策略与"完成"的定义冲突。`blt_idle()` 的判据是 `DONE && FIFO_EMPTY && !ERR`（`comptest.c:150-155`）；只要"FIFO 一有空间就补下一帧"，`FIFO_EMPTY` 就永远为假 ⇒ 引擎永远 BUSY ⇒ `blt_idle()` 永不为真 ⇒ 上屏帧计数、场景推进、OSD 搬运三件事全部不发生。
### 解决方法
改成**按帧节流**：推满一帧就停手，等引擎真空后再推进（`comptest.c:654-698`）。新增 `hw_frame_pushed`：本帧 N 条块的指令全部下发后置 1 并 `break` 出下发循环（`:472`、`:692-694`）；主循环里 `if (hw_frame_pushed) { if (blt_idle()) {...} }`，在这个**确定的空闲点**上完成三个动作——`hw_frames++`、`scene_step()`、必要时 `blt_fill` 重铺 + `blt_copy_osd()` 搬状态条（`:660-678`）。`FinalDemo.c:668-709` 沿用同一结构（`:669`、`:707`）。下发前一律先查空间：`blt_can_push()` 要求 `cnt <= BLT_FIFO_DEPTH - HW_FIFO_MARGIN - 1`（`HW_FIFO_MARGIN=56`，`FinalDemo.c:173-178`）——**FIFO 满时写 DATA 会把 CPU 挂在 APB 上**，主循环会死在那里。
### 原理分析
**"完成"是一个需要在指令流里留出空隙才能被观测的事件**：引擎的 DONE / `BUSY=0` 是电平信号，只在下发指针追上执行指针时出现；主机若持续灌指令，这个空隙在时间上不存在，软件永远看不到。**一帧在飞**同时是"帧率统计口径正确"的前提：SC/R 计数、场景推进、OSD 刷新都要绑在帧边界上，否则统计的是"下发速度"而不是"渲染速度"。APB 写 FIFO 满会反压 CPU（`blt_can_push` 就是为此存在），这类"满时写会挂住总线"的接口必须由**软件**做流控。
### 教训
"状态没更新"不一定是状态机坏了，很可能是**没有给它被观测的机会**——先看生产者/消费者的节奏关系再看逻辑；任何"能推就推 + 轮询完成位"的组合都要检查完成条件里有没有一个"需要空隙"的项（FIFO 空、总线空闲）。
## 9. 改 N / 切模式后屏上留下旧方块
### 现象
按 `n` 加/减方块数、或切换渲染路径之后，屏上**残留旧方块**；它们不会自己消失，要等某个新方块碰巧路过把它们盖住才刷新。
### 我最初以为的原因 / 走过的弯路
先怀疑擦除逻辑（`dx/dy` 记账不对、擦错位置），围着单块的擦/画绕了很久。真正漏掉的是**"谁来擦那些已经不在名单里的方块"**：`n` 变小之后，多出来的那些块的像素已经写进帧缓冲，但场景数组里已经没有它们的下标了。
### 定位过程
把"场景变了"当独立事件看：凡是"目标集合变化"的操作（`n` 改变、场景类型改变、路径改变、复位）都会让**帧缓冲里存在一批没有主人的像素**。判据很直接：不重铺时残影一直在，一重铺立刻干净。
### 根因
重铺（repaint）缺失。旧版本只在"方块移动"时擦旧位置，没有处理"场景/路径变化后整片区域的状态已经过期"这一情形（`comptest.c:474-478` 注释即此）。
### 解决方法
引入两侧各自的重铺标记，任何"场景/路径变化"都把它置 1，下一趟先把整片渲染区铺回背景色：

| 文件 | 位置 | 内容 |
| --- | --- | --- |
| `comptest.c` | `:474-478`、`:592`、`:598`、`:603`、`:607` | `repaint[2]` 与 `hw_repaint`；模式切换/加减 N/复位全部置 1 |
| `comptest.c` | `:623-631` | CPU 侧重铺：该缓冲场景区铺背景 + `scene_sync()` 让 `px=py` 重新对齐 |
| `comptest.c` | `:666-673` | 硬件侧重铺：引擎整屏 `blt_fill` 背景，紧接着 COPY 把状态条补回（FIFO 保序） |
| `comptest2.c` / `FinalDemo.c` | `:587`、`:643-647`、`:711-715` / `:527`、`:584-589`、`:613-617` | `repaint_hw` / `repaint_cpu` 两个标记 |
| `FinalDemo.c` | `:718-721` | `if (repaint_cpu) { cpu_fill32(FB_BACK, 0, cpu_y0(path), FB_WIDTH, cpu_h(path), COL_BG); repaint_cpu = 0; }` |

顺带修掉一个同源问题：场景虚拟区域高度原来**固定成 `HALF_H`**，所以即使单模式给了整屏高度，物块也只在上面 260 行里弹——就是"切到纯 CPU/纯硬件时仍只渲染一半"的原因；新增 `vrg_h(path)`（`FinalDemo.c:480-483`、`comptest2.c:563-566`）让它跟着路径变。
### 原理分析
**增量渲染的不变量**：`dx/dy` 记账只在"上一趟画过、这一趟仍在名单里"的前提下成立；`n` 变化、场景/路径切换会破坏这个前提 ⇒ 必须有一个**全量重铺**入口把它拉回已知状态。**硬件侧重铺要成对**：整屏 `blt_fill` 会连状态条一起盖掉，必须紧跟一条 COPY（或重画状态条），且依赖命令 FIFO 的**保序**特性（`blt_emit` 逐字写 `BLT_CMD_FIFO_DATA`，`FinalDemo.c:153-164`）。**重铺的位置选择**：`FinalDemo` 把信息条放在 y=0..16（`OSD_H=16`），硬件区从 `TOP_Y0=16` 开始、CPU 区从 `cpu_y0()`=16/280 开始 ⇒ **每趟区域重铺不会碰到信息条**，字可以常驻（`FinalDemo.c:7-13`、`:740-742`）。
### 教训
增量渲染必须明确定义**失效（invalidate）入口**——任何改变"目标集合"的操作都要走它；全量重铺与增量绘制混用时注意它会不会顺手擦掉不该擦的东西（这里是状态条）。
## 10. 运动尾迹（以及一次失败的"两阶段"重写）
### 现象
方块运动路径上拖出一串残影，**越慢的一侧（帧率越低的一侧）越稠密**；ALPHA 场景下还表现为"方块不动时逐帧变暗、场景步进时亮度恢复"的 25Hz 周期性忽明忽暗。
### 我最初以为的原因 / 走过的弯路
① 认为是擦除顺序问题（先擦后画 vs 先画后擦）与重叠处闪烁 ⇒ 把硬件侧改成**两阶段："先擦完 N 块，再统一画 N 块"**。结果**引入了尾迹，而且闪烁也没修好**，只能退回"相邻式擦+画"（`comptest2.c:764-768` 完整记了这次失败）。② 认为是"方块没动就不擦"造成的（`if (b->dx != b->tx || b->dy != b->ty)` 才擦）⇒ 对 FILL/KEY 安全（幂等），但 **ALPHA 不擦就会再混一次、一次比一次暗**。
### 定位过程
"越慢的一侧越稠密"这个**不对称性**是决定性线索：两侧代码对称、只有帧率不同 ⇒ 说明位置在**一趟渲染中间**发生了变化（慢的一侧一趟跨了更多场景步进）。于是把"一趟开始时给场景拍快照"当假设去验证：一拍快照，残影立刻消失。
### 根因
两个独立原因。① **记账时刻错误**：早期实现在一趟**结束时**把当前位置记为 `dx/dy`，而绘制用的是**趟内实时读取**的位置；一趟内位置若变化，同一趟里有的块用旧位置、有的用新位置 ⇒ `dx/dy` 记账不再自洽 ⇒ 有位置被画过却再没人擦 ⇒ 沿路径一串残影（`FinalDemo.c:126-130`）。② **两阶段重写放大了瞬态窗口**：把"已擦未画"的窗口从相邻式的一个块拉长到 N 个块（10ms 量级），而屏幕每 16.7ms 采一次样 ⇒ 更容易被拍到（`comptest2.c:726-730`）。
### 解决方法
① **每趟场景快照 `scene_snap()`**：一趟开始时把 `x,y` 冻结到 `tx,ty`，此后本趟内所有擦/画都用 `tx,ty`；场景本身仍在后台被推进，只是要等下一趟才生效（`FinalDemo.c:438-442`、`comptest2.c:421-425`；调用点 `FinalDemo.c:632-633`、`:674`、`:736`）。② **回到相邻式擦+画**，位置一律用本趟快照，画完后把 `dx/dy = tx/ty` 记账（`FinalDemo.c:694-706`）。③ **双缓冲**：把重叠/擦除这些中间态关在后台缓冲里，屏幕只看到整帧 COPY（`FinalDemo.c:186-191`、`:642-661`）。④ **ALPHA 必须每次都擦**（或整片重铺），FILL/KEY 可以"没动就不擦"（`FinalDemo.c:685-693`、`comptest2.c:788-796`）。
### 原理分析
**快照 = 把"动画时间"与"渲染时间"解耦**：没有快照时渲染一趟的时长会泄漏进画面内容，帧率越低泄漏越多——这正好解释了"越慢的一侧尾迹越稠密"。**幂等性分类**是决定"能不能省擦除"的依据：FILL 与 KEY 对同一 dst 重复执行结果不变（幂等）；ALPHA 是 `dest = blend(src, dest)`，每次都改 dest ⇒ 不擦就累积变暗，而周期性忽明忽暗的 25Hz 正好等于 `SCENE_TICKS` 的步进频率（`FinalDemo.c:472`：`BSP_CLINT_HZ/25` = 40ms）。**双缓冲把"瞬态窗口"变成不可观测**：屏幕只在帧边界采样后台缓冲的完整结果，中间态多长都不影响观感——比"缩短窗口"更彻底。
### 教训
动画类 bug 先看**不对称性**（哪一侧更严重），不对称往往直接指向"时间/速率相关的量"；修 A 引入 B 时先退回已知状态再找真正原因——那次两阶段重写同时"没修好闪烁 + 引入尾迹"，说明它对闪烁的因果判断本身就是错的。
## 11. 重叠处上下关系高频切换（z 序乱跳）—— 最长的一次调查
### 现象
驱动背靠背下发多条**写重叠区域**的指令时，重叠处 z 序高频闪/换（"层级被换掉"）；**纯 CPU 渲染没有这个现象**。此外还有两个形态不同的残影问题（见"根因"第 4、5 条）。
### 我最初以为的原因 / 走过的弯路（按顺序）
① **WAW 写提交乱序假设**：认为两条指令的写突发同时在飞、DRAM 层面把提交顺序打乱。先加软件侧**逐块围栏 `f`**（每块之间等引擎 IDLE）——症状**完全消失**但帧率被拖死；再加**预拷等待 `g`**（推 COPY 前干等 300µs）——**没有效果**；再加**冻结 `m`**（暂停运动）用来排除"是不是撕裂/帧间内容差异"。② **像素回读诊断 `d` + 周期扫描**：串口 `d` 手动 dump 第一对重叠方块在 `FB_BACK`/`FB_BASE` 的值并统计两缓冲不一致像素数（`comptest2.c:655-692`）；自动诊断 `dbg_quick()`（每 2×2 抽样，`:430-464`）与 `osd_fill()`（1/16 抽样，`:488-534`）在 `backup/comptest2_osd_diag_20260912.c:731-733` 里是**周期性**跑的（`disp_frames % 32` / `% 4`），每帧要读回几万个 DDR 像素、走的是与引擎/扫描共享的读通路，实测把 `HW=` 明显压低 ⇒ 变成第 12 章那个性能回退问题。③ **RTL "根修"**：在 `rtl/axi_wr_master.v` 加 `b_pending`（AW 受理 +1 / B −1）与 `wr_idle_committed`，在 `rtl/blt_top.v` 合成 `wr_commit_idle`，接到 `rtl/blt_engine_fsm.v` 的 `done_out` 与 `ST_WDWAIT` 出口——**在仿真里验证通过**，并顺带抓到"根因"第 2 条那个真 bug。
### 定位过程
**(a) 仿真先否定了最初的 WAW 假设。** 新 TB `rtl/tb/tb_wr_order.v`（配新的可乱序提交从机模型 `rtl/tb/axi_slave_mem_ord.v`：AW/W 进深写缓冲、按各自 `ctime` 提交、**B 在真正提交那一拍才回**、读只能看见已提交数据）测出：整场仿真里写突发**在飞峰值 = 1**，RTL 的 `b_pending` 与 TB 在 AXI 引脚上数的 AW−B **完全一致**（`tb_wr_order.v:438-442`），而且 T3（两条重叠 FILL、提交延迟随机、WAW 守卫）**在屏障 OFF 时也 PASS**（`log_tb_wr_order_off.txt`）⇒ **写通道本来就是程序序，WAW 重排在这份 RTL 里不可能发生**。代码层结构性证据（§19.1）：写主机是 `S_AW→S_W→S_B→S_IDLE` 串行（`rtl/axi_wr_master.v:96-136`）、`wd_busy=(st!=S_IDLE)`（`:67`）、`m_axi_awvalid=(st==S_AW)`（`:145`）⇒ **同一时刻最多一笔写突发在飞**；写仲裁器是纯组合直通（无 skid、无 FIFO），只在 `cnt_b==0 && !b_wvalid` 时换 owner。

**(b) 但 TB 抓到了一个真的"假完成"。** `tb_wr_order` 的 H1 项统计"引擎报 IDLE 那一拍写通路是否干净"：

| 判据 | 屏障 ON（默认） | 屏障 OFF（旧行为） |
| --- | --- | --- |
| H1 完成事件总数 / 其中"写通路未清" | 117 / **0** | 117 / **55**（`wd_occ=1 wr_st=0 未回B=0`） |
| T1（IDLE 当拍读 mem 应已是本条颜色） | PASS | **FAIL**（读到旧值 `1111`） |
| T2（FILL→COPY，读刚写的字） | PASS | **FAIL**（COPY 到 `0000`） |
| T2b（FILL→ALPHA(α=0)，读刚写的 dst） | PASS | **FAIL**（读到旧 dst `4444`） |
| T3（重叠 FILL 的 WAW） | PASS | PASS（证明问题不在 WAW） |
| H2 写突发在飞峰值 | 1 | 1 |

（`log_tb_wr_order.txt` / `log_tb_wr_order_off.txt`；`-DBLT_WR_ORDER_OFF` 是 `run_regress.ps1:30` 的 A/B 对照项，按"必须失败"判定，见 `final_regress.txt` 的 `tb_wr_order_off A/B OK`。）

**(c) 决定性的一步来自板上对照。** **纯硬件模式（`h`）完全不出现 z 序乱跳** 【据观察记录】⇒ 这个现象只属于 SPLIT 模式；SPLIT 的结构特点是**两个主机（引擎 + CPU）写同一块后台缓冲**，而且"发布"被**更慢的 CPU 侧**用 `hw_done/cpu_done` 门控（`FinalDemo.c:655`、`comptest2.c:744`）——纯硬件模式两个条件都不满足。

**(d) 剩下两条残影追下去发现是擦除策略而不是顺序。** 只擦方块的**旧矩形**有两个后果【据观察记录】：(i) 会咬到**本趟已经画好的邻居**——场景 1 里表现为一条 2~3px 宽、背景色的拖尾，宽度正好等于每次步进的位移；(ii) **不会刷新新位置的前沿带**——KEY 场景里色键（洋红）的透明四角会露出上一帧的旧像素并闪烁（场景 3）。判定证据：`m` 冻结时**根本没有擦除动作**、什么都不闪；`f` 打开**什么都不改变**；残影与 `N` 无关。
### 根因
按确认顺序：① **"完成"判据是假的（真 bug，已被 RTL 修复）**：引擎 `ST_WDWAIT` 的出口是 `wd_empty && !wd_busy`，而 `sync_fifo.empty = !out_v`（**同步读 + 输出寄存器**，`rtl/sync_fifo.v:41-56`），最后一个写词推进 FIFO 后要 **2~3 拍**才在 `out_v` 上可见——这段窗口里 `empty=1`（**假空**）。逐拍时间线（§19.2）：

| 拍 | `sync_fifo` 内部 | `empty=!out_v` | 引擎 | 写主机 |
| --- | --- | --- | --- | --- |
| T | `do_wr`：`mem[wptr]<=data` | 1（还是"空"） | 最后一拍 EXEC | S_IDLE |
| T+1 | `mcnt=1` → 发起 BRAM 读 | 1（**假空**） | `RS_DRAIN` | S_IDLE |
| T+2 | `rd_pend=1`，数据在飞 | 1（**假空**） | `ST_WDWAIT` 采样 → 条件成立 | S_IDLE |
| T+3 | `take` → `out_v=1` | **0**（这一刻才可见） | **st→IDLE、BUSY=0** | 下一拍才 pop |
| T+4..T+6 | — | 0 | 下一条指令开始取数 | `S_BUF→S_AW→S_W` 才发出去 |
| T+7+B | — | 0 | — | 收到 B（`b_pending` 才回 0） |

⇒ **`BUSY=0` 比"这个词被 AXI 受理"早 3~4 拍，比"内存系统受理（B）"早了一次写往返**；软件按 `BUSY` 判完成 ⇒ 下一条指令的 dst/src 读会抢在前面（**RAW 危险**）⇒ ALPHA 混到旧背景、KEY 的键比较用到旧值 ⇒ 重叠处看起来"层级闪/换"（`rtl/blt_engine_fsm.v:187-194`、`:369-373`；`rtl/blt_top.v:162-179`）。② **WAW 提交乱序在本设计中不可能**（被同一个 TB 证伪）。③ **SPLIT 模式的两个写者 + 发布被慢侧门控**是 z 序乱跳的放大器。④ **只擦旧矩形会咬到邻居**（背景色拖尾，宽度 = 每步位移）。⑤ **只擦旧矩形不刷新新位置前沿带**（KEY 场景四角闪烁）。
### 解决方法
**① RTL：指令边界写屏障（`b_pending` + wd FIFO 真空）**

| --- | --- | --- |
| `rtl/axi_wr_master.v` | 头部注释 `:9-15`、端口 `:30-32`、逻辑 `:69-86` | `aw_hs` +1、`b_hs` −1（带 0 保护，防 B 错路时回绕成 31）；`wr_idle_committed = (b_pending_r==0) && (st==S_IDLE)` |
| `rtl/blt_top.v` | `:86-88`、`:159`、`:162-179` | `u_wd_fifo .count(wd_count)`；`wr_commit_idle = wr_idle_committed && (wd_count==5'd0) && !wd_busy`；`ifdef BLT_WR_ORDER_OFF` 时强行置 1（= 旧行为） |

吞吐代价（T4a~d，实测）：

| 用例 | 屏障 ON | 屏障 OFF | 差 |
| --- | --- | --- | --- |
| 16×FILL 32×32，写回延迟 2 拍 | 1335 周期/条 | 1333 | **+2** |
| 16×FILL 32×32，写回延迟 128 拍 | 20776 | 20776 | **0**（写通路本来就饱和） |

| 同 T4c，B=32 | 69 | 31 | **+38 ≈ 一次 B 往返** |

结论：代价 = **命令尾部一次写往返**；指令内部的写突发仍与行计算重叠（T4a 只 +2、T4b +0 就是证据），**没有把像素串行化**。

**② 软件：`e` 模式 = 每趟整片重铺 + 不发任何逐块擦除**（`FinalDemo.c:663-667`、`:676-679`；`comptest2.c:769-813`）。这个过程本身有一个值得记的弯路：**`e` 的第一版只是"加了整片清屏"，却仍然保留那些破坏性的逐块擦除** ⇒ 看起来毫无用处；能用的版本是**同时把逐块擦除也去掉**的那个版本（`FinalDemo.c:663-667` 注释即此）。CPU 侧语义**故意保持 comptest2 的"先擦后画"不动**（`FinalDemo.c:712-714`），这样 CPU-vs-HW 的帧率对比才是诚实的。
### 原理分析
**B 是 AXI 上唯一可用的写排序原语**：AW/W 只表示"主机发出"，只有 B 才表示"内存系统已受理这一笔"；因此"命令 k+1 的读不得早于命令 k 的写被受理"只能靠 `b_pending==0` 表达。`wd_count==0` 补上的是"最后一个词已经离开 FIFO"，`!wd_busy` 补上的是"突发已收完"——三者缺一，`BUSY=0` 就还是假的。**`sync_fifo.empty = !out_v` 的语义**：这是一个"读延迟可见"的标志，表达"输出寄存器里现在没有数据"，**不是**"FIFO 里没有数据"；真实占用是 `count = mcnt + rd_pend + out_v`（`rtl/sync_fifo.v:49-52`）——任何用 `empty` 判"下游可以收工"的地方都要重审。**`b_pending` 的 0 保护**：正常情况下每个 B 对应一笔已受理 AW，但历史上 `axi_wr_arb` 出过 B 错路（§12.1），所以 0 保护必要——否则计数回绕成 31，完成判据会被永久卡死（比原来的假完成更糟）。**为什么"整片重铺 + 不擦"能同时消掉两种残影**：不再有逐块擦除 ⇒ 不会咬到本趟已画好的邻居；整片清屏覆盖了**每一个**上一帧留下的像素 ⇒ 新位置前沿带也是干净的，透明四角不会露出旧像素；代价是每趟多一次整片 FILL 的写带宽，但这是**有界、可预测**的每帧固定预算。**单写者/原子呈现**：只有整帧 COPY 写显示缓冲（`FinalDemo.c:186-191`、`:642-661`），所以中间过程永远不会被屏幕看到。
### 教训
**"完成"的定义要落在最下游的确认上**（这里是 B），不能用上游"看起来空了"的代理标志——代理标志一旦有流水线延迟，"完成"就是假的，而且只在背靠背调用时暴露。**A/B 没有差异也是结论**：`tb_wr_order` 用同一套 TB 同时"证实了假完成"和"证伪了 WAW"，后者的价值不比前者低——它把一个方向永久排除掉了。**板级对照比仿真更快定性**：`h` 模式不出现 z 序乱跳这一条观测，一次性把"顺序问题"与"模式结构问题"分开了。
## 12. 性能回退：OSD / 像素扫描诊断把帧率吃掉了
### 现象
加了"周期性像素扫描"之后 `HW=` 帧率明显下降，关掉扫描立刻回升。`comptest2.c:735-737` 的注释即此："它们每帧要读回几万个 DDR 像素（1/4 与 1/16 抽样），走的是与引擎/扫描共享的读通路，实测会把 `HW=` 明显压低"。
### 我最初以为的原因 / 走过的弯路
一开始把扫描当"只读、不影响渲染"，所以让它常开，甚至每 4 帧就刷一次屏上读数（`backup/comptest2_osd_diag_20260912.c:731-733`）。这是典型的"测量装置改变了被测对象"。
### 定位过程
把扫描关掉、其余不动，帧率立刻恢复 ⇒ 因果确立。按抽样密度与调用节奏算回读量（以 `path==99` 分支的 `hw_h(99) = FB_HEIGHT - TOP_Y0 = 524` 行为准，`FinalDemo.c:476-479`）：

| 函数 | 抽样 | 采样点/次 | 每次读（两缓冲各一次） | 调用节奏 |
| --- | --- | --- | --- | --- |
| `dbg_quick()`（1/4 抽样） | `yy+=2, xx+=2` | `(524/2)×(960/2) = 262×480 = 125,760` | 251,520 | 每 32 帧 |
| `osd_fill()`（1/16 抽样） | `yy+=4, xx+=4` | `(524/4)×(960/4) = 131×240 = 31,440` | 62,880 | 每 4 帧 |

⇒ 每 32 帧合计 `251,520 + 8×62,880 = 754,560` 次读 ⇒ **平均 ≈ 23,580 次/帧**，与工作记录里的"约 23,600 次"吻合；SPLIT 模式（`hw_h = HALF_H = 260`）约 **11,700 次/帧**。代价 **2.4–4.7 ms/帧** **【据观察记录】**（帧时间与 D$ 命中率强相关，仓库里未留下这项测量日志）。
### 根因
诊断代码走的是**与引擎/扫描输出共享的 DDR 读通路**（两级 `axi_rd_arb`）。每帧几万次 16bit 读在缓存上是流式访问（几乎全部 miss），既占读带宽又拉长 DDR 里排队的引擎突发 ⇒ 引擎与扫描输出都变慢。即：**测量通道与被测对象共用一条资源**。
### 解决方法
把周期扫描**停用**，只保留手动触发（`comptest2.c:735-742`）：

```c
/* ★ 周期诊断已停用：它们每帧要读回几万个 DDR 像素（1/4 与 1/16 抽样），
 *   走的是与引擎/扫描共享的读通路，实测会把 HW= 明显压低。
 *   需要时发串口 'd' 手动触发一次即可（或让 path==99 走进下面分支）。 */
if (path == 99) { dbg_quick(...); osd_fill(...); }
```

最终版 `FinalDemo.c` 把 `dbg_quick` / `osd_fill` **彻底删除**（`FinalDemo.c:4-5` 文件头注释），信息栏刷新改成"≥16 个已发布帧 且 ≥300ms"且**只写 960×16 黑底 + 两串 8×8 点阵**（`FinalDemo.c:89-91`、`:747-752`）——**不含任何逐像素 DDR 扫描**；串口侧保留 `'d'` 手动 dump（`comptest2.c:655-692`）。
### 原理分析
**读带宽是共享资源**：`axi_rd_arb` 只有一条通往 DDR 的读通道，扫描输出的行取数有**硬死线**（一行 1481 拍 @core100MHz），诊断读没有死线却会插进同一个仲裁队列 ⇒ 受害的是有死线的那一方。**缓存的放大效应**：1/4 抽样的跨距是 8 字节、行跨距 1920 字节，等于把整个 1MB 帧缓冲"扫"一遍，D$ 几乎不命中；每次 miss 还按行填充（实际 DRAM 流量大于 2 字节/次），所以"只读几万次 16bit"在 DDR 上远不是几万次访问那么便宜。**正确做法**：诊断要可关闭、手动触发，或者在硬件里做——本工程现成有硬件计数器：寄存器 0x20 的 `dbg_underrun`/`dbg_abort`（`rtl/blt_regs_axi_lite.v:265`、`rtl/blt_top.v:59-62`）。**用硬件计数器替代软件扫描**是这类问题的通用出路。
### 教训
**测量装置会改变被测对象**：任何周期性诊断都要先做"开/关 A/B 测帧率"，再做功能判断；优先用硬件计数器观测硬件状态，别用软件扫描。
## 13. 显示通路与帧时间：一帧 16.7ms，整屏 COPY 就要 19ms
### 现象
CPU 模式下"画完再搬"时帧率被压到 30 多 fps，掩盖了真实的渲染差异；屏幕上看到的内容总是"混合"的。
### 我最初以为的原因 / 走过的弯路
先认为 CPU 渲染太慢，实际是**搬运本身**就超过了场周期。也试过用"冻结场景（`m`）"判断显示通路在不在因果链里（冻结时内容不变，若还闪就说明是显示侧）**【据观察记录】**。
### 定位过程
直接量：整屏 COPY 实测 ≈ **1,889,194 核心周期**（§15.5，v2.5 修复后 1,917,926，+1.5%）。
### 根因
**整屏 COPY 的时长超过一个 60Hz 场**：整屏 COPY 960×540 ≈ 1.89M core 周期 ≈ **19 ms** @100MHz（§15.5、`功能清单.md:1564`），而 60Hz 场周期是 **16.7 ms** ⇒ COPY 上限 ≈ **53 fps**（§18.5）。所以单缓冲串行"画完再搬"时，屏幕每 16.7ms 采一次样而一次搬运要 19ms ⇒ 显示内容必然是两帧的混合，帧率也被 COPY 压到 30 多 fps。
### 解决方法
**软件侧（已实施）**：**双缓冲**：`FB_BACK`（后台，CPU 与引擎都画这里）→ 整帧 COPY → `FB_BASE`（显示）（`FinalDemo.c:49-50`、`:186-191`、`:642-661`），只有这一处写显示缓冲；**统计口径分开报**，保证对比干净——`HW=`/`CPU=` 是**纯渲染**完成帧率（不含 COPY 等待），`SCR` 是**实际上屏**帧率（`功能清单.md:1559-1562`）；双缓冲让 COPY 与渲染重叠后，CPU 侧报出的就是它自己的渲染速度。

**RTL 侧（尚未实施）**：要做到真正的原子呈现还需要两件事，**目前都还没做**：① **扫描输出基址寄存器**——现在显示基址是**参数**不是寄存器（`fb_scanout.v:27` 的 `parameter [31:0] FB_BASE`，顶层硬编码 `32'h0030_1000`，`ddr3_example_top.v:724`），没有它就无法做"翻页（buffer flip）"；② **场/帧计数器（vblank 或帧号）可读**——`fb_scanout` 有 `frame_tick` 输出（`fb_scanout.v:104`），但顶层**悬空未接**（`ddr3_example_top.v:755`），也没有对应的只读寄存器（`blt_regs_axi_lite.v` 只到 0x20：`0x18 DBG_CUR_CMD`、`0x1C PERF`、`0x20 SCAN_DBG`）。
### 原理分析
游戏渲染需要三条性质：① **单写者**——显示缓冲只由一个主体写（这里是引擎的整帧 COPY），否则"擦除/重画/重叠"的中间态会被屏幕看到；② **原子呈现**——切换必须发生在场边界，正确做法是把"显示基址"做成寄存器并在**帧开始（vblank/帧首）**那一刻锁存新值 ⇒ 一帧之内扫描输出读的始终是同一块缓冲；③ **固定的每帧命令预算**——19ms > 16.7ms 是硬约束，靠"搬得更快"解决不了，只能靠"不要每帧搬整屏"或"搬到看不见的地方去"解决。**双缓冲与翻页的区别**：双缓冲仍然要搬整屏（19ms 的 COPY 只是被藏到后台去了），翻页只改一个寄存器（0 搬运）——上面缺的两件 RTL 改动正是为翻页准备的。**为什么不能直接读 `frame_tick`**：它是 pclk 域的单拍脉冲，跨到 core/CPU 域必须变成可读的计数器或 toggle + 边沿检测，否则软件无法稳定采样。
### 教训
帧预算要先算：**任何单帧固定开销超过场周期，就必须改成异步/翻页**，否则"混合帧"是数学上必然的结果。"软件已经能跑"不等于"机制已经对"：双缓冲掩盖了 19ms 的搬运，但 19ms 仍在每帧预算里。缺失的能力要写成清单（这里就是"基址寄存器 + 场计数寄存器"两条），而不是含糊地记成"显示还可以优化"。

### 现象 / 目标

**⑥ `cache_evict()`**：CPU 写完 DDR 后、引擎紧接着要读的场合调用（`FinalDemo.c:144-150`），本质是 store 有序屏障（D$ 是写穿），保证 CPU 的像素对引擎可见（`:656`、`:777`）。
### 原理分析
**口径诚实性是有代价的**：为了"CPU-vs-HW 帧率对比干净"，CPU 侧**故意保留** comptest2 的"先擦后画 + 逐块擦旧矩形"语义、不跟随 `clear_pp`（`FinalDemo.c:712-714`）——硬件侧用 `e` 模式省掉的擦除，CPU 侧一次都没省，否则对比就变成"两种不同工作量的对比"。**同一场景、同一颗种子**：两侧用同一 `seed` 初始化同一套推进规则 ⇒ 目标坐标逐位相同，差异只体现在"谁跟得上"（`:410-433`、`:465-469`）。**固定宽度数字**：`appn()` 把 fps 补 3 位、N 补 4 位、SC 补 1 位、A 补 3 位（`:380-387`、`:493-505`），配合"整条先铺黑再重画"⇒ 数值变短时不会把上一次的长数字留在右边（`:486-489`），屏上无残字、无闪烁。**`t` 模式为什么需要 `pend_adv`**："发布一帧"与"渲染一趟结束"不在同一时刻（发布由整帧 COPY 完成触发，下一趟渲染有自己的收尾点），所以必须攒一步、在收尾点结算，否则会在同一趟里推进多次（`:642-654` 注释即此）。
### 教训
**子代理的"已验证"必须回读文件核对**——关键产物（标签、寄存器、打印串）要逐行确认存在。**UTF-8/LF 源码只走编辑器工具**：不做 PowerShell 文本往返、不用 `-replace` 替换源码（`$1` 会被当反向引用）——这类损坏是"改一处、坏一片"的隐形伤害。
## 15. GameDemo（高负载互动弹幕游戏）：没有板子时怎么找出四个真缺陷
### 目标 / 背景
赛题【高阶挑战 3】要一个"同屏元素数量极高、靠硬件 Alpha+ColorKey、冲 60FPS 极限"的互动游戏，
而且**输入不许用板载按键**（要 PC 键盘经串口）。本轮工作区**没有板子**，
所以先做了一件以前没做过的事：**把 GameDemo.c 原样 `#include` 进一个仿真宿主，
只覆盖三个基址，用假引擎/假时钟/假场边界在 QEMU 上把真主循环跑起来**
（`tools/host_selfcheck_game/`）。下面四个缺陷全是它抓出来的 —— 光靠读代码一个也发现不了。
### 缺陷 1：精灵飞出游戏区 ⇒ 目的地址算出界外（**最严重，会踩别的缓冲区**）
**现象**：弹幕会飞出游戏区，而目的地址算的是 `FB + y*FB_STRIDE + x*2`。
`dl_sprite()` 用的是 `PX(cx) - sz/2`，`int16` 的负数一旦被转成 `uint32` 参与乘加，
这个偏移会变成一个巨大的数 ⇒ **写到帧缓冲之外的 DDR**（踩别的缓冲区 / 画面整片花掉）。
**为什么读代码时容易漏**：FinalDemo/AdDemo 的方块**永远被钳在区内**（`scene_step` 负责钳位），
所以那两份代码里根本没有负坐标；弹幕游戏的"出界即回收"语义是新的，
"钳在区内"这条隐含前提被悄悄破坏掉了。
**解决方法**：`dl_sprite()` 进清单前**按游戏区裁成矩形**，并记下源偏移 `(sx,sy)`；
完全在区外的条目直接丢（`g_clip_drop` 计数）。`push_chunk()` 用
`src = ATLAS + off + sy*ss + sx*2` 与裁剪后的 `w/h` 下发；CPU 参考路径同口径。
顺带把屏幕骨架也保护住了：`y` 一律裁到 `PLAY_Y0=16` 以下，弹幕永远糊不到信息条上。
**守门人**：主机自检 D 组每一帧遍历整张绘制清单，断言
`x≥0 && y≥PLAY_Y0 && x+w≤960 && y+h≤540 && w,h>0` —— 600 帧 × 最多 2584 条，0 次越界。
### 缺陷 2：生成器跟不上 N —— 用户会误判成"加速器带不动"
**现象**：主机仿真里把 N 从 256 跳到 2400，**同屏元素数只到 345**。
**根因**：不是引擎，是**生成器**。老逻辑"每个生成节拍只补一架敌机"，
铺满 27 架要 7 秒，再等它们把弹幕铺开又要好几秒 ⇒ 用户按 `4` 之后要等半分钟才看见密集弹幕，
第一反应必然是"这加速器不行"。
**解决方法**：`ENEMY_MAX 16 → 24`（它才是"弹幕能不能被喂到 N"的天花板：
24 × 22 × 240 / 46 ≈ 2750 > N_MAX=2400）+ `ENEMY_SPAWN_T 22 → 16` +
**每拍补到 want**（`ENEMY_TOPUP=4`）+ 环弹发数也随 N 增长。
改完同一次仿真 `ON_max = 784`。
**守门人**：自检里那条 `D8 高负载：同屏元素数 > 600`。
### 缺陷 3：弹池满时的 O(N) 扫描，最坏比一帧预算还长
**现象**：`bul_alloc_enemy()` 是线性扫描。池满时**每一次发射**都要把 2400 个槽扫一遍；
一帧里最多有"敌机数 × 环弹数"= 24×24 = 576 次发射 ⇒ 最坏 138 万次循环 ≈ 3~4M 拍，
**比一帧预算（1.67M 拍）还长** ⇒ 表现就是"弹幕铺满的一瞬间掉帧"。
**为什么读代码时不显眼**：单次调用看起来只是个不到 2400 次的小循环，
"一帧会调用几百次"这件事要跨函数（`enemy_fire` → `bul_fire`）才看得出来。
**解决方法**：加 `g_bul_live` 计数 + `if (g_bul_live >= g_ncap) return -1;` 的 O(1) 快路径。
计数每帧在子弹循环里重算一次（那里本来就要遍历），帧内靠 `++` 记账；
子弹在别处被回收时计数会暂时偏大 —— 那只会让判断更保守，不会漏发。
### 缺陷 4：`DRAW_FILL_FULL` 的宽高放不进 `uint8`
**现象**：绘制清单条目设计成 `uint8_t w, h`，而整片重铺是 960×524 ⇒ 被截成 192×12。
**发现方式**：写 `draw_t` 定义时对着 `PLAY_W/PLAY_H` 的数值核了一遍，
意识到 960 > 255；主机自检里那条"整片重铺必须 x=0,y=PLAY_Y0"的断言是第二道保险。
**解决方法**：`DRAW_FILL_FULL` 的 w/h 在清单里存 0（哨兵），由 `push_chunk()` /
`cpu_render_frame()` 按常量 `PLAY_W/PLAY_H` 展开。
### 缺陷 5（小）：切渲染路径那一秒会读到"半个窗口"的假帧率
**现象**：`c` / `h` 切换后第一秒的 `ST fps=` 明显偏低（实测出现过 30），第二秒才恢复。
**根因**：1Hz 窗口的起点 `t_fps` 是 main 的**局部变量**，切路径时没法重置；
`g_hw_frames` 清零了，但窗口 `el` 还横跨着上一段 CPU 渲染的时间 ⇒ 算出来是半个窗口的帧率。
**解决方法**：把窗口起点提成全局 `g_t_fps`，`serial_cmd()` 在 `c`/`h` 里顺手重置它。
### 为可测试性做的一次重构：`serial_cmd()`
自检要实现"按键/命令真的驱动了固件"，最省事的写法是在测试里**另抄一份 `switch`** ——
但那样测的就不是固件了。所以把单字符命令的 `switch` 从 `serial_drain()` 里抽成
**独立函数 `serial_cmd(c)`**（固件里唯一一份实现），`serial_drain()` 只负责"协议分派"，
仿真宿主直接调 `serial_cmd()`。这是"为可测性重构"而不是"为测试加后门"。

### 原理分析
**没有板子时，唯一能拿到真证据的办法是把被测对象真的跑起来。**
本轮的做法（原样 `#include` 固件 + 只覆盖基址 + 假外设）之所以有效，靠的是三件事：
① 固件里所有硬件访问都收敛在 `blt_wr/blt_rd/cpu_fill32/cache_evict` 这几个薄封装上，
而三个**基址**是 `#ifndef` 可覆盖的 ⇒ 不用改一个字符就能把它搬进 RAM；
② 主循环的**所有等待都是有界且由 `tick32()` 驱动的** ⇒ 只要在 `clint_getTimeLow()` 里
推进虚拟时钟并刷新假寄存器，状态机就会自己往前走；
③ 收尾用 QEMU 的 SiFive test 设备自杀退出 ⇒ 不需要超时，一次跑完就是"没有死循环"的证明。
**假引擎的能力边界必须写清楚**：假引擎"瞬时完成"⇒ 仿真验的是**状态机与安全性**
（不越界、不卡死、协议解析、帧轮转、退化路径），**不是性能**。
极限 N 只能上板用 `g` 自动爬坡量 —— 这条写在 `doc/GameDemo_高负载互动弹幕游戏.md` §8.1 的口径里。

### 教训
① **"钳在区内"这类隐含前提，在换了游戏语义之后必须重新论证**——缺陷 1 就是这么来的；
② **"用户看到的现象"的第一嫌疑人应该是"内容生成"，而不是"渲染性能"**——缺陷 2 的 345 与引擎无关；
③ **复杂度要按"每帧调用次数"算，不是按单次调用算**——缺陷 3；
④ **测试的期望值也要有出处**，自检报红时先怀疑自检（本轮 5 次里有 5 次是自检错）；
⑤ **为可测性重构（把 `switch` 抽成函数）比在测试里复制逻辑更值**；
⑥ **"不许改 A、新建 B"这种要求要当成硬约束执行**：`game_console.html` 一字未改，
   增强版是副本 + 增量（见 §15 追加），改完用 `git`-less 的方式核对过字节数没变；
⑦ **已写进教训的坑照样会再踩**（`.ps1` 的 ASCII 问题本轮又踩一次）——所以教训要配**可执行的检查**，
   光靠"记住"不够。

## 贯穿全程的规则/教训

1. **先验证测量通道，再采信任何观察结果。** 串口方向、状态字段语义（`>>24` vs `>>16`）、printf 格式串（只认 `%c %s %d %X %x`，无 `%u`/宽度/`%%`、调试串用 ASCII）、`bsp_init()` 必须先调用——这些都算测量通道。通道坏了，**基于它得出的每一个结论都要作废重测**（第 1 章里 `f`/`g`/`m` 的结论就是这样作废的）。
2. **硬件/TB 证据优于推理。** `SCAN=00070108`（`abort=7`）比"看门狗已经修好了"的推理可信；`tb_rd_arb_leak` 的 `cnt_s=1 / owner 1→0 / 57105 vs 0` 比"归还条件应该成立"可信；`tb_wr_order` 的 `117/55 vs 117/0` 比"FIFO 空了就是完成了"可信。反过来，同一个 TB 也**证伪**了整整一个方向（WAW 重排）——这种"否定性证据"和阳性结果一样值钱。
3. **A/B 没有差异时先查激励，不要改结论。** `tb_rd_arb_leak` 第一版因为 `28'h010_0000` 是 bit20 而不是 bit24，A/B 两边都 PASS——问题在激励，不在被测对象；给内部状态加变化监视器是最便宜的定位手段。
4. **"完成/释放/归还"的每一个条件都要问：它有独立上限吗？** `S_FETCH` 唯一出口是"收满 120 拍"（无上限）→ 加 `FETCH_TO`；硬放弃后立刻重试（占用率 ~100%）→ 加 `BACKOFF_TO`；`cnt_s` 泄漏有永久否决权 → 加 `LEAK_TO`；`sync_fifo.empty` 的"假空"窗口 → 完成判据补上 `count==0` 与 `b_pending==0`。只修其中一个量，剩下的照样能把系统锁死（第 2、6、11 章各一次）。
5. **现象相同不代表机制相同；静默停死先查异常。** "屏幕停在最后一帧 + 串口静默"至少三种机制：CPU 触发对齐异常、取不到 DDR 读通道（整程序在 DDR 里 ⇒ 取指失败）、引擎 BUSY 不退——它们被误判了四轮（第 2、6、7 章）。软件侧一行可疑的强制类型转换比 RTL 里十个计数器更值得先查；同类更早一例是未实现的 `mcycle` CSR。
6. **每一类"静默失败"都要配一个开机自检。** `aligncheck`（奇数 x / 奇数宽度各一次）把"偶发冻屏"变成"上电第一秒可见的失败"；`selfcheck: STATUS/COUNT/SCAN` 一次打印三个关键状态；分阶段自检按**操作类别**拆分（PH0~PH3），不按时间点拆分。
7. **测量装置会改变被测对象。** 每帧几万次 DDR 像素回读（≈23,580 次/帧，算式见第 12 章）会吃掉读带宽、直接压低帧率。诊断要可关闭、手动触发；能用硬件计数器就别用软件扫描（现成有 0x20 `SCAN_DBG`：`dbg_underrun[15:0]` / `dbg_abort[31:16]`）。
8. **带宽与帧预算要在改之前算。** 放大放到扫描输出做（DDR 流量 62MB/s 不变），不要放大帧缓冲（124MB/s）；一帧只有 16.7ms 而整屏 COPY 要 19ms（1.89M 周期）⇒ 单帧固定开销超预算时，唯一出路是异步/翻页（基址寄存器 + 场计数寄存器，**目前尚未实现**）。
9. **动画与增量渲染先解决"时间基准"和"失效入口"。** 一趟渲染开始拍场景快照（`scene_snap`）把"动画时间"与"渲染时间"解耦，尾迹立刻消失；任何改变目标集合的操作（改 N / 切场景 / 切路径 / 复位）都必须走全量重铺入口（`repaint_*`），否则会留下没有主人的像素。
10. **UTF-8/LF 源码只走编辑器工具，不做 PowerShell 文本往返。** `Set-Content`/`Get-Content -Raw` 往返会把中文注释按 GBK 解坏并吞换行；`-replace` 里的 `$1` 会被当正则反向引用（曾把 `#define N_MAX 1000` 写成 `#define N_MAX$1700`）。这条同样适用于 RTL/TB 源码（`功能清单.md:1468-1469`，§17.8 的 TB 因此重写过一次）。
11. **子代理的"已验证"不能当证据。** 本轮就出现过"报告了已验证的右上角标签、文件里却根本没有"的情况；关键产物必须自己回读文件、逐行确认存在，再谈验证。
12. **测试用例的形状要覆盖真实使用。** 早期 6 个用例全是 8 像素宽（1 词/行），恰好绕过"多词/行"这条最容易错的路，直到 demo 里的 16×16 精灵（4 词/行）才暴露（§7.2）；同理 `tb_scanout_bw` 原来把 CPU 读通道一直拉成 idle，等于没测"CPU 也在猛读"这个场景（§14.2）。
