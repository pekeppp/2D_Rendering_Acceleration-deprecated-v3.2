## 0. 摘要

本作品在 RISC-V + FPGA 异构平台上实现了一款**自研的 2D 位块传输（BitBlt）硬件加速引擎**，
把"逐像素搬运"这件事从 CPU 手里彻底拿走：RISC-V 只负责高层逻辑与指令下发，
像素级的搬运、Alpha 混合、颜色键控抠图全部由 FPGA 硬件完成。

工程从 v1 迭代到 **v3.2**，中间经历了 **14 次板级问题定位与修复**（非对齐 lane、
指令 FIFO 满丢字、Alpha 定点抽头取错、写仲裁器 AW 握手漏计数、扫描输出饿死 CPU、
读仲裁 `cnt_s` 泄漏、引擎"假完成"导致的 z 序乱跳……），
每一步都留下了 testbench 与 A/B 对照，最终 **44 项 RTL 回归 0 失败**。

三项赛题高阶挑战全部落地：

| 挑战 | 实现 | 证据 |
| --- | --- | --- |
| **硬件 Alpha 混合** | `pixel_path.v` 用 DSP 做定点乘加，支持 alpha / 加算 / 乘法三种混合模式 + 逐像素 ARGB4444/1555 + 全局 alpha | `tb_attr_blend` 32 条判据（含 7 条手算期望值）全过 |
| **颜色键控去背** | 16bit 比较器，整词全键色不提交（省写）；另有 4×4 透明块掩码进一步跳过整块 | `tb_px_path` / `tb_dl_mask` 逐像素比对金标准 |
| **高负载互动游戏 Demo** | `GameDemo`：纵版弹幕游戏，同屏元素（弹+机+火花+星空）全部由引擎绘制；串口 `g` 自动爬坡量化 60FPS 下的同屏极限 | 主机全固件仿真 74 项 + 上位机协议 53 项，0 失败；**基础版已上板跑通** |

**关键性能（板测，v2.16 单 lane 口径）**：

| 精灵尺寸 | FILL | KEY（色键） | ALPHA（混合） |
| --- | --- | --- | --- |
| 16×16 | **514.3** 拍/精灵 | **719.1** | **856.4** |
| 32×32 | 1263.8 | 1617.4 | 1969.0 |
| 64×64 | 4450.0 | 5537.5 | 6742.7 |

拟合式 `每块 = A + B×像素`：FILL `252 + 1.025·px`、KEY `398 + 1.255·px`、ALPHA `464 + 1.533·px`。
60fps 帧预算 1,666,667 拍（core 100MHz）⇒ 16×16 ALPHA 理论 **1946 只/帧**，
取 70% 预算做安全余量 **1362 只/帧**【模型】。

**与纯 CPU 的差距**：同一场景、同一份图集，CPU 逐像素直写 vs 引擎 BitBlt，
同屏几百个精灵时帧率差 **1~2 个数量级**（`FinalDemo` 左右分屏实时对比，`HW=` / `CPU=` 两个数同屏显示）。

## 2. 赛题要求逐条对照

### 2.1 基础要求

#### 要求 1：硬件 2D 位块传输（BitBlt）引擎设计

| 赛题原文 | 本作品实现 | 证据 |
| --- | --- | --- |
| FPGA 端解析 RISC-V 发送的渲染指令（**操作类型、源地址、目的地址、宽度、高度**） | 每条形如 **8 个 32bit 字** 写 `CMD_FIFO_DATA(0x08)`：`op / src / dst / src_stride / dst_stride / {H,W} / alpha / color`。`op`：`0=COPY 1=FILL 2=ALPHA 3=KEY` | `rtl/cmd_fifo.v`、`rtl/blt_engine_fsm.v`；`tb_cmd_fifo`、`tb_blt_top` |
| 支持**图像块拷贝（Block Copy）** | `op=0`，源/目的各自带行距，支持任意地址、任意尺寸、非 16B 对齐 | `tb_blt_burst` / `tb_blt_unalign`（U1~U12，lane 0..7 全扫） |
| 支持**纯色填充（Solid Fill）** | `op=1`，`w7` 直接给 RGB565 填充色 | `tb_blt_top`、`tb_perf_probe` |
| 生成**标准 VGA/HDMI 时序**，输出到显示器（**≥640×480@60Hz**） | `fb_scanout.v` + `video_timing_1080p.v` 生成 CEA-861 **1920×1080** 时序（H 总 2200、V 总 1125）⇒ **实际 60.10Hz**，远高于 640×480@60Hz 的下限；帧缓冲 960×540 由扫描输出侧 `SCALE_SH` 放大到 1080p | `ARC_2DRA/rtl/video/video_timing_1080p.v`、`dvi_tx/`；`tb_fb_scanout`、`tb_scanout_scale` |

> **关于"最低分辨率"**：赛题下限是 640×480@60Hz。本作品用 **960×540 RGB565** 帧缓冲，
> 扫描输出到 **1080p@60.1Hz**。放大放在扫描输出侧（`SCALE_SH`），**DDR 带宽零增量**；
> 若把帧缓冲直接做成 1080p，DDR 流量会从 62MB/s 翻到 124MB/s —— 这是刻意避免的。

#### 要求 2：总线读写与存储器优化

| 赛题原文 | 本作品实现 | 证据 |
| --- | --- | --- |
| 加速器通过**系统总线**直接访问内存 | AXI4 主机读写（`axi_rd_master` / `axi_wr_master`），寄存器面走 **AXI-Lite**，板级经 `blt_apb_top.v` 挂在 APB 上（`0xF8100000`） | `rtl/blt_top.v`、`ARC_2DRA/rtl/blt/blt_apb_top.v` |
| 合理使用**突发传输（Burst Transfer）** | 内部按 **16B（128bit）一个词** 打包，`MAX_BURST=16` 的 AXI 突发；写主机做了**突发合并**（`burst_max` 从 1 提到 16，`burst_avg=16.0`） | `rtl/axi_wr_master.v`；`tb_perf_probe` 探针输出 `burst_max=16 burst_avg=16.0` |
| 使用**内部 FIFO 缓存**提高带宽利用率 | ① 256 条指令 FIFO（BRAM 可推断，见 §10 资源修复）；② 写数据 FIFO 深度 16；③ 源读取器**双词槽预取**；④ 扫描输出**四行缓冲环** | `rtl/cmd_fifo.v`、`rtl/sync_fifo.v`、`rtl/stream_reader.v`、`fb_scanout.v` |
| 提高内存带宽利用率 | 整屏 FILL 实测 **0.9958 px/拍**【板测，单 lane】；v3.1 双 lane 仿真 **1.983 px/拍**（**2.0×**） | `tb_perf_probe`：`cyc/px=0.504257 px/cyc=1.983114`（v3.1/v3.2） |

> **DDR 不是瓶颈，读延迟才是**。实测 DDR 占用只有峰值的 9%~28.5%，
> 但"非引擎读流"曾等待 **39,998 拍** —— 所以工程的优化重点一直放在**读仲裁公平性**上（见 §10 第 5、6 条）。

### 2.2 高阶挑战

#### 挑战 1：硬件 Alpha 混合

**赛题公式**：`输出像素 = 前景像素 × Alpha + 背景像素 × (1 – Alpha)`

**实现**（`rtl/pixel_path.v`）：

```verilog
// 通道 5/6/5 → 8bit 位复制展开
R8 = {fg[15:11], fg[13:11]};   // 5→8，位复制
G8 = {fg[10: 5], fg[ 8: 5]};   // 6→8
B8 = {fg[ 4: 0], fg[ 2: 0]};   // 5→8
// 定点混合（两积之和必须 18bit）
out = (fg8 * A + bg8 * (255 - A) + 127) >> 8;   // 再量化回 5/6/5
```

**三个层次的可编程性**（v3.2 属性侧口，`0x8C ATTR_PORT`）：

| 项 | 位域 | 说明 |
| --- | --- | --- |
| `blend_mode` | `[3:0]` | `0`=按算子默认 / `1`=alpha 混合 / `2`=加算饱和 / `3`=乘法 |
| `src_format` | `[5:4]` | `0`=RGB565 / `1`=ARGB1555 / `2`=**ARGB4444（逐像素 4bit alpha）** |
| `global_alpha` | `[13:6]` | 整条命令的全局淡入淡出系数 |
| `flags` | `[31:24]` | bit0 = alpha 测试（跳过完全透明像素）/ bit1 = 强制不透明 |

有效 alpha：`A = ⌊sprite_alpha · global_alpha / 255⌋`，
其中 `sprite_alpha` 可以来自**命令字**（`w6`，8bit）、**描述符**（`dw2[23:16]`，8bit）、
**属性字**（`global_alpha`，8bit）或**像素本身**（ARGB4444 的 4bit）。

**验证**：`tb_attr_blend.v`（545 行）32 条判据全过，其中 **7 条手算期望值**：

| 用例 | 输入 | 期望输出 |
| --- | --- | --- |
| L1 | `7BEF/C618 @ ga=128` | `A4F4` |
| L2 | 乘法模式 | `5AEB` |
| L3 | 加算 `1082/2945` | `39C7` |
| L4 | ARGB4444 `8ABC @ ga=128` | `BE18` |
| L5 | ARGB1555 `87E0 @ ga=64` | `B692` |
| L6 | `α=0` + alpha 测试 | 留孔（不写） |

> ★ L1~L6 这 7 条手算值**抓到过 TB 作者自己的位抽取错误**（把 `R8={r,r[4:2]}` 写成 `{r,r[2:0]}`）——
> 纠正后与 RTL 逐位一致。"表与 RTL 不一致时先怀疑表"这条经验也是那次留下的。

#### 挑战 2：颜色键控去背（Color Keying）

| 层 | 做法 | 收益 |
| --- | --- | --- |
| 像素级 | 16bit 比较器 `keep = (fg != key)`，键色由 `w7` 每命令可编程（软件约定洋红 `0xF81F`） | 不规则边缘精灵完美抠图 |
| **整词级** | 一个 128bit 词（8 个像素）**全部**等于键色 ⇒ **不提交这次写** | 省写带宽 |
| **块级（S3，v2.12）** | 4×4 网格覆盖整颗精灵，位 `rt*4+ct=1` 表示"这一块一个像素都不用碰"（不取数、不 blend、不写）。判据：该块**每一个**像素都等于色键才置 1 | 只收缩行两端 |

掩码生效条件（RTL 里显式限定）：`MASK_EN && OP==KEY && W≥4 && H≥4`；
FILL/ALPHA/COPY **显式忽略**掩码（测试台用全 1 掩码反证过）。

**实测收益**（`tb_dl_mask`）：收益完全取决于美术 —— 圆盘精灵 **0%**（每个 4×4 块都压着实体像素），
典型弹幕 **−4.5% / −21.4%**，小尺寸弹 **−68.1%**。

### 3.1 平台参数

| 下载调试 | 板载 FT4232HL Type-C 一线通（供电 / 下载 / **UART**） |
| 主频 | core_clk = **100MHz**（`pt.sdc: create_clock -period 10.000`），pclk = 148.75MHz |
| 时序余量 | V3.0 P&R：setup slack **1.063ns**、hold slack 0.026ns、最高可分析频率 **111.894MHz** |

> **为什么不做 112.5MHz**：V3.0 的 P&R 硬证据给出上限 111.894MHz，hold slack 只剩 0.026ns ⇒ 不可行。
> 本工程的所有优化都建立在 100MHz 之上，不依赖超频。

### 3.2 时钟与视频时序

```
25MHz 板载晶振 ──► PLL_BR0 ──► pclk = 148.75MHz = 25 × 119 ÷ 20
                                   │
                              1920×1080 CEA-861
                              H: 1920 + 88 + 44 + 148 = 2200
                              V: 1080 +  4 +  5 +  36 = 1125
                              ⇒ 148.75MHz / (2200×1125) = 60.10 Hz
                              行周期 2200 / 148.75MHz = 14.81µs = 1481 core 拍 @100MHz
```

扫描输出的取数预算：一行 1920B = **120 拍 128bit**。
优化前占行周期 73%（1080 拍），v2.5 后降到 **≈250~400 拍（约 20%）**，
余量从 0 提到约 27%。这是"左侧黑三角闪烁"问题的根因，见 §10 第 5 条。

### 3.3 DDR3 内存映射

`DDR_BASE = 0x00001000`（`soc.h: SYSTEM_DDR_BMB`）；解码窗 `0xE0000000`。

| 偏移 | 用途 | 大小 |
| --- | --- | --- |
| `+0x000000` | 程序镜像（bootloader 从 SPI Flash 搬入） | 1MB（linker `default.ld`） |
| `+0x100000` | （保留 / 备用精灵区） | 2MB |
| `+0x200000` | **精灵图集** `ATLAS_BASE` | 8KB 级 |
| `+0x300000` | **显示缓冲 0** `FB_BASE`（只由引擎/扫描输出写） | ~1.04MB |
| `+0x500000` | **后台缓冲 1** `FB_BACK` | ~1.04MB |
| `+0x600000` | 缓存写穿屏障临时区 `FLUSH_SCRATCH` | 8KB |
| `+0x700000` | **第三块缓冲 2** `FB_BUF2`（三缓冲用） | ~1.04MB |
| `+0x800000` | **显示列表几何表** `DL_GEOM` | 176B |
| `+0x820000` / `+0x840000` | **显示列表缓冲 A / B** | 各 128KB |

**选址的四条理由**：① 避开程序镜像与堆；② **1MB 对齐** ⇒ 自动满足 16B DDR 突发、64B D\$ 行、
AXI 突发；③ 行距 1920B = 120×16B ⇒ 行首 16B 对齐、无跨行碎块；
④ 两块缓冲隔 1MB ⇒ 减少 DRAM 行/bank 冲突。

### 3.4 读/写通路与仲裁

**优先级：扫描输出 > BitBlt 引擎 > CPU**（两级级联 `axi_rd_arb`）。
写通路经 `axi_wr_arb`，B 通道按 owner 分路。

这个优先级不是随便定的：扫描输出有**硬死线**（一行 1481 拍），错过就出黑行；
引擎次之（有帧预算）；CPU 没有死线（慢一点只是游戏逻辑慢）。实测最长等待：

| 场景 | 最长等待 | 出处 |
| --- | --- | --- |
| 优化前，扫描输出抢不到读通道 | **16,071 拍 ≈ 80 行** | `功能清单.md §13` |
| 加 `S_PRIO` 后 | **211 拍** | `功能清单.md §13.6` |

### 4.3 像素通路

```
                ┌──────────── 双 lane（v3.1，只在 dst 偶 lane 上配对）─────────────┐
  16B/词 ──► 源读取器（两词槽预取，2.0 px/拍）
                │
                ├─► 色键比较器  keep = (fg != key)  ──► 整词全键色则不提交
                ├─► 4×4 块掩码（仅 KEY）           ──► 整块透明则跳过
                │
                └─► 【混合通路】唯一一份乘加单元，按 blend_mode 选式：
                        α混合   out = (fg·A + bg·(255−A) + 127) >> 8
                        加算     out = min(255, ⌊fg·A/255⌋ + bg)
                        乘法     out = (fg·bg) >> 8
                     └─► 量化回 5/6/5：{r8[7:3], g8[7:2], b8[7:3]}
                                    │
                            ┌───────▼────────┐
                            │ 128bit 打包器  │（打包乒乓：藏掉每词专属冲刷拍）
                            └───────┬────────┘
                                    ▼  AXI4 写突发（合并后 burst_max=16）
```

**关键性能改造（v3.x 三步走）**：

| 步 | 改动 | 收益 |
| --- | --- | --- |
| ① 像素打包乒乓 | 藏掉每 16B 词的专属冲刷拍 | 每词 9 拍 → 8 拍（**+11%**）**但依赖写主机也提到 8 拍/词** |
| ② 写突发合并真正生效 | 合并判据换口径 + `S_BUF` 愿意等 | 写主机从 **8 拍/词 → 1.13 拍/词** |
| ③ 命令末尾冲刷提示 | 给写主机"命令结束"显式输入 | 尾延迟三段收敛 |

> ★ 第 ① 步有一个值得记的教训：仿真里 `wd_full=0`、写主机 idle 66,988 拍，
> 看起来"写通路与像素通路打平、余量=0"；**板上 B 往返只要比仿真多 1 拍，这 11% 收益就会被吃光**。
> 所以第 ②③ 步不是"锦上添花"，而是第 ① 步能否兑现的前提。

### 4.4 显示列表（DFU 取指器，v2.11）

**动机**：板测"每块一次 CPU 下发"≈**190 拍/块**（1 读 COUNT + 8 写 DATA 走 APB 桥），
把 16×16 FILL 从引擎自身能到的 367 拍/块抬到 561 拍/块。

**做法**：DDR 里放**紧凑描述符表**，硬件取指器自己展开成与 CPU 逐位相同的 8 字命令，
推进**同一个** `cmd_fifo`（引擎 FSM / 像素通路一行未改）。

```
描述符 = 16B = 4 字 = 恰好 1 个 128bit AXI beat（小端）
  dw0 [15:0]=X(signed)  [31:16]=Y(signed)
  dw1 [15:0]=SPR_ID     [31:16]=FLAGS
  dw2 [15:0]=KEY(0xFFFF=用几何表默认) [23:16]=ALPHA [31:24]=PRIO
  dw3 [15:0]=MASK_ID    [23:16]=W_OVR [31:24]=H_OVR

FLAGS：[1:0]OP [2]MIRROR_X [3]MIRROR_Y [4]CLIP_EN [5]SIZE_OVR [6]SRC_OFF_EN
       [7]MASK_EN [9:8]MASK_MODE [10]END_OF_LIST [11]IRQ_AFTER [12]CHAIN
       （MIRROR / SRC_OFF / CHAIN / MASK_MODE≠01 未实现 ⇒ 报 DL_ERR.UNSUPPORTED）

几何表 = 16B/条（16 条直接映射 cache）
  gw0=ATLAS_BASE   gw1=[15:0]ATLAS_STRIDE [31:16]KEY_DEFAULT
  gw2=[15:0]W [31:16]H   gw3=[15:0]SX [31:16]SY
```

**板级现实**：ALPHA/KEY 场景的描述符取指会被 DDR 争用饿过 `DL_TIMEOUT`
（即使把看门狗从 4096 拍提到 65535 拍仍触发，`stall_seen=1`）。
固件写了**三条硬上界**的自动重试（一次事件最多 1 次、1s 窗口内第二次即停用、重试自身失败即停用），
避免退化成"同一帧反复重画整趟"的永久重试环。**结论：演示主力用逐条下发，列表路径作为可选加速。**

### 4.5 属性侧口 / scissor / 扫描输出 LUT（v3.2 / S5）

| 功能 | 关键设计 | 为什么这么做 |
| --- | --- | --- |
| **属性侧口** | 深 16 的 **FWFT** 属性 FIFO；引擎在**每条命令起始**（`S_DEC`，8 个命令字弹完后）按序弹一个 | 刻意**不用** `sync_fifo` 那种"同步读 + 假空窗口"——属性与命令按序配对，任何一次假空都会让后续属性整体错位（**静默错模式**） |
| **scissor** | 与 S3 的行窗口**求交**；整行在外则走"空窗口跳过"（不取数、不算、不写）。坐标是**本条命令目的矩形的局部坐标**，半开区间 `[x0,x1)×[y0,y1)`，命令起始锁存 | 完全不碰像素通路 ⇒ 关闭时**逐位原样返回**，零代价 |
| **扫描输出 LUT** | 3 通道 × 2 bank × 256 项 8bit→8bit，插在行缓冲之后、输出级之前；读地址由 `px1` 级组合给出 ⇒ **不新增流水级、不产生 1 像素相移** | 全屏淡入淡出/白闪**零 DDR 带宽** |

**兼容档保证**：`blend=0` 时属性字**整字惰性** ⇒ 四种算子与 v3.1 逐位相同。
默认字 `0x0000_3FC0` = 位域精确的"blend 0 / RGB565 / ga 255 / flags 0"。
**最强证据**：`tb_perf_probe` 的 310 行 `PROBE *` 输出与 v3.1 的日志**逐行完全一致**
（整屏 FILL 261,407 拍、`burst_max=16`/`burst_avg=16.0`、`wd_full_cyc=0`）⇒ **未使用时吞吐代价为零**。

### 5.1 驱动与 BSP

| 项 | 说明 |
| --- | --- |
| BSP | Efinity Sapphire SoC BSP（`bsp.h` → `soc.h/uart.h/clint.h/print.h`） |
| 时钟口径 | `SYSTEM_CLINT_HZ = 100000000`（core 域），`tick32()` 只读 CLINT mtime 低 32 位（1 次总线读，而不是 `clint_getTime` 的 3 次） |
| 寄存器访问 | `blt_wr(off,v) / blt_rd(off)` 两个薄封装（`BLT_BASE = 0xF8100000`） |
| 唯一命令出口 | `blt_emit(attr, op, src, dst, ss, ds, w, h, alpha, color)` —— 属性配对纪律靠它保证 |
| 缓存一致性 | `cache_evict()`：向 `FLUSH_SCRATCH` 写 8KB（**store 有序屏障**，D\$ 是写穿）。**禁用 `data_cache_invalidate_all()` 代替 flush**（写回模式下会丢脏行） |
| UART | 非阻塞轮询；**RX 占用 = `status[31:24]`**，TX 余量 = `status[23:16]`（早期用错 `>>16` 导致串口指令完全无效） |

### 5.2 双缓冲 → 三缓冲 → FLIP

| 版本 | 方案 | 代价 |
| --- | --- | --- |
| 早期 | 后台缓冲 → **整帧 COPY** → 显示缓冲 | 实测 ≈**1.89M 核拍 ≈ 19ms**/帧，**超过 16.7ms 场周期** ⇒ 上限被钉在 ~53fps |
| v2.6 | **FLIP**：写 `FB_SEL` 请求，扫描输出在帧边界锁存基址 | 一次 DDR 搬运都不做（省下 19ms 给内容） |
| v2.7 | **三缓冲**（显示 A / 画 B / 预清 C）+ **并发清屏引擎** + **帧边界中断** | 背景重铺也不进关键路径 |

**"不撕裂"的保证链**（每一条都有独立机理）：

1. 写 `FB_SEL` 只是**请求**，扫描输出在**垂直消隐起点**锁存 ⇒ 一场之内只读一个缓冲；
2. `FB_STAT[1:0]` 是**已生效**的选择，软件等它变成请求值才认为"这一帧上屏了"；
3. 有界超时（100ms ≈6 场）后**重发请求继续等**，绝不退化成"往可能正在上屏的缓冲里画"；
4. **硬件互斥**：清屏引擎的目标 == 正在显示 / 正在画的缓冲 ⇒ 一个像素都不写并置 ERR ——
   "清屏不会破坏正在上屏的缓冲"是**硬件保证**，不依赖软件正确性。

## 6. 性能测试与实测数据

### 6.1 测量口径（**先立口径，再看数字**）

| 指标 | 口径 |
| --- | --- |
| 单位 | **core 拍**（`DL_PERF` 是取指器在 core 域数的周期；逐条路径的秒表是 CLINT mtime，同在 core 域） |
| "每精灵拍数" | 该帧引擎总周期 ÷ 精灵数。**只数精灵**，但周期里含整片重铺；N 大时重铺占比 <3% |
| 帧预算 | 60fps = **1,666,667 拍** @100MHz |
| 报出的三个帧率 | `HW=` 纯硬件渲染趟率 / `CPU=` 纯 CPU 渲染趟率 / `SCR=` **真正上屏帧率**（整帧 COPY 或 FLIP 完成次数）。三者共用同一个 1Hz 窗口、同一次清零 |
| 1Hz 成本行 | `EV cmd path done: n=.. cycles=.. cyc/sprite=..`（逐条）/ `EV dl list done: ...`（列表），同口径可直接比大小 |

### 6.2 板级实测（v2.16 口径，`e` 开、逐条下发）【板测】

**每精灵拍数**：

| 尺寸 | N | FILL | ALPHA | KEY |
| --- | --- | --- | --- | --- |
| 16×16 | 2725 / 1725 / 2025 | **514.3** | **856.4** | **719.1** |
| 32×32 | 1200 / 775 / 950 | 1263.8 | 1969.0 | 1617.4 |
| 64×64 | 350 / 225 / 275 | 4450.0 | 6742.7 | 5537.5 |

（测量粒度：16/32 档 ±0.9%~±4%，64 档 ±7%~±11%）

**拟合式 `每块 = A + B×像素`**：

| 算子 | A（固定开销，拍） | B（每像素，拍） | 渐近吞吐 |
| --- | --- | --- | --- |
| FILL | **252** | **1.025** | 97.6 Mpx/s |
| KEY | 398 | 1.255 | 79.7 Mpx/s |
| ALPHA | 464 | 1.533 | 65.2 Mpx/s |

拟合残差：16×16 与 64×64 **逐拍精确**；32×32 有 **+3.3%** 残差（文档已如实记录 −2.9%/−3.9%/−3.2%）。

**结构性事实**：

- `A_FILL = 252` 拍在 64×64 只占 **5.7%**、在 16×16 占 **49%** ⇒ **尺寸档的杠杆已经用尽**；
- **命令之间零重叠**（`ST_WDWAIT` 写屏障；64 块背靠背只藏 63 拍 = 0.075%）⇒ 固定开销是**串行累加**的；
- 每条命令残留 **19 拍**合并固有代价（16×16 时占 4.4%，调 `TAIL_GRACE` 6~8 可解）。

**带宽**：DDR 实测占用只有峰值的 **9%~28.5%**（线速外推 37.5%）⇒ **带宽不是墙，像素通路才是**。

## 7. 高负载互动游戏 Demo（高阶挑战 3）

### 7.1 与赛题的对应

| 赛题要求 | 实现 |
| --- | --- |
| 极高同屏元素数量 | 同屏 = 敌弹 + 自机弹 + 敌机 + 自机 + 爆点火花 + 星空，**全部走引擎**；N 上限 **2400** |
| Alpha 混合 | 敌弹/自机弹/火花走**加算混合**（`ATTR_PORT blend=ADD`），每颗弹的 `global_alpha` = 发光强度 |
| Color Keying | 图集统一用 **`0x0000`（纯黑）** 作键色；机体走 `op=KEY` 硬边抠图 |
| 60FPS 稳定 | 三缓冲 FLIP + 并发清屏引擎，**不做整屏 COPY** |
| **同屏数量极限** | 串口 `g` 自动爬坡：逐秒抬 N 直到帧率 <58，打印 `LIMIT N=… fps=… ON=…` |
| 与纯 CPU 对比 | `c`/`h` 键切换，`HW=` 与 `SW=` **两个数都留在屏幕上** |

### 7.2 输入：PC 键盘 → 串口（**板载按键一个都不用**）

```
PC → 板   '@' + 两位十六进制 + '\n'
           bit0 上(W/↑)  1 下(S/↓)  2 左(A/←)  3 右(D/→)
           bit4 开火(J/空格) 5 慢速(K/Shift) 6 炸弹(L/X) 7 暂停(P/回车)
           · 任一键变化立刻发；另外每 100ms 补发一包心跳
板 → PC   EV ...（命令回显）/ ST ...（4Hz 记分板）/ LIMIT ...（爬坡结论）
```

三条设计决定：

| 决定 | 为什么 |
| --- | --- |
| **整包替换语义**（每包携带完整 8 位位图，不是增量） | 丢一个包最多晚 100ms 生效，**永远不会卡住某个方向键** |
| **100ms 心跳** | 4 字节/包 = 40 B/s，串口开销 ~0.35ms/包；顺带喂饱看门狗 |
| **500ms 看门狗** | 标签切走 / 拔线 / 上位机崩了，自机都不会一直飞 |

输入延迟：串口轮询放在**每 4 圈**（不是 FinalDemo 的每 32 圈慢时间片），
主循环一圈 ≈ 一两百拍 ⇒ 轮询间隔 ≈ 几十 µs，**比一个 16.7ms 的帧快两个数量级**。

### 7.3 渲染架构（为什么能顶住几千个精灵）

| 手段 | 说明 |
| --- | --- |
| **三缓冲 FLIP** | 一趟画完只写一个寄存器换显示基址，**零 DDR 搬运** |
| **并发清屏引擎** | 下一块缓冲的背景由硬件后台铺（≈2.1ms），不进关键路径；目标冲突时硬件拒写 |
| **逐条下发** | v3.2 的属性字只有"每条命令配一个"这一种配对方式，16B 描述符装不下 ⇒ 要每精灵不同 alpha/混合就只能逐条（且板级记录里 DL 在 ALPHA/KEY 场景会被饿过看门狗） |
| **一张图集服务两条路径** | 透明处一律 `0x0000`：有属性侧口 ⇒ `op=ALPHA + blend=ADD`（黑像素加 0 = 天然透明，真辉光）；无属性侧口 ⇒ `op=KEY + w7=0`（硬边但完全正确）⇒ **位流能力只影响好不好看，不影响能不能跑** |
| **加算可交换** | 辉光弹之间**没有 z 序问题**，几百颗重叠不需要任何排序 |
| **裁剪** | 弹幕会飞出游戏区，`int16` 负数转 `uint32` 参与乘加会写到帧缓冲之外 ⇒ 每条精灵进清单前先裁成矩形并记源偏移 |

### 7.4 ★ 敌弹显示模式：FILL / ALPHA / ADD / KEY

串口 `5/6/7/8` 直选、`f` 循环。**只作用于敌机放出的弹**（自机弹与火花固定加算），
所以切档时只有弹幕的画法在变：

| 档 | 引擎算子 | 观感 | 16×16 @70% 预算容量 |
| --- | --- | --- | --- |
| **FILL** | `op=1` | 纯色方块，**没有源/键色/alpha** —— 最省，但会盖住底下 | **2269 颗/帧** |
| **ALPHA** | `op=2` + 命令字 `α=160` | 经典半透明；图集是矩形、四角纯黑 ⇒ 半透明把背景压暗，**每颗弹套一个暗方块** | **1362 颗/帧** |
| **ADD** | `op=2` + 属性字 `blend=ADD` | 加算辉光（默认档） | 1362 颗/帧 |
| **KEY** | `op=3`，色键 `0x0000` | 硬边抠图 | **1622 颗/帧** |

> **ALPHA 档的暗方块不是 bug，正是 Color Key 存在的理由** —— 把这条写进文档而不是"想办法抹掉它"，
> 因为它恰好是赛题要展示的"三种算子的差别"。切到 KEY 档方块感立刻消失。

**HUD 报的是"生效档"而不是"请求档"**：ADD 档在没有属性侧口时会降级成 KEY，
`bulm_eff_name()` 是唯一判定点，`OP=` 会如实显示 KEY（串口回包同时给两个值
`EV bulm=FILL (requested; effective=FILL)`）。这是刻意的 —— **"看起来成功了"的假成功是本工程反复踩过的坑**。

**怎么用它量极限**：`4` 拉满 N → `g` 自动爬坡 → 换一档重复 → 比较四次的 `LIMIT N=… ON=…`。
同一份弹幕下 FILL 能顶住的同屏数量明显高于 ALPHA（容量 2269 vs 1362，约 **1.67×**）。

### 7.5 生成器必须跟得上 N（踩过的坑）

主机仿真第一次跑出来的结论：把 N 从 256 跳到 2400，**同屏元素数只到 345**。
根因不是引擎，是**生成器**：老逻辑"每个生成节拍只补一架敌机"，铺满 27 架要 7 秒，
再等弹幕铺开又要几秒 ⇒ 用户按 `4` 之后要等半分钟才看见密集弹幕，
第一反应必然是"这加速器带不动"。

修法：`ENEMY_MAX 16 → 24`（它是"弹幕能不能被喂到 N"的天花板：24×22×240/46 ≈ 2750 > 2400）
+ 生成节拍 22 → 16 帧 + **每拍补到 want**（上限 4 架）+ 环弹发数也随 N 增长。
改完同一次仿真 `ON_max = 784`。

### 7.6 弹池与 O(1) 快路径

`bul_alloc_enemy()` 加了 `if (g_bul_live >= g_ncap) return -1;` 的快路径。
没有它的话池满时**每一次发射**都要扫 2400 个槽；一帧最多 24×24 = 576 次发射
⇒ 最坏 **138 万次循环 ≈ 3~4M 拍 > 一帧预算（1.67M 拍）** ⇒ 表现就是"弹幕铺满的一瞬间掉帧"。

## 8. 纯 CPU vs 硬件加速：差距有多大

### 8.1 对比的诚实性设计

| 项 | 硬件侧 | CPU 侧 |
| --- | --- | --- |
| 场景 | 同一颗种子初始化、同一套推进规则 ⇒ **目标坐标逐位相同** | 同 |
| 擦除语义 | 可用"每趟整片重铺"省掉逐块擦除 | **故意保留"先擦后画 + 逐块擦旧矩形"**（朴素语义），不跟随硬件侧优化 |
| 精灵图集 | 同一份 | 同一份 |
| 混合公式 | `pixel_path.v` 定点式 | `blend565()`/`add565()` **同式实现** |
| 显示通路 | 三缓冲 FLIP | 同（两边都用同一套上屏机制，隔离出"谁在画像素"这一个变量） |

### 8.2 观测方式

`FinalDemo` 默认 **SPLIT 模式**：上半屏硬件引擎画、下半屏 CPU 逐像素画，
顶部信息条同屏显示 `HW=nnn CPU=nnn SCR=nn`（三个数共用同一个 1Hz 窗口）。

`GameDemo` 里按 `c` 切到纯 CPU、`h` 切回硬件，`HW=` 与 `SW=` 两个数**同时留在屏幕上**，
按一下就能做实时对比；切换时 1Hz 窗口**重置**（避免读到"半个窗口"的假帧率）。

### 8.3 结论

- CPU 侧每像素要做 16bit 读 + 判色键/混合 + 16bit 写，16×16 精灵约 256 次这样的操作；
  硬件侧同尺寸 ALPHA **856 拍/精灵**（板测）。
- RISC-V 直写 DDR 的吞吐远低于引擎的 **65~98 Mpx/s**（板测渐近值），
  同屏几百个精灵时帧率差 **1~2 个数量级**。
- 更关键的是**CPU 被解放**：硬件模式下 CPU 只做游戏逻辑与指令下发（N=2400 时约
  **21,600 次 APB 写/帧** = 每条命令 1 个属性字 + 8 个命令字，摊到每圈 ≤64 条），
  碰撞/生成/AI 全部还在 CPU 上跑而帧率不掉。

## 10. 版本演进：14 次板级问题的定位与修复

这一章是本工程最有价值的部分 —— **每一个都是"上板才知道"的问题，而且大多数在仿真里看不到**。

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 串口指令完全无效 | `uart_poll_char` 用 TX 余量（`>>16`）当 RX 占用 ⇒ 判据恒真、读空 RX | 改 `>>24`；另发现 mini printf **只认 `%c %s %d %X %x`**（`%u`/宽度/`%%` 会错位消耗 va_arg 挂死） |
| 2 | 非对齐 dst 特定 lane 出错 | lane 处理边界 bug | `功能清单.md §10.1`，逐 lane 用例 |
| 3 | 指令 FIFO 写满时丢指令 | 满边界丢字 ⇒ 后续所有 8 字指令帧**整体错位 1 个字** | `§10.2`；上板"mis=240 却无 ERR"由此解释 |
| 4 | ALPHA 数值全错 | **绿通道位复制抽头取错**（`{p[10:5],p[8:5]}` 应为 `{p[10:5],p[7:6]}`） | `§11`；R/B 两通道与旧仿真逐位一致，只有绿差 —— 决定性线索 |
| 5 | 时序收敛但板子不启动 | §13 的读侧改动在 CPU 对抗 TB 下不成立 | `§14`，二分 + 回退 |
| 6 | 写仲裁让位那一拍 AW 握手漏计数 ⇒ B 错路 ⇒ **引擎 BUSY 不退** | `axi_wr_arb` 组合直通 + 强制让位不判握手 | `§12`：AW 受理与转发解耦（skid/守护），新 TB `tb_arb_deadlock` |
| 7 | 左侧黑三角闪烁 | 三因叠加：单行占行周期 73% + 抢不到读通道（最长等 **16,071 拍**）+ 仅 2 行缓冲 | `§13`：`S_PRIO`（→211 拍）+ 128bit 拍缓冲 + 连续 AR + **4 行缓冲环** + 重同步看门狗 |
| 8 | 整机跑 1~2 秒后彻底静止 | `S_FETCH` 唯一出口是"收满 120 拍"（**无超时**）⇒ `s_hold` 把 CPU 永久锁在 DDR 之外（程序全在 DDR ⇒ 取指失败） | `§17`：`FETCH_TO/DRAIN_TO/BACKOFF_TO=4096`、按突发持有、rlast 计数排空、`dbg_abort` 单比特 toggle 两级同步 |
| 9 | 第三次上板仍死 | 读仲裁 `cnt_s` 泄漏具有**永久否决权**（AR 已计入但 rlast 永不来） | `§18.8`：`LEAK_TO=256`；TB `57105 vs 0` |
| 10 | 重叠处 z 序高频乱跳 | 引擎**"假完成"**：`sync_fifo.empty = !out_v` ⇒ `BUSY=0` 比 AW 受理早 3~4 拍、比 B 早一次写往返 ⇒ 下条指令 RAW 抢跑 | `§19`：完成判据并上 `b_pending==0 && wd_count==0 && !wd_busy` |
| 11 | 整屏 COPY 19ms > 16.7ms 场周期 ⇒ 上限 53fps | 单帧固定开销超预算 | `§20`：**FLIP**（只换基址，零搬运） |
| 12 | 背景重铺仍在关键路径 | 每帧清屏 568k 周期 | `§21`：**并发清屏引擎**（后台铺）+ 三缓冲轮转 + 帧边界中断 |
| 13 | 帧率被诊断吃掉 | 周期像素扫描走共享读通路（**23,580 次读/帧，代价 2.4~4.7ms/帧**） | `§12`：停用周期扫描，改手动触发；优先用硬件计数器（`SCAN_DBG 0x20`） |
| 14 | **冻屏真根因** | **未对齐 32bit 存储**（`scene_step` 让 x 变奇数 ⇒ alignment 异常 ⇒ 默认 trap 死循环）。**前四次 RTL 修复（看门狗/CDC/LEAK_TO/预热）都是针对幻影** | 用 16bit 收头/收尾；删掉 `x & ~1` 补丁；加开机 `aligncheck` |

**贯穿全程的六条方法论**（都写进了 `doc/开发问题与解决记录.md`）：

1. **先验证测量通道，再采信任何观察结果**（串口方向、状态字段语义、printf 格式串都算通道）；
2. **硬件/TB 证据优于推理**，且"否定性证据"（A/B 两边都 PASS ⇒ 假设被证伪）与阳性结果一样值钱；
3. **A/B 没有差异时先查激励**（`28'h010_0000` 是 bit20 而不是 bit24 ⇒ 两边都 PASS，问题在 TB）；
4. **"完成/释放/归还"的每个条件都要问：它有独立上限吗？**（只修其中一个量，剩下的照样锁死系统）；
5. **现象相同不代表机制相同**：`"屏幕停在最后一帧 + 串口静默"` 至少有三种机制（CPU 对齐异常 / 取不到 DDR 读通道 / 引擎 BUSY 不退），它们被误判了四轮；
6. **每一类"静默失败"都要配一个开机自检**。
