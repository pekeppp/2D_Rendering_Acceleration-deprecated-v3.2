## 第 0 部分　你的知识地图：已会 vs 要学

你设计过 RISC-V CPU，意味着以下能力已经具备，本赛题全部用得上：

| 你已经在 CPU 里做过的 | 本赛题对应要用到的 | 区别/新东西 |
| --- | --- | --- |
| 有限状态机（取指/译码/执行） | 视频时序状态机、BitBlt 行/像素状态机 | 都是 FSM，只是状态含义不同 |
| 流水线（IF/ID/EX/MEM/WB） | 像素处理流水线（读像素→混合→写回） | 原理完全一样：分阶段、每拍推进一拍 |
| 内存映射（访存地址译码） | 显存编址、寄存器组、地址对齐 | 显存就是一个"大数组"，编址是数学换算 |
| 简单总线（或 AXI 从机经验） | AXI4/AXI-Lite 主机+从机、突发传输 | 你之前可能只写过从机，这里要写**主机**（主动发起读写） |
| 中断/异常 | 指令完成中断、帧同步（VSYNC）中断 | 软硬协同的握手方式 |
| 计数器/定时器 | 像素计数、FPS 统计 | 基本没有新概念 |
| 异步 FIFO（如果 SoC 里写过） | 跨时钟域数据通路 | 图形系统里有 3 个时钟域，FIFO 是标配 |

**真正全新的知识点只有 4 个**：
1. **视频时序**（HSYNC/VSYNC/消隐、像素时钟）—— 本质还是一个计数器状态机；
2. **帧缓冲/双缓冲** 的概念 —— 本质是"共享内存的读写竞争"问题；
3. **BitBlt 位块搬运算法** —— 本质是"带行距的二维内存拷贝"状态机；
4. **Alpha 混合 / 色彩键控** —— 本质是"每个像素做一次乘加运算"。

好消息：图形渲染的硬件核心（2D 加速器）比 CPU 简单得多——没有取指、没有分支预测、没有乱序，就是**一个按指令搬运并处理像素的专用状态机**。你的 CPU 经验是降维打击。

## 第 1 部分　赛题解读：把赛题翻译成工程任务

### 1.1 一句话理解赛题

> 做一张"显卡里的 2D 加速器（BitBlt Engine）"：RISC-V CPU 只负责游戏逻辑和下发指令，FPGA 硬件负责把内存里的图像数据高速搬运/混合到显存，再通过 HDMI 输出到显示器。

赛题的核心考点是**异构计算与软硬件协同**：CPU 不碰像素，像素活全部由硬件干。

### 1.2 基础要求 → 工程任务

| 赛题条目 | 翻译成工程任务 | 涉及原理 |
| --- | --- | --- |
| ① BitBlt 引擎：解析"操作类型、源地址、目的地址、宽高"指令 | 设计一个寄存器接口（AXI-Lite 从机）+ 指令 FIFO + 引擎状态机，支持 **Block Copy**（块拷贝）和 **Solid Fill**（纯色填充） | 总线、FIFO、FSM、地址计算 |
| ② 生成 VGA/HDMI 时序（最低 640×480@60；本项目主线 960×540@60） | 时序发生器（计数器状态机）+ 帧缓冲扫描输出 + HDMI TX IP | 视频时序 |
| ③ 必须通过**系统总线**访问内存，用**突发传输 + FIFO** 提高带宽 | BitBlt 引擎带 AXI4 **主机**口，DDR3 读写用 Burst（如 16~64 字节），内部 FIFO 解耦速率 | AXI 突发、DDR3 控制器、带宽 |
| ④ C 驱动：寄存器配置 + **双缓冲**避免撕裂 | 驱动库 blt_copy()/blt_fill()，两个帧缓冲轮流做"显示/绘制"，VSYNC 时交换 | 双缓冲、撕裂 |
| ⑤ Demo：方块随机移动、大图快速切换；实时对比"纯软件渲染 vs 硬件加速"帧率 | 一个测试程序：同一批方块，软件路径（CPU 逐像素写）和硬件路径（下发指令）各跑一遍，屏上显示两边 FPS | 性能测量 |

### 1.3 高阶挑战 → 工程任务

| 赛题条目 | 翻译成工程任务 | 涉及原理 |
| --- | --- | --- |
| ① 硬件 Alpha 混合 | 引擎像素通路加"读背景像素 → `out = fg×α + bg×(1−α)` → 写回"，用 DSP 乘法器 | 定点数、DSP、流水线 |
| ② 色彩键控去背 | 引擎里加比较器：像素 == 透明色（如品红）则跳过不写，实现不规则精灵 | 比较器、条件写 |
| ③ 高负载游戏 Demo（弹幕/幸存者类）@60FPS 极限 | 精灵引擎 + 对象池 + 碰撞 + 粒子；压测同屏精灵数上限 | 软硬协同、性能瓶颈分析 |

### 1.4 隐含评分点（评委大概率看这些）

1. **带宽利用率**：有没有用突发？突发长度多少？有没有 FIFO 吸收延迟？（赛题明确点名）
2. **双缓冲 + 无撕裂**：必须做，且要在文档里讲清楚怎么防撕裂。
3. **对比数据**：纯软件 vs 硬件加速的 FPS 数字，同屏精灵数极限——**用数字说话**是最大加分项。
4. **软硬协同深度**：指令队列（批量下发）、完成中断、帧同步——"CPU 发了指令就去干别的"才是异构。
5. **演示效果**：游戏手感、画面流畅度、屏上实时 FPS 显示。
6. **文档**：架构图、时序图、测试数据表、设计决策理由。

### 2.1 板卡资源（官方 datasheet + 板卡文档核实）

**FPGA 核心：易灵思钛金 Ti60F225I3**（Efinix Titanium，16nm FinFET）

| 资源 | 数量 | 对本赛题的意义 |

### 2.2 三个关键设计结论（先想清楚再动手）

**结论 1：帧缓冲必须放 DDR3，片内 BRAM 装不下。**
- 960×540 @ RGB565（16bit）：960 × 540 × 2B = **1,036,800 B ≈ 1.0 MB**，双缓冲要 **2.1 MB**；
- 片内 BRAM 总共只有 ≈325 KB → **装不下**。
- 所以：赛题要求的"从内存（DDR）搬到显存"路线是**必然**的，DDR3 控制器 IP 是必经之路，要最早学、最早跑通。

**结论 2：带宽充裕，瓶颈不在带宽，在"每像素吞吐"和"总线利用率"。**

| 流量 | 计算 | 数值 |
| --- | --- | --- |
| 960×540@60 扫描输出（只读） | 960×540×2B×60 | ≈ **62 MB/s** |
| 1080p@60 扫描输出（RGB888 只读） | 1920×1080×3B×60 | ≈ **373 MB/s** |
| DDR3 理论峰值 | 800Mbps × 16bit ÷ 8 | 1.6 GB/s |
| DDR3 实际可用（含刷新/行激活/仲裁，按 60~75%） | — | ≈ 1.0~1.2 GB/s |

→ 显示扫描只吃掉 ~5%（62MB/s ÷ ~1.2GB/s 可用），剩下 ~95% 带宽全给 BitBlt 引擎用，**带宽不是瓶颈**。

真正的瓶颈是**引擎的像素吞吐率**：1 像素/时钟 × 100MHz = 1 亿像素/秒。
- 960×540 满屏画一遍 = 518,400 像素 ≈ **5.2ms**，60fps 一帧预算 16.7ms → 每帧能干 3 遍满屏绘制；
- 32×32 精灵 = 1024 像素 → 理论上每帧可画 1600 个以上（60fps 下），实际受 DDR 读写与指令下发开销影响，落到几百~上千个。

**结论 3：分辨率主线定 960×540@60（qHD，1920×1080 的 1/4），1080p 只作冲刺加分项。**
- 960×540 像素时钟 37.36MHz，时序宽松、带宽充裕、**16:9 宽屏无黑边**，且高于赛题最低 640×480@60；
- 960×540 = 1920×1080 双向各取 1/2 → 升 1080p 冲刺时结构与参数可整体沿用（像素率 ≈×4）；
- 1080p@60 像素时钟 148.5MHz，TMDS 每通道 1.485Gbps，贴着板卡高速 IO 的 1.5Gbps 上限，时序收敛压力大；
- 建议：先把 960×540 全链路做扎实，后期有余力再上 1080p（把引擎改成 2 像素/时钟）。

### 2.3 时钟方案（3 个时钟域）

| 时钟 | 频率 | 来源 | 用途 |
| --- | --- | --- | --- |
| core_clk | 100MHz | 25MHz 晶振 × PLL ×4 | CPU、AXI 互联、BitBlt 引擎、DDR 控制器接口 |
| pixel_clk | 37.36MHz（960×540） | PLL | 视频时序发生器、HDMI TX |
| ddr_clk | 400MHz（DDR 800Mbps） | PLL | DDR3 物理层 |
| tmds_bit（由 HDMI IP 内部产生） | 373.6MHz（960×540） | pixel×10 | TMDS 串行输出 |

跨时钟域处全部用异步 FIFO/同步器（见原理第 11 节）。

## 第 3 部分　系统总体架构设计（推荐方案）

### 3.1 先做一个关键决策：RISC-V 用谁的？

你设计过 RISC-V CPU，但"能用"和"能用于比赛"之间差一个完整的 SoC 环境。三个选项：

| 方案 | 说明 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- |
| **A. Efinix Sapphire SoC IP（推荐）** | 板卡文档 08 号 demo 就是它：RISC-V 软核 + AXI 互联 + UART/SPI/Timer/GPIO + softJTAG 调试 + Efinity RISC-V IDE + 现成 DDR3 通路 | 最快跑通；官方 IDE 调试（断点/单步/看内存）；精力全部投入 BitBlt 引擎（**这才是赛题核心**） | CPU 不是自己写的，报告里"CPU 自主性"弱一些 | **绝大多数队伍** |
| B. 自研 CPU + 自研 SoC | 用自己的 RISC-V 核，自己搭 AXI 互联、中断控制器、DDR3 通路、引导代码 | 展示度极高，"全自主"；你已有 CPU 基础 | 工作量 +2~3 周；DDR3 初始化、调试链路（JTAG/串口打印）都要自己搞定，翻车风险大 | 时间充裕、想要最高自主性的队伍 |
| C. 混合（先 A 后 B） | 先用 Sapphire 跑通全部功能，后期把 CPU 换自研核（接口兼容） | 两头都占 | 两次系统集成，工作量大 | 时间非常充裕 |

> **我的建议：选 A 或 C。** 赛题的灵魂是"软硬件协同的 2D 加速器"，评委看的重点是 BitBlt 引擎设计、带宽优化、演示效果。CPU 是谁家的不影响主线分数；把省下的时间投到 Alpha 混合、精灵引擎和游戏 Demo 上，收益大得多。如果队伍想冲"自主设计"分，就在报告里写明"CPU 采用 Efinix 软核，加速器完全自主设计"，并考虑后期（C 方案）替换。

下文按**方案 A** 展开（自研路线在 3.7 给出差异点）。

**数据流（一帧）**：
1. CPU 运行游戏逻辑 → 更新精灵位置 → 向引擎**批量下发指令**（写指令 FIFO）；
2. 引擎逐条执行：从 DDR3 读源图 →（Alpha/抠图处理）→ 突发写回帧缓冲 Back；
3. 扫描输出控制器从帧缓冲 Front 读行 → 行 FIFO → HDMI TX → 屏幕；
4. CPU 等一帧结束（VSYNC 中断/查询）→ 交换 Front/Back 指针 → 循环。

### 3.3 地址映射（寄存器接口，AXI-Lite 从机）

| 偏移 | 名称 | R/W | 说明 |
| --- | --- | --- | --- |
| 0x00 | CTRL | RW | bit0=GO(启动/使能), bit1=IRQ_EN, bit2=软复位 |
| 0x04 | STATUS | R | bit0=BUSY, bit1=DONE, bit2=ERR, bit3=FIFO空 |
| 0x08 | CMD_FIFO_DATA | W | 写指令字（FIFO 模式，可连续写 8 个字） |
| 0x0C | CMD_FIFO_COUNT | R | 指令 FIFO 深度（剩余条数） |
| 0x10 | INT_EN / INT_STATUS | RW | 完成中断使能/状态 |
| 0x14 | PIXEL_CLK_DIV... | RW | （可选）时序参数可编程 |

> 约定（软件见 `software/blt_regs.h`）：GO 写一次后引擎**自动消费指令 FIFO**（边推边跑，
> 批量可超 FIFO 深度）；DONE 为电平（FIFO 空且引擎空闲）= 一批指令全部完成。

指令字（FIFO 内 8×32bit，与 C 结构体一一对应）：

```c
// 一条渲染指令 = 8 个 32bit 字，一次写入 CMD_FIFO
typedef struct {
    uint32_t op;          // 0=BLOCK_COPY, 1=SOLID_FILL, 2=ALPHA_BLEND, 3=COLOR_KEY
    uint32_t src_addr;    // 源地址（字节地址，须对齐到突发粒度）
    uint32_t dst_addr;    // 目的地址（字节地址）
    uint32_t src_stride;  // 源图像行距（字节）= 源图宽度×2
    uint32_t dst_stride;  // 目的行距（字节）
    uint16_t width;       // 块宽（像素）
    uint16_t height;      // 块高（像素）
    uint16_t alpha;       // 0~255，仅 ALPHA_BLEND 用
    uint16_t pad0;
    uint32_t color;       // 填充色（SOLID_FILL）/ 透明色（COLOR_KEY）
} blt_cmd_t;              // 共 32 字节 = 8 个字
```

**批处理设计（赛题点名要的"指令 FIFO"）**：CPU 把一帧所有精灵的指令连续写入 CMD_FIFO，一次 GO 启动，引擎自己排队执行，全部完成后置 DONE/发中断。CPU 写入 FIFO 不阻塞、不等待引擎，这就是"CPU 只管发指令"的体现。

### 3.4 BitBlt 引擎内部结构（你要写的核心 RTL）

```
                     AXI4 Master 口（连互联 → DDR3）
                        │          │
              ┌─────────▼───┐  ┌───▼─────────┐
              │  读通道     │  │  写通道      │
              │ (源/背景读)  │  │ (目的写)     │
              └─────┬───────┘  └───┬─────────┘
                    │              │
        ┌───────────▼──────────────▼───────────┐
        │            像素处理通路                │
        │   COPY:     FIFO直通                   │
        │   FILL:     产生常量色                 │
        │   ALPHA:    out = fg×α + bg×(1−α)     │  ← DSP/乘法器, 流水线
        │   COLOR_KEY: fg==key ? 跳过 : 输出     │  ← 比较器
        └───────────┬──────────────┬───────────┘
                    │              │
        ┌───────────▼──────────────▼───────────┐
        │       引擎状态机 (FSM)                 │
        │  IDLE→POP_CMD→LINE_LOOP→PIXEL_LOOP→   │
        │  →DONE (每行: 算地址→突发读→处理→突发写)│
        └───────────────────────────────────────┘
        ┌───────────────────────────────────────┐
        │  指令FIFO (BRAM) + 寄存器组 (AXI-Lite) │
        └───────────────────────────────────────┘
```

核心状态机（伪代码）：

```
IDLE:      等待 GO 或 FIFO 非空 → POP_CMD
POP_CMD:   读一条指令到寄存器 → 校验 → LINE_LOOP
LINE_LOOP: 若 行数==0 → 置 DONE → IDLE
           else 计算本行源/目的地址 → 发起突发读 → PIXEL_LOOP
PIXEL_LOOP: 逐像素: 按 op 处理 → 写 FIFO → 攒够突发长度(或行尾) → 突发写
           行结束 → 行数--, 地址+=stride → LINE_LOOP
```

设计要点（对应赛题"突发+FIFO"要求）：
- **突发读写**：每行按"行内对齐段"发起 AXI4 Burst（长度 8~16，即 16~32 字节），而不是逐像素单次读写；
- **源/目的两个 FIFO**：源读 FIFO 缓冲 DDR 读回数据，目的写 FIFO 缓冲待写数据，解耦 DDR 延迟抖动，让像素通路匀速流动；
- **地址对齐**：把块的每行起点对齐到 DDR 突发边界（16 字节），首尾不齐的用"读-改-写"或逐字节补齐（见原理第 5 节）。

### 3.5 显示通路（扫描输出 + HDMI TX）

- **扫描输出控制器**：以 pixel_clk 逐像素计数，产生 H/V 时序信号（active/sync/blank），需要哪个像素就向 AXI 发起行突发读（一行 960×2B=1920B=120 拍@16B，可 1 个 Burst），写入行 FIFO（容量≥2 行，用 BRAM，960×2B×2≈3.75KB，BRAM 放得下），再以像素节奏读出喂给 HDMI TX；
- **HDMI TX IP**：Efinity 自带，输入 RGB+DE/HSYNC/VSYNC 和 pixel_clk，输出 TMDS 差分对。板卡 03_hdmi_tx_demo 有现成例程，直接改数据源即可；
- **VSYNC 同步**：扫描输出的 VSYNC 引出两路：一路进 CPU（中断/状态查询）用于交换缓冲，一路给引擎（可选：限制引擎只在非显示区写，进一步防撕裂）。

### 3.6 软件架构（RISC-V 端 C 程序）

```
┌────────────────────────────────────────────┐
│  游戏 Demo (main.c)                        │
│  ├─ 精灵对象数组 (x,y,图,α,key,激活标志)    │
│  ├─ 游戏循环: 输入→物理/碰撞→更新精灵        │
│  ├─ 渲染提交: 遍历精灵 → 生成 blt_cmd       │
│  │      → 写 CMD_FIFO → GO                 │
│  └─ 帧结束: 等 VSYNC → swap(Front,Back)     │
├────────────────────────────────────────────┤
│  驱动层 (blt_drv.c/h)                      │
│  ├─ blt_copy(dst,src,w,h)                  │
│  ├─ blt_fill(dst,color,w,h)                │
│  ├─ blt_alpha(dst,src,bg,alpha,w,h)        │
│  ├─ blt_key(dst,src,key_color,w,h)         │
│  ├─ blt_wait_done() / blt_irq_handler()    │
│  └─ fb_swap() (改扫描输出寄存器里的Front指针) │
├────────────────────────────────────────────┤

└────────────────────────────────────────────┘
```

**对比 Demo 设计**（基础要求⑤）：同一个精灵数组，两条渲染路径——
- 软件路径：`for(y) for(x) fb[y*W+x] = sprite[...]`（CPU 逐像素写，可通过 AXI-Lite/直连口写 BRAM 小缓冲再批量写 DDR，但本质上每个像素都要 CPU 参与）；
- 硬件路径：生成指令 → 引擎执行；
- 屏上同时显示"软：xx FPS / 硬：xx FPS"，按键切换。

### 3.7 如果选方案 B（自研 CPU）：差异点

- CPU 核：用你现有的 RISC-V 核，补上 AXI 主机接口（或复用你 SoC 的总线）；
- 需要自己补：AXI 互联（Crossbar/简单仲裁）、中断控制器（timer + 外设中断）、UART（打印调试）、DDR3 通路（把 CPU 接到 DDR 控制器从口）、引导/链接脚本、工具链（riscv-none-elf-gcc + OpenOCD）；

- 其余（BitBlt、显示、驱动、Demo）与方案 A 完全一样。

## 第 5 部分　原理讲解（图形渲染入门篇）

> 每一节都用"你做过 CPU"做类比。先讲清楚"是什么、为什么"，再给"怎么做"。

### 5.1 像素、分辨率、帧缓冲：显存就是一张"大表格"

**是什么**：屏幕是点阵（本项目 960×540 = 518,400 个点；640×480 = 307,200 个点是赛题最低要求的经典例），每个点叫**像素（Pixel）**，每像素一个颜色值。一屏所有像素的颜色数据按行连续存放在内存里，这块内存叫**帧缓冲（Framebuffer）**。

**类比 CPU**：帧缓冲 = 一个 `uint16_t fb[540][960]` 大数组。坐标 (x,y) 的像素地址 = `y × 行距 + x × 每像素字节数`。行距（stride/pitch）= 一行的字节数（本项目 = 960×2 = 1920B，天然 16B 对齐；通常还对齐到 4/16 字节）。

**关键点**：
- 分辨率 = 数组维度；刷新率 = 每秒把这张表"读出来发到屏幕"的次数；
- 渲染 = 往这张表里写像素；显示 = 从这张表里读像素——**读写完全独立，可以并行**（这就是"扫描输出"和"渲染引擎"可以同时工作的基础）；
- 960×540 RGB565 一张表 ≈ 1.0MB；两张（双缓冲）≈ 2.1MB → 只能放 DDR3。

### 5.2 颜色编码：RGB565 与 RGB888

- 屏幕颜色 = 红(R)+绿(G)+蓝(B) 三原色叠加；
- **RGB888**：每通道 8bit，一像素 24bit（HDMI 常见，色彩好）；
- **RGB565**：R5+G6+B5 = 16bit，一像素 2 字节，**带宽省 1/3**，DDR3 带宽利用率高，本赛题推荐（赛题没规定格式，选 RGB565 是合理设计决策，要在文档里写明理由）；
- 显示时把 565 扩展回 888（移位+复制高位），HDMI TX IP 一般支持直接输入 565 或 888，选其一。

### 5.3 视频时序：VGA/HDMI 是怎么"画"出来的

**是什么**：老式 CRT 用电子束从左到右、从上到下逐行扫描。现代 LCD 沿用同一套**时序协议**：一个像素一个像素地送出（像素时钟驱动），每隔一定行数发"行同步脉冲（HSYNC）"，每帧结束发"场同步脉冲（VSYNC）"，同步脉冲之间是**消隐期（blanking）**——不送有效数据，给电子束"回扫"留时间（数字时代它只是协议要求，且现在被用来"隐藏"数字音频/辅助数据）。

**VESA DMT 640×480@60 标准时序**（赛题最低要求，也是经典教学例）：

| 参数 | 数值 |
| --- | --- |
| 像素时钟 | 25.175 MHz |
| 水平：有效 640 / 前肩 16 / 同步 96 / 后肩 48 | 合计 800 |
| 垂直：有效 480 / 前肩 10 / 同步 2 / 后肩 33 | 合计 525 |
| 刷新率 | 25.175M ÷ (800×525) ≈ 59.94 Hz |

**本项目主线：960×540@60**（qHD，1920×1080 的 1/4；非 VESA DMT 标准，采用业界 cvt 生成的 modeline，多款显示器实测可锁）：

| 参数 | 数值 |
| --- | --- |
| 像素时钟 | 37.36 MHz（精确 37.3632MHz） |
| 水平：有效 960 / 前肩 48 / 同步 32 / 后肩 80 | 合计 1120 |
| 垂直：有效 540 / 前肩 3 / 同步 5 / 后肩 8 | 合计 556 |
| 刷新率 | 37.3632M ÷ (1120×556) ≈ 60.0 Hz（极性 +HSYNC/−VSYNC） |

**类比 CPU**：这就是一个**计数器状态机**——水平计数器从 0 数到 799（0~639 送像素，640~799 输出同步/消隐），数完一行垂直计数器 +1，垂直计数器从 0 数到 524，循环。HSYNC/VSYNC 就是计数器到特定区间的输出，和你 CPU 里"地址计数器 + 译码逻辑"没有任何本质区别。**960×540 时只是把上表的边界换成 960/540/1120/556，状态机结构一字不改。**

```verilog
// 简化示意：水平时序
always @(posedge pixel_clk) begin
    hcnt <= (hcnt == 799) ? 0 : hcnt + 1;  // 960×540: 回绕值 1119
    de   <= (hcnt < 640);          // data enable：有效像素（960×540 时换成 960）
    hsync<= (hcnt >= 640+16) && (hcnt < 640+16+96);
end
```

**HDMI 是什么**：HDMI = DVI 的消费级扩展 = **数字化的 VGA 时序 + TMDS 串行编码**：
- 同样的 DE/HSYNC/VSYNC + RGB 像素数据，只是不再并行 24 根线，而是把每 8bit 编码成 10bit（**8b/10b，TMDS**）后，在 3 条差分线上**串行**发（另 1 条差分线发像素时钟）；
- 所以 HDMI 的"像素时钟"与时序分辨率一致：本项目 960×540 用 37.36MHz，每根线比特率 = 37.36×10 = **373.6Mbps/线**（640×480 的 DMT 例为 25.175MHz → 251.75Mbps/线）；
- 板上没有专用 HDMI 芯片，直接用 FPGA 高速 IO（HSIO，支持 1.5Gbps）输出 TMDS——所以时序参数、DE 信号和 VGA 完全一致，**Efinity 的 HDMI TX IP 会替你完成 8b/10b 编码和串并转换**，你只需给它像素时钟 + DE + HSYNC + VSYNC + RGB。

**怎么做**：扫描输出控制器 = 上面那个计数器状态机，`de` 有效期间从行 FIFO 取像素送 HDMI IP；行 FIFO 由 AXI 突发读 DDR 填满（每行 1920B = 120 拍@16B，提前 1~2 行预取，防止行切换时断流——这就是 FIFO 的作用）。

### 5.4 撕裂（Tearing）与双缓冲（Double Buffering）

**问题**：扫描输出在"读"帧缓冲的同时，渲染在"写"同一个帧缓冲。如果写到了一半扫描追上来，屏幕上半是旧帧、下半是新帧——**撕裂**。

**类比 CPU**：一个线程读一个共享数组，另一个线程同时改写它，读到一半的数据是"新旧混合"的——这就是没有锁的共享内存竞争。双缓冲就是"读写各用一张表"。

**双缓冲做法**：
1. 内存里放两张帧缓冲 A、B；
2. 扫描输出永远只读"当前显示的那张"（Front）；
3. 渲染永远只画"另一张"（Back）；
4. 一帧画完，等 **VSYNC 到来**（一帧显示结束的边界）才交换：把扫描输出的 Front 指针改成刚画完的那张，原来显示的变成新的 Back。

交换必须锁在 VSYNC 上（不能在帧中间换），否则又撕裂。VSYNC 由扫描控制器产生，给 CPU 中断或给寄存器查询——这就是"帧同步"。

### 5.5 总线：AXI4 / AXI-Lite / Wishbone 与突发传输

**赛题要求"必须通过系统总线访问内存"**，即引擎不能偷偷用专用口，要按 AXI/Wishbone 规范当总线设备。

**AXI4 五通道**（你已经见过就不细讲）：读地址 AR、读数据 R、写地址 AW、写数据 W、写响应 B。握手信号 VALID/READY。**AXI-Lite** 是简化版（每次固定传 1 个字，用于配置寄存器）；**AXI4 完整版**支持**突发（Burst）**。

**突发（Burst）为什么重要**：
- DDR3 访问有"固定开销"：每次访问要先激活行（tRCD）、有延迟（CAS Latency）、结束后还要预充电——**单次访问的"起步成本"高达几十~上百纳秒**，只传 2 字节等于浪费 99% 时间；
- 突发 = 一次"起步"，连续传 N 个数据（AXI4 单笔突发最多 256 拍 = 256×4B = 1KB；DDR 控制器 IP 通常限制更短，如 16~32 拍）；
- 一次 32 拍的突发（128B）只花"1 次起步 + 32 拍连续"，**效率从个位数百分比提升到 80%+**；
- 这就是赛题点名的"突发传输 + FIFO 缓存"：FIFO 把 DDR 的"一次来一大块"和像素通路的"匀速小口喝"之间缓冲起来。

**对齐**：突发要求起始地址对齐到"突发大小 × 数据位宽"。一行 1920B 若从非对齐地址开始，就拆成"首段不齐（单次读改写）+ 中间整段突发 + 尾段不齐"。写代码时让精灵图在内存里**行首就按 16/32B 对齐**（分配内存时对齐），能省去一半麻烦。

**Wishbone 备选**：如果选自研 CPU 且总线已定 Wishbone，同理——引擎做 Wishbone 从机（寄存器）+ 主机（数据），突发用 WB 的 `CTI`/`BTE` 扩展。但板卡生态（DDR 控制器、HDMI IP）默认 AXI，**推荐 AXI**。

### 5.6 为什么"纯软件渲染"慢、硬件快（量化对比）

| 对比项 | 软件（CPU 逐像素） | 硬件引擎 |
| --- | --- | --- |
| 单像素成本 | 取指→译码→访存→写回，还要经过总线到 DDR3，每像素 **几十~几百 ns** | 流水线 **1 拍（10ns @100MHz）**，DDR 访问用突发摊薄 |
| 吞吐 | ~3~10M 像素/秒（受总线延迟限制） | **100M 像素/秒**（1px/clk） |
| 960×540 满屏重画 | ~50~170ms（6~20 FPS，且 CPU 100% 占用无法跑游戏逻辑） | ~5.2ms（≈190 FPS 的绘制能力） |
| 并行动作 | 画像素时 CPU 干不了别的 | CPU 画完指令后**立刻去跑游戏逻辑** |

关键不在"CPU 主频低"，而在**访存方式**：软件逐像素写 = 每像素一次"慢速小事务"；硬件突发 = 每 128B 一次"快速大事务"。加上硬件把"搬运+混合"流水线化（一个像素处理 = 乘加 1~2 拍），两者差 1~2 个数量级。这就是异构的意义：**让专用硬件做带宽密集的机械活，让 CPU 做逻辑活**。

### 5.7 BitBlt 引擎：带行距的二维内存搬运

**BitBlt（Bit Block Transfer）**：把内存中一块矩形像素数据搬到另一块位置，可附带处理（填充/混合/抠图）。这是所有 2D 图形系统（Windows GDI、游戏）最基础的图元操作。

**关键不是"搬字节"，而是"按矩形搬"**：
- 源矩形、目的矩形在内存里都可能是**非连续**的（源图一行 640B，但只搬中间 100×80 的一块 → 每行只搬 100B，然后跳过 540B 再搬下一行）；
- 所以指令里除了"首地址、宽、高"，还要有**行距（stride）**：`下一行地址 = 本行地址 + stride`；
- 状态机就是两层循环：外层行循环（height 次），内层像素循环（width 次），每次行循环地址加 stride——**和你写 C 的双重 for 循环一模一样，只是做成硬件**。

**COPY 型**（无需读背景）：源突发读 → FIFO → 目的突发写。
**FILL 型**：不需要读源，写通道直接产生常量颜色字节流 → 目的突发写（甚至不需要源 FIFO）。
**设计注意**：COPY 源和目的可能重叠（比如把一个精灵图原地右移 1 像素），此时要按"从后往前"或"分方向"拷贝，否则覆盖未读数据（软件 memmove 同样的问题）。赛题 demo 通常不需要重叠拷贝，但文档里写清楚这个考虑是加分点。

### 5.8 Alpha 混合：每像素一次乘加

**公式**（赛题给的）：
```
out = fg × α + bg × (1 − α)
```
- fg = 前景像素（精灵），bg = 背景像素（目的缓冲里已有的），α = 透明度（0 全透明 ~ 1 全不透明）；
- 所以混合必须**先读背景**（DDR 多一次读），三通道各算一遍；
- **定点数**：α 用 0~255 整数表示（255 = 不透明），则 `1−α = 255−α`：
  ```
  out = (fg×α + bg×(255−α) + 127) >> 8   // +127 是四舍五入
  ```
  全部是整数乘加移位——你写 CPU 时熟悉的定点技巧，这里做成硬件流水线。
- **硬件实现**：RGB565 三通道（5/6/5 bit）各一组"乘加+移位"，即每像素 6 个乘法器（或等价）。Ti60 有 **160 个 DSP 块**，引擎 1px/clk 只耗 ~6~12 个 DSP，余量巨大。也可用 LUT 乘法器（BRAM 查找表）省 DSP；
- **流水线**：和你 CPU 的 EX 级一样——`读fg/读bg(并行) → 乘(2拍) → 加/移位(1拍) → 写回`，每拍吞吐 1 像素。**只做半透明精灵时，混合也可以按"每精灵整体 α"（constant alpha）做，不读像素自带的 α 通道，省带宽**。

### 5.9 色彩键控（Color Keying）：绿幕抠图的硬件版

- 设定一个"透明色"（如纯品红 0xF81F），引擎在像素通路加**比较器**：`fg == key ? 跳过 : 写回`；
- 效果：不规则形状的精灵（如弹幕子弹、人物）在透明背景上绘制时，背景色不写入 → 精灵边缘是干净的任意形状；
- **和 α 混合的区别**：抠图是"要么全写、要么不写"（硬边），α 是"写一半"（软边/半透明）。两者可组合：先抠图再做 α；
- **省钱点**：抠图跳过时**不写 DDR**，省带宽；如果整行都透明甚至可以不发起写突发（行尾判断）。
- 类比：你做 CPU 时的条件写（`if (valid) mem[addr] <= data`），加一个"颜色相等判断"而已。

### 5.10 精灵（Sprite）与合成顺序：画家算法

- **精灵** = 一张小图 + 位置 + 绘制方式（拷贝/α/抠图）。一屏几十上百个精灵，就是几十上百条 BitBlt 指令；
- **合成顺序**：像画家一样，**先画背景/远处的，再画前景/近处的**——后画的覆盖先画的（画家算法）。游戏里就是"按 z 序排序指令下发顺序"；
- 引擎按指令 FIFO 顺序执行 → 顺序天然就是 z 序。所以 **CPU 只需把精灵按 z 序排好写进 FIFO，引擎不用知道"图层"概念**；
- 优化技巧：背景（每帧不变的静态图）不需要每帧重画——只画"变化的矩形区域"（脏矩形）。精灵引擎里：先清一次 Back（fill 黑色或背景），再画所有精灵，最后 swap。清屏也是 Fill 指令，全屏 518K 像素 ≈ 5.2ms，占帧预算 31%，可接受（也可用脏矩形清屏降到更低）。

### 5.11 FIFO 与跨时钟域（你写异步 FIFO 的话这节等于复习）

系统里有 3 个时钟域：core 100MHz（引擎/CPU）、pixel 37.36MHz（显示 960×540）、DDR 400MHz（内存）。凡是跨域的，一律 FIFO：

| 位置 | 时钟域 | 用途 | 深度参考 |
| --- | --- | --- | --- |
| 行 FIFO（扫描输出） | DDR读侧 100M → 显示侧 37.36M | 缓存一整行像素，防行切换断流 | ≥2 行 = 960×2B×2 ≈ 3.75KB（深度 2048×16bit） |
| 引擎源 FIFO | DDR 读突发 → 像素通路 | 吸收 DDR 延迟抖动 | 1~2 个突发长度 |
| 引擎目的 FIFO | 像素通路 → DDR 写突发 | 攒够一突发再写 | 1~2 个突发长度 |
| 指令 FIFO | CPU 写 → 引擎读 | 批处理指令（同域 FIFO 即可） | 64~256 条 × 32B |

写 FIFO 用 Efinix IP（简单双口 RAM + 读写指针）或你熟悉的异步 FIFO 结构。BRAM 256×10Kbit 里这些 FIFO 加行缓冲总共用不到 10 块，剩余大量可给引擎缓存/精灵缓存。

### 5.12 FPS 统计与性能瓶颈（怎么算"同屏精灵极限"）

**FPS 怎么数**：帧计数器每画完一帧 +1，定时器（如 1s 中断）采样：`fps = frames_delta / time_delta`，把数字用 8×8 字库渲染到屏幕角落。这是全系统"性能仪表盘"，赛题明确要。

**瓶颈链条（按顺序检查）**：
1. **引擎吞吐**（像素/秒）：1px/clk×100MHz=100Mpx/s。一帧预算 16.7ms → 每帧最多 1.67M 像素的绘制量；
2. **DDR3 带宽**：α 混合每像素 3 次访存（读fg+读bg+写）= 6B/px @RGB565 → 1.67Mpx/帧 = 10MB/帧 = 600MB/s，加上扫描输出 62MB/s，仍低于 1.2GB/s 可用带宽（**带宽不是瓶颈，但 α 比拷贝多 3 倍流量，量级要先算**）；
3. **指令下发**：CPU 写 FIFO 的速度（每指令 8 字，几百时钟）。上千精灵时 CPU 侧也要优化：批量写、指令结构体打包、避免逐条查状态；
4. **显示扫描本身**：只读，62MB/s，永远不是瓶颈。

**32×32 RGB565 精灵极限粗算**（960×540，引擎 1px/clk @100MHz）：
```
每帧绘制预算  = 100M px/s ÷ 60fps ≈ 1.67M px
32×32 精灵    = 1024 px
理论上限      ≈ 1600 个/帧
扣除 α 混合的 DDR 带宽开销 + 指令下发 + 清屏等 ≈ 实际几百 ~ 1000+ 个
```
拿到这个数字再上板实测，测出来的"60FPS 同屏极限"就是答辩数据。想翻倍：引擎做 2px/clk、或把时钟提到 150MHz+、或精灵缓存进 BRAM（热精灵免 DDR 读）。
